# M154: автоматическая история экспериментов и память уроков

Пользователь разрешил автоматически сохранять и отправлять изменения, проверки и неуспешные результаты экспериментов. Этот инструмент выполняет данное правило для явно подготовленного пакета изменений.

## Запуск текущего пакета

Скачать один `SkynetVS_M154_AutoExperiment.ps1` и выполнить обычным PowerShell:

```powershell
& "$env:USERPROFILE\Downloads\SkynetVS_M154_AutoExperiment.ps1"
```

ZIP с исходниками, тестами и планом встроен в PS1. Используется уже существующий Python проекта `C:\Project\SkynetVS\.venv\Scripts\python.exe` либо существующий ModelLab Python. Установка зависимостей и ручные git add/commit/push не нужны. Публикация использует обычную уже настроенную аутентификацию локального Git.

Текущий пакет добавляет именно `tools/m154_workflow/` в самостоятельную экспериментальную копию на базе `3cd5a06b3b17ce2e6b9b25351a1b455289974dfb`. Его цель — проверка автоматизации и памяти, `AUTOMATION_SELFTEST`. Полный pipeline исходного изменения напоминаний остаётся отдельной следующей проверкой M154.

## Что выполняется автоматически

1. Создаётся короткий каталог `%USERPROFILE%\m154a_<id>` и запись попытки.
2. Коммит исходного проекта копируется в независимый Git без hardlinks. Незакоммиченные пользовательские изменения не включаются в эту копию.
3. Применяются только перечисленные в `plan.json` файлы с проверкой исходных и новых SHA256.
4. До тестов создаётся коммит кандидата в `experiments/m154/<run_id>`.
5. Выполняются проверки с реальным exit code и ограничением времени.
6. При PASS, FAIL, ошибке запуска или timeout сохраняются результат, диагностика, план, patch, ограниченные очищенные логи и наблюдение для памяти.
7. Отчёт коммитится локально до сетевых операций. После этого обычным push отправляются ветка эксперимента и дополнение в `reports/m154`.

`main` и `sandbox/m154` не продвигаются этим инструментом. Проверенный коммит указан в каждом отчёте. Сгенерированные тестами файлы не добавляются в candidate commit автоматически. Непрошедший тест сохраняет свой ненулевой exit code даже после успешного push.

## Повтор после ошибки сети

Повторить ту же команду. Launcher найдёт сохранённую попытку данного пакета и повторит публикацию без запуска тестов. Если предыдущий процесс аварийно завершился, его доступные данные публикуются как `INTERRUPTED`; неизвестный exit code дочернего процесса не придумывается. Одновременный второй запуск той же попытки блокируется обычным файловым lock ОС.

Если специально нужен новый тестовый запуск того же пакета:

```powershell
& "$env:USERPROFILE\Downloads\SkynetVS_M154_AutoExperiment.ps1" -NewRun
```

Новый запуск не исправляет старую ошибку автоматически. Для ошибки теста нужен разбор и следующий пакет исправления; для ошибки публикации достаточно retry. Никакой фоновой службы и автоматического мониторинга чата нет.

## Результат в Git

Код и включённые проверки: ветка `experiments/m154/<run_id>`.

Данные запуска: `reports/m154`, каталог `reports/M154/<run_id>/`:

- `summary.json`: результат, code commit, этапы, исходные exit codes и границы проверки;
- `diagnostics.json`: структурированные причины отказа обёртки;
- `receipt.json`: SHA256 и размер каждого явно публикуемого файла;
- `plan.json`, `change.patch`: воспроизводимый состав изменения и команды проверок;
- `logs/*.txt`: захваченный вывод именно запущенных проверок, до 64 КиБ на файл, с заменой известных абсолютных путей и типовых секретных значений;
- `observation.json`: наблюдение PASS/FAIL без автоматически выдуманной причины;
- `Development_Context.md`: релевантные проверенные уроки для следующей разработческой задачи.

Сырые полные логи остаются в `private_logs` каталога запуска. Публикатор берёт только файлы из receipt и проверяет их хеши. Посторонние файлы в `public`, весь рабочий каталог, окружение и файлы учётных данных не собираются. Очистка вывода не является универсальной гарантией для произвольной будущей команды: будущий подготовленный план должен учитывать, какие данные печатают его проверки.

История подготовки самого инструмента содержит реальный неудачный тест `qa001_isolated_import`: исходный тест, лог ошибки, исправляющий diff и успешный повтор. Она сохранена в `preparation_history/` и попадёт в экспериментальный коммит вместе с инструментом.

## Память агента

В `lessons.json` шесть проверенных уроков M154. Каждый содержит симптом, установленную причину или границу доказательства, правило предотвращения, применимость и ссылки/хеши доказательств. Новый провал автоматически записывается как `observed_only`, с `root_cause=null` и `training_label=null`. После разбора подтверждённый урок можно добавить вместе с регрессионной проверкой.

`development_lessons.py` выбирает до пяти релевантных уроков и ограничивает контекст 8192 байтами. В отчёте фиксируются ID фактически включённых уроков. Нерелевантной задаче соответствует пустой контекст.

Программное подключение к существующему локальному LLM предусмотрено через `LessonsModelAdapter(existing_llm, selected)`: адаптер подходит к уже имеющемуся `review_repository(..., llm=adapter)`. Он сохраняет system и исходный prompt, добавляет исторический контекст и записывает квитанцию использованных уроков. Сам конструктор не вызывает модель.

Текущая GUI-кнопка собственного AST-анализатора ещё не подключена к этой новой памяти. Его ранжировщик учится на размеченных AST-находках; ошибки Git и запуска не являются такими метками. Веса моделей в этом пакете не переобучаются, реальный Ollama не вызывается, DTR_Request.json и fingerprint не меняются. Пакет создаёт проверяемую основу памяти и автоматический поток наблюдений.

## Проверка инструмента

```text
python -I -S -B tools/m154_workflow/test_workflow.py
python -I -S -B tools/m154_workflow/test_git_transport.py
python -I -S -B tools/m154_workflow/test_development_lessons.py
```

Проверки используют собственные временные Git-репозитории и локальные bare remotes. В них намеренно моделируются FAIL, timeout, отсутствие сети, несовпадение SHA, конкурирующее дополнение отчёта, повторная отправка и незакоммиченная работа. Эти ожидаемые ошибки внутри fixture не означают ошибку реального проекта.

## Границы результата

Это инструмент пользовательских экспериментов. Он не выдаёт полномочия DTR, не применяет изменения к рабочему проекту и не закрывает pending `pipeline(flow=check)` прежнего предложения напоминаний. Успех транспортного теста подтверждает именно транспорт, а не поведение всего SkynetVS.

Исходный clone проверяется по HEAD, refs, index/config, Git status и diff отслеживаемых файлов. Это не побайтовый аудит всех ignored-файлов. Windows-специфические ветви process tree / PowerShell требуют фактического Windows-запуска; локальные проверки автора выполнены на Linux.
