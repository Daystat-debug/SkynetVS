# Учёт исправлений по событиям: явное включение и повторяемая проекция

Документ M154, сообщение №96. База исходников:
`7674fc616850e1071b8fd25cc5e849964527c94c`.

## Что меняется

Пакет связывает writer `LearningMemory`, постоянный SQLite ledger и builder
памяти исправлений. Новый режим включается отдельной операцией. Обычный запуск
приложения, builder или pipeline не создаёт новый период учёта и не выполняет
миграцию автоматически.

Это реализация протокола и его проверки на собственных синтетических данных.
Установочный launcher №96 не читает пользовательскую историю/память/ledger,
не создаёт пользовательский epoch, не включает новый режим и не запускает
приложение, модели, обучение, promotion либо полный pipeline. Его публичный
Result должен разделять наличие кода и фактическую активацию.

Документы о компонентах №92–95 остаются историей их первоначального объёма.
Этот документ описывает последующее подключение. Низкоуровневые API по-прежнему
сами не переключают режим и не изменяют approval/status кандидатов.

## Почему необходим отдельный признак перехода

Прежний builder передавал накопительные группы в
`CorrectionMemory.sync_cumulative_candidates(..., source="feedback_analyzer_v2")`.
Его checkpoint — максимум размера группы, а не множество идентификаторов.
Уже существующие `seen_count` могут содержать неизвестное историческое
завышение: данный переход не пытается угадать и исправить его.

Новый источник нельзя передать в тот же API как очередной delta. В частности,
первое обращение с новым source к существующей строке делает legacy baseline
и не прибавляет количество. Такая комбинация потеряла бы первую порцию новых
наблюдений. Новый модуль проекции поэтому имеет собственный event checkpoint.

Одного наличия SQLite-файла также недостаточно для выбора режима: пропавшая БД
не должна возвращать ранее активированный проект к старому начислению. Для
этого хранится маленький отдельный control-файл. Его отсутствие допускает
legacy только при отсутствии ledger/его sidecar и event checkpoint в памяти.

## Постоянные приватные файлы

| Путь внутри проекта | Назначение |
| --- | --- |
| `data/learning/command_history.jsonl` | История наблюдений; старые строки не переписываются и не получают epoch задним числом |
| `data/learning/correction_memory.jsonl` | Существующие кандидаты, счётчики и новый checkpoint в одной строке |
| `data/learning/correction_evidence.sqlite3` | Принятые идентификаторы, полные payload, пары и использованные endpoints |
| `data/learning/correction_evidence_runtime.json` | Сохранённый выбор PREPARING/ACTIVE и epoch |
| `data/learning/correction_evidence_runtime.lock` | Постоянный файл для блокировки средствами ОС; его наличие не означает активацию |

Control имеет закрытую схему:

```json
{"kind":"SKYNETVS_CORRECTION_EVIDENCE_RUNTIME_CONTROL_V1","version":1,"state":"ACTIVE","epoch":"32 lowercase hexadecimal characters"}
```

В PREPARING значение epoch равно `null`. Неизвестное поле, неверный тип,
повторяющийся JSON-ключ, повреждённый/пустой/слишком большой control — отказ,
а не повод восстановить legacy. Ограничение control — 4096 байт.

Новые точные правила `.gitignore` закрывают control, lock и короткоживущий
соседний файл `.correction_evidence_runtime.json.*.tmp`. Четыре правила для
SQLite и sidecar были добавлены в №95 и сохраняются. Игнорирование не заменяет
резервное копирование; программа не удаляет и не пересоздаёт эти состояния
автоматически.

## Режимы и явная активация

| Состояние | Новое наблюдение writer | Обычный builder |
| --- | --- | --- |
| Control отсутствует, нет ledger/sidecar и event checkpoint | Запись с новым `event_id`, без epoch | Прежнее накопительное начисление под общей блокировкой |
| PREPARING | Разрешена новая строка без epoch | Отказ `ACTIVATION_PENDING`, без старого начисления |
| ACTIVE | Новая строка получает точный epoch из control | Валидация ledger/epoch, sync и проекция полных totals |
| Повреждённый control, orphan ledger, иной epoch, недоступный active ledger | При неверном control writer отказывает в записи; БД на каждую команду не читает | Отказ с фиксированным кодом, без fallback |

Активация выполняется `activate_learning_evidence(repo)` под той же
блокировкой, что writer и builder:

1. Проверяется существующая память исправлений строгим reader. Наличие
   `event_evidence` при отсутствии control — `MISSING_CONTROL_STATE`.
2. Через исключительное создание сохраняется PREPARING. С этого момента
   обычный builder не может выбрать legacy.
3. Если ledger отсутствует, существующая полная история становится baseline
   нового ledger. Начальное число принятых пар равно нулю.
4. Читаются и проверяются ledger и его epoch. Для возобновления PREPARING
   допустим только валидный ledger без принятых пар. Память снова проверяется,
   даже если это повтор после прерывания предыдущей попытки.
5. Control заменяется целиком на ACTIVE. Существующая история и память
   исправлений не переписываются. Последующие новые наблюдения получают epoch.

Повтор с валидным ACTIVE и совпадающим epoch возвращает UNCHANGED. Пустой или
частично созданный ledger/control сохраняется для разбирательства. Нет
автоматического удаления, сброса, импорта другого epoch или восстановления
неизвестной истории. Если запись ACTIVE имела неопределённый исход, повтор
сначала читает фактически сохранённый control.

Перед первым реальным включением нужно завершить старые процессы приложения
и builder: загруженный старый Python-код не знает о новой блокировке. Новые
версии writer, builder и activation используют общий протокол. Реальные
данные и их пригодность проверяются отдельным последующим шагом; успешный
синтетический suite не доказывает, что приватная история допускает активацию.

## Общая блокировка и основной путь команды

`learning_evidence_lock(base_dir)` использует неблокирующую блокировку одного
байта через `msvcrt.locking(..., LK_NBLCK, 1)` на Windows и `fcntl.flock` на
POSIX. Дескриптор закрывается после операции; ОС освобождает блокировку также
при завершении процесса. Сам lock-файл не удаляется и не имеет «срока
протухания». Подменять защиту удалением такого файла нельзя.

Блокировка охватывает:

- выбор режима и запись одной новой строки `LearningMemory.log_command`;
- активацию, включая baseline и сохранение ACTIVE;
- выбор legacy и его чтение/запись либо полный event build.

Поэтому legacy builder, уже вошедший в защищённую секцию, не пересекается с
активацией; writer не получает epoch из незавершённого перехода. Lock-файл
может появляться и в legacy-режиме — это раскрытый побочный эффект новой
координации, а не включение event counting.

Занятая блокировка даёт фиксированный `BUSY`. Writer не делает обходную
незащищённую запись. Ожидаемый `RuntimeRefused` при сохранении наблюдения
обрабатывается на границе `CommandProcessor`: основное выполнение команды
продолжается, а отказ обучения фиксируется без приватного текста команды.
Это не означает, что наблюдение было сохранено: пропущенная запись не
становится учебным свидетельством. Другие ошибки не маскируются как BUSY.

Произвольные внешние редакторы, старые процессы, прямой вызов legacy API
`CorrectionMemory` и низкоуровневых ledger API эту блокировку не обязаны
соблюдать. Проектный единственный builder переведён на координатор; полной
сериализации любых внешних программ не заявляется.

## Полные totals из ledger

`read_correction_evidence_totals(repo)` возвращает приватный результат вида
`SKYNETVS_CORRECTION_EVIDENCE_TOTALS_V1`. READY содержит epoch, полное число
принятых пар и накопительные кандидаты. При отказе кандидаты очищаются.
Текущая command history при этом не читается и не синхронизируется.

Чтение использует существующий ledger и одну SQLite-транзакцию. Сохраняются
закрытая V1-схема и лимиты №95. Каждая принятая пара дополнительно проверяется
по двум сохранённым полным payload, их ID, epoch, baseline-флагам и результату
зафиксированного planner. Исходные индексы проверяются как соседние позиции;
сам planner для повторной проверки получает два endpoint. Семантически
несогласованная пара не превращается в начисление только потому, что JSON
синтаксически корректен.

Нормализованный ключ совпадает с `CorrectionMemory._make_key`. Пары обходятся
в порядке их первоначального приёма (`pairs.rowid`; поддерживаемый API их не
удаляет и не вставляет заново). Тексты сохраняются от первой пары группы,
confidence берётся по максимуму, позднее принятые slots обновляют одноимённые
ключи. Это порядок приёма, а не доказательство хронологии независимых событий.

Поздний карантин уже принятого endpoint не отзывает старую пару — это
сохранённый контракт ledger №95. Проверка не аутентифицирует состояние и не
обнаруживает любой согласованный откат одновременно БД и памяти. SQLite может
выполнить восстановление hot journal, поэтому API не обещает абсолютного
отсутствия файловых изменений при чтении или отказе.

## Проекция в существующую память

`project_correction_evidence(repo, expected_epoch=...)` использует отдельное
поле строки:

```json
"event_evidence": {"version": 1, "epoch": "…", "observed_count": 3}
```

Для существующей строки без этого поля предыдущий event total равен нулю.
Сохранённый `seen_count` не обнуляется и не пересчитывается задним числом.
Если ledger содержит 3 пары, а checkpoint равен 2, прибавляется только 1.

Например, старый `seen_count=99` после первой новой пары становится 100.
Повтор остаётся 100. Следующая новая пара даёт 101. Старый
`cumulative_evidence.feedback_analyzer_v2`, status, created_ts, неизвестные
поля и остальные строки сохраняются. Новые строки имеют status `candidate`.
Никакого автоматического approval или promotion нет.

При положительном росте обновляются `seen_count`, event checkpoint,
`last_seen_ts`, объединение slots, максимальный confidence и source
`correction_evidence_v1`. Даты отражают момент проекции, как и в прежнем
builder; они не выдаются за timestamp исполнения действия. Если новых
свидетельств нет, запись не производится: байты и mtime остаются прежними.

Checkpoint иной epoch, число больше полного total, отсутствие ранее
положительно учтённого ключа или `seen_count` меньше event checkpoint
приводят к отказу всей проекции. Повреждённая память не переписывается с
выбрасыванием неудобных строк.

Сериализуются все строки; счётчик и checkpoint заменяются одним вызовом
существующего `_write_snapshot`, с flush/fsync временного файла и
`os.replace`. Это одна замена JSONL, не общая транзакция SQLite+JSONL.

| Место прерывания | Что делает повтор |
| --- | --- |
| Ledger ещё не принял пару | Повторный sync проверяет реальные сохранённые ID и пары |
| Ledger принял пару, память ещё не заменена | Полные totals снова дают недостающую разность |
| Память уже заменена, сообщение об успехе не дошло | Сохранённый checkpoint подавляет повторное начисление |
| Исключение во время замены, исход неизвестен | `MEMORY_WRITE_OUTCOME_UNKNOWN`, без заявления об успешной прибавке; повтор читает файл |
| Неполная/некорректная текущая история в обычном event build | Sync отказывает; legacy не запускается. Отдельная проекция сохранённых totals не требует текущей истории |

Memory limit — 64 MiB по предварительному stat и размеру выходной
сериализации, 100 000 строк после чтения. Это не строгий потоковый предел
памяти при бесконтрольном параллельном дописывании. Метаданные файла
проверяются повторно; это обнаружение обычного вмешательства, а не атомарный
compare-and-swap против враждебного процесса. Защиту от потери питания на
нескольких файлах, rollback приватных резервных копий и любые особенности
сетевой файловой системы данный протокол не обещает.

## Builder, CLI и pipeline

`tools/build_correction_memory.py` вызывает координатор до чтения analyzer.
В ACTIVE при отказе ledger, epoch, history или projection он возвращает
exit 2 с фиксированными кодами. Legacy fallback отсутствует.

Отдельная опция `--activate-evidence` выполняет только явную активацию;
обычный вызов builder выполняет выбранное начисление. Поддерживается
`--repo` с локальным корнем. Из корня проекта модуль можно вызвать как
`python -m tools.build_correction_memory`; реальная активация не входит в
установку пакета №96.

Описания эффектов `pipeline` теперь указывают чтение control/ledger,
создание/использование lock и условную запись SQLite/journal в активном
режиме. Обычные analyze/full не активируют режим. Изменены только описания
эффектов, не исполнение pipeline, его критерии успеха или promotion.

## Проверки и границы результата

Используются восемь прежних именованных suites, отдельные suites проекции и
runtime и существующий `eval_pipeline_effects`. В старых idempotence/identity
fixtures добавлены изолированные зависимости, но прежние сценарии и
assertions сохранены. Новая ветка отказа `CommandProcessor` проверяется
листовым импортом с синтетическими зависимостями, без загрузки dotenv,
Settings, приложения или модели.

Проверяются restart/replay, первое начисление существующей строке,
preservation старых полей, BEFORE/AFTER replace failures, PREPARING resume,
orphan/missing/foreign ledger, block contention и раскрытие побочных эффектов.
Конкретное число и результат checks фиксируются в Result и полном handoff.

Подготовка на Linux не заменяет запуск тех же suites на Windows/Python 3.12.
Наличие event_id, epoch и ledger не доказывает независимость наблюдений,
успех действия, правильность intent или готовность данных к обучению.
Обучение `nlu_intent.joblib` и внутреннего агента этим пакетом не запускается.

общие свойства примитивов ОС/SQLite не расширяют их до общей транзакции всех
файлов проекта.
