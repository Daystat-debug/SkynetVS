Перенос блока в main отложен до его завершения.

## Назначение и место в текущем проекте

Новый модуль `modules/learning/correction_pair_evidence.py` формирует
эвристические кандидаты пар «непринятая команда → принятая формулировка»
и сохраняет ID обоих исходных наблюдений. Это чистая функция над переданными
значениями: она не читает файлы, не импортирует приложение, не пишет память,
не обучает модель и не запускает действия ОС.

Модуль пока не подключён к `FeedbackAnalyzer.analyze()` или builder. Их
исходники, отчёты, накопительные счётчики и правила promotion остаются прежними.
Подготовка такого модуля не означает включения событийного учёта в приложении.

Основание для отдельной реализации установлено по точным исходникам:
существующий `_read_jsonl()` пропускает неразобранные строки, а
`_find_correction_pairs()` сортирует оставшиеся объекты по времени. После
пропуска строки уже нельзя установить, были ли два объекта соседними в
исходной истории. Добавление ID в итоговый агрегат не восстанавливает эту
информацию. Поэтому V1 явно задаёт контракт последовательности до интеграции.

Предыдущие этапы:

- [`SKYNETVS_LEARNING_EVENT_IDENTITY_V1.md`](SKYNETVS_LEARNING_EVENT_IDENTITY_V1.md) — ID новых строк;
- [`SKYNETVS_LEARNING_EVENT_PAYLOAD_AUDIT_V2.md`](SKYNETVS_LEARNING_EVENT_PAYLOAD_AUDIT_V2.md) — диагностика одинакового ID с разным содержимым.

## Входной контракт и полнота

Публичная точка вызова:

```python
plan_correction_pair_evidence(rows, *, snapshot_complete: bool)
```

Флаг полноты обязателен и должен быть именно `bool`. Переданная последовательность
должна сохранять исходный порядок и позиции, включая непригодные строки.
Будущий строгий читатель обязан оставлять для неразобранной строки отдельную
позицию-барьер. Он не должен сначала удалять ошибки, legacy-строки или дубликаты.

`snapshot_complete=True` — утверждение вызывающей стороны, а не доказательство,
что она действительно прочитала весь файл и сохранила позиции. По уже разобранным
объектам нельзя восстановить пропущенную JSON-строку, исходные повторные ключи
JSON или изменения файла во время чтения. Производственный строгий reader
с проверкой снимка и передачей барьеров остаётся отдельной задачей.

При неполном входе, неподдерживаемом контракте, исчерпании ресурса или
несовместимом режиме времени результат содержит `status=REFUSED`, фиксированную
причину и пустой список `pairs`. Частичные кандидаты не выдаются как полный
план. `READY` означает, что функция закончила обработку своего входа;
это не готовность данных к обучению и не отсутствие непригодных строк.

Входные объекты не изменяются. Вложенные данные слотов в результате отделены
от объектов вызывающей стороны. Результат содержит производные приватные
данные: его нельзя автоматически коммитить или печатать в публичный отчёт.

## Исходный порядок и барьеры

Планировщик рассматривает только две непосредственно соседние позиции
переданного порядка. Он не сортирует записи, не удаляет строки и не перескакивает
через непригодное наблюдение. Временная отметка проверяет допустимый интервал
между этими соседями, но не определяет их порядок заново.

Барьером для пары является:

- legacy-строка без пригодного ID;
- неподходящий объект, тип поля или содержимое;
- любое появление повторённого ID, даже при одинаковом payload;
- любое появление ID, у которого обнаружены разные варианты payload.

Повторяемость ID проверяется по всему переданному входу до выдачи пар. Поздняя
копия поэтому блокирует и раннее появление того же ID. Видимый пригодный ID
не должен исчезать из глобального учёта только потому, что остальные поля
его объекта непригодны. Это препятствует принятию раннего объекта, если
позже встречается повреждённый объект с тем же ID.

Ни одна физическая копия повторённого ID не выбирается как автоматически
достоверная. Такая политика может отложить пригодные наблюдения, но не создаёт
новую пару путём удаления строк. Отдельное будущее решение о принятии одной
копии потребует сохранения контекста и проверки ранее учтённых событий.

| Последовательность позиций | Поведение |
|---|---|
| Непринятая A, принятая B; оба ID пригодны и уникальны | Возможна одна пара A → B |
| Непринятая A, барьер, принятая B | Пары A → B нет |
| A, B, затем повтор ID A | Все появления A блокируются; ранняя пара не выдаётся |
| Две копии A, две копии B | Копии не превращаются в независимые подтверждения |
| Две разные пары с разными ID и одинаковыми текстами | Это разные кандидаты по ID; независимость наблюдений не доказана |

## Пригодность соседней пары

Для чистых, корректных, идентифицированных наблюдений сохраняется смысл
прежней эвристики: первое наблюдение не принято, второе принято, между ними
от 0 до 60 секунд включительно, у второго есть intent, confidence не ниже
0.40 и нет недостающих слотов. Тексты непусты и различаются; фразы просьбы
повторить («повтори», «еще», «ещё») исключаются по прежнему правилу.

Типы проверяются строго. Строка `"false"`, число вместо bool или NaN confidence
не получают смысл через неявное приведение truthiness/float. Числовая confidence
должна быть конечной и лежать в диапазоне от 0 до 1. Более строгая проверка
типов намеренна; поведение на повреждённых/нестандартных входах не обещает
совпадать с прежним читателем и агрегатным подсчётом.

Поддерживается история с разбираемыми naive-отметками либо история с aware-
отметками. Смешение этих режимов не переинтерпретируется: весь план отклоняется.
При aware-отметках интервал определяется их значениями с часовыми смещениями.
Отрицательный интервал между соседями не даёт пары; перестановки записей для
исправления времени не происходит. Совпавшее время сохраняет исходный порядок.
Наличие правильной временной строки не доказывает доверенность часов или
хронологическую полноту журнала.

## Содержимое и идентичность кандидата

ID сравнивается как точная непустая строка; он не обрезается, не приводится
к общему регистру и не вычисляется из текста или времени. Формат writer UUID4
hex сохраняется, но API не приписывает UUID исключительную доверенность.

Сравнение пригодных JSON-payload соответствует контракту аудитора V2:
весь объект, сортировка ключей JSON, ASCII-экранирование, компактные разделители,
запрет нечисловых float. Порядок ключей/форматирование/эквивалентные escapes
несущественны после разбора; строки, массивы и int/float/bool различаются.
Сохраняются ограничения округления float при исходном JSON-разборе.

Каждый кандидат несёт структурированную идентичность:

```json
{
  "rule_version": "adjacent_unique_observation_v1",
  "failed_event_id": "ID первого наблюдения",
  "corrected_event_id": "ID второго наблюдения"
}
```

Структура избегает неоднозначности склеивания строк через разделитель. В
результате также сохраняются исходные позиции и поля кандидата: обе формулировки,
corrected intent/confidence/slots и интервал. Это приватный предварительный
результат; автоматического увеличения `seen_count` в нём нет.

Для выходного `corrected_intent` сохраняется прежнее преобразование `.upper()`
без удаления окружающих пробелов. Проверка непустого intent использует `strip()`,
но проверка пригодности и преобразование возвращаемого значения — разные шаги.
Это сохраняет поля старого кандидата и для допустимой строки intent с пробелами.

Идентичность не включает доказательство подлинности или криптографическую
привязку всего содержимого. Два вызова на разных снимках могут вернуть тот же
набор endpoint IDs с изменившимся payload, если прежнего payload уже нет во
входе. Между вызовами функция ничего не запоминает. Она также не узнает,
что один и тот же accepted ID уже использовали с другим предшественником
в прошлом снимке. Эти проверки относятся к будущему постоянному реестру.

В пределах одного готового плана принятое наблюдение не используется второй
раз: его ID уникален во входе, позиция одна, пара задаётся непосредственным
предшественником, а принятая строка не становится непринятым концом следующей
пары. Это ограничение одного снимка, а не долговременная гарантия exactly-once.

## Границы ресурсов и отказ

Константы модуля задают конечные размеры входа, глубины JSON, количества
элементов и канонического представления:

| Ограничение | Значение |
|---|---:|
| Входных позиций | 100 000 |
| Глубина JSON | 64 |
| Узлов JSON в одной строке | 100 000 |
| Канонические байты одной строки | 1 MiB |
| Канонические байты всего входа | 64 MiB |
| Разрядность целого числа перед сериализацией | 16 384 бита |
| Учтённые посещения узлов во всём входе | 8 000 000 |
| Общий бюджет обработки скаляров и контейнеров | 64 × 1024 × 1024 условных единиц |

Это границы обработки уже переданных значений, а не предел всего RAM процесса.
Вход — именно встроенный `list` или `tuple`, а не произвольный iterable с
неограниченным вычислением элементов. Проверки выполняются до неограниченного
кодирования/копирования вложенных данных. Неподдерживаемые пользовательские
объекты не сериализуются через repr или пользовательские методы.

Общий бюджет работы учитывает и попытки разбора объектов, которые в итоге
оказались непригодными для сериализации. Длины ID и временной строки
проверяются и учитываются до `strip()` и разбора даты. Повторное обращение
к тому же значению может повторно расходовать бюджет: это консервативная
оценка работы, а не размер уникальных данных или точное количество байтов RAM.
Один только лимит успешно сериализованных payload не ограничил бы длинную
последовательность повреждённых строк.

При превышении ограничения выход не содержит ранее найденных кандидатов.
Это отказ от плана, а не молчаливое усечение до top-10 или другого окна.
Пригодность одного полного входа не означает, что библиотека подтверждает
происхождение файлового снимка, отсутствие конкурирующего писателя или
историю событий после ротации.

## Переход к накопленной памяти — отдельный этап

Для подключения нового пути потребуются:

1. Строгий reader, который сохраняет позиции непригодных строк и передаёт
   проверенную полноту входного снимка без пропусков и сортировки.
2. Сохранение привязки ID к содержимому и уже использованных accepted endpoint
   IDs между снимками, в том числе после ротации или редактирования истории.
3. Явная граница между прежним накопительным агрегатом `feedback_analyzer_v2`
   и новым учётом. Одну пару нельзя прибавлять через оба пути.
4. Согласованные правила записи, восстановления после сбоя и конкурирующих
   писателей, прежде чем заявлять долговременную защиту от повторов.

Старым строкам нельзя присвоить вымышленные доверенные ID задним числом.
Прежние `seen_count`, status, metadata и checkpoints сохраняются. Наличие
этого модуля не исправляет исторические завышения и не меняет promotion.
Обучение кандидата модели и решение о замене активной модели — отдельный блок.

## Проверки и доставка

`tools/eval_correction_pair_evidence.py` проверяет чистую функцию на собственных
синтетических значениях. Дополнительно выполняются прежние 126 именованных
проверок: 32 границ пакетов, 23 памяти, 43 аудитора, 10 writer и 18 payload V2.
Настоящая история, приложение, модели, обучение и полный pipeline не запускаются.

Пакет `SkynetVS_M154_AddCorrectionPairEvidence.ps1` применяет четыре закреплённых
файла и записывает фактический Windows-результат в
`docs/maintenance/M154_CorrectionPairEvidence_Result.json`. Код и обезличенный
отчёт автоматически коммитятся и отправляются в текущую experiment, включая
FAIL. Производственный вызов нового планировщика при установке не выполняется.

Приватные каталоги нового пакета — распаковка, состояние запуска, резервные
копии, логи и временные данные проверок — размещаются под
`%USERPROFILE%\Downloads\SkynetVS_Runs\M154`. Старые каталоги предыдущих пакетов
не переносятся. Временный файл атомарной замены по-прежнему создаётся рядом
с конкретным целевым файлом и удаляется только своим writer после операции.
Это технический механизм записи, а не рабочий каталог с данными проверок.

Обычные Git hooks сохраняются. Не относящиеся к пакету изменения не добавляются
в commit. Main остаётся на завершённом предыдущем блоке; текущий блок открыт.
