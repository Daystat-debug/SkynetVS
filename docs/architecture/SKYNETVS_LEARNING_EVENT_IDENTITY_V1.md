# Идентификаторы записей истории команд — V1

## Область контракта

Первый пакет блока `learning_event_provenance` добавляет `event_id` только
новым записям `data/learning/command_history.jsonl`, создаваемым через
`LearningMemory.log_command()`. Это идентификатор сохранённого наблюдения
о распознавании и принятии команды. Существующие строки не переписываются.

Текущий путь записи:

1. `CommandProcessor.process()` получает результат понимания команды.
2. `log_command_observation()` передаёт наблюдение в `LearningMemory.log_command()`.
3. Writer добавляет строку истории с новым идентификатором.
4. Затем runtime обрабатывает действие.

Поэтому запись с `accepted=true` описывает решение о принятии команды.
Она не подтверждает успешное выполнение действия ОС или правильность метки
для обучения. Пустая команда, для которой processor выходит до этой точки,
не получает запись и идентификатор от данного механизма.

## Поле и жизненный цикл

| Свойство | Контракт |
|---|---|
| Поле | `event_id` на верхнем уровне объекта JSONL |
| Тип | Строка |
| Формат новых записей | `uuid4().hex`: UUID версии 4 в виде 32 строчных шестнадцатеричных символов без дефисов |
| Место создания | В payload `LearningMemory.log_command()` до открытия файла для добавления |
| Область назначения | Один вызов writer, создающий новую строку наблюдения |
| Повторный вызов | Генерируется новый UUID, в том числе при одинаковом тексте и времени |
| Повторное чтение/копирование сохранённой строки | Идентификатор сохраняется вместе со строкой |
| Старые строки | Отсутствие поля сохраняется; автоматического заполнения нет |
| Приём ID от вызывающего кода | В V1 отсутствует |
| Возвращаемое значение writer | Прежнее `None` |

Используется `uuid4()` из стандартной библиотеки Python; он создаёт случайный
UUID. Представление `.hex` определено документацией
[Python: uuid](https://docs.python.org/3.12/library/uuid.html).
Текст команды, её временная отметка, путь файла и номер строки не используются
для вычисления идентификатора. Новая запись получает новый случайный ID,
а не хеш потенциально изменяемого содержимого.

Случайные UUID не являются реестром с абсолютной гарантией отсутствия коллизий.
Writer не сканирует всю историю перед добавлением. Если генератор ID выдаёт
ошибку до append, новая строка не записывается; отдельный протокол восстановления
частично записанного файла этим изменением не вводится.

## Совместимость с существующими данными

Сигнатуры `log_command()` и `log_command_observation()`, возврат `None`,
метаданные команды, `accepted`, `missing_slots` и остальные значения сохраняются.
Общий `_append_jsonl()` не меняется. Остальные журналы — hard cases, resolver
candidates и action failures — сохраняют прежний формат. Общей корреляции
между этими журналами поле V1 пока не создаёт.

Формат `ts` остаётся прежним: локальное время без часового пояса с точностью
до секунд. Это сохраняет совместимость с существующей историей и текущей
сортировкой/вычитанием времени в `FeedbackAnalyzer`. Переход на UTC с часовым
поясом требует отдельного контракта для старых и новых записей.

Установка пакета меняет только разрешённые исходники, тесты и документацию.
Настоящие history/correction-memory файлы не открываются для анализа или
миграции установщиком. Новые ID появляются при последующих обычных вызовах
writer после загрузки обновлённого кода. Для уже работающего Python-процесса
потребуется обычный перезапуск приложения, чтобы он загрузил новую версию.

В существующем аудиторе отсутствие `event_id` у старой строки остаётся
информационным наблюдением. Повтор одного сохранённого ID учитывается в
`duplicate_event_id_rows`. Публичный результат содержит только счётчики,
а не тексты команд или сами идентификаторы. Аудитор продолжает проверять общий
формат старого необязательного поля; он не меняется на UUID-only валидатор.

## Что этот этап не устанавливает

Один ID относится к строке наблюдения. Повторная попытка выполнить ту же
логическую команду может вызвать writer ещё раз и получить другой ID.
Следовательно, V1 не обеспечивает идемпотентность повторов, дедупликацию
логических команд или доказательство независимости нескольких наблюдений.

Сохранённый ID не является подписью содержимого. Редактирование строки не
обнаруживается только по неизменному UUID. Копия строки с тем же ID может быть
распознана как повтор идентификатора существующим аудитором, но writer не
отвергает её и analyzer не исключает её из подсчёта автоматически.

`FeedbackAnalyzer` продолжает формировать соседние пары rejected → accepted
по прежним правилам времени и содержимого, а затем выдаёт агрегаты. Он пока
не передаёт event IDs в correction memory. Builder сохраняет существующий
механизм верхней достигнутой величины агрегата. Изменение writer не меняет
`seen_count`, checkpoints, пороги promotion, классификатор или модель.

Наличие ID не доказывает истинность разметки, правильность исторических
счётчиков или готовность к обучению. Поэтому `stable_event_identity_verified`
в существующем структурном аудите остаётся `false`, а готовность к обучению
не объявляется подтверждённой. Старые 502 строки без ID и одна запись памяти
без checkpoint не получают вымышленные идентификаторы или исправленные числа.

## Следующий этап учёта по событиям

Перед переходом памяти от агрегатов к отдельным событиям необходимо определить:

1. Какие два исходных наблюдения образуют один correction pair, как сохраняется
   его идентичность и как обрабатываются одинаковые ID с разным содержимым.
2. Где создаётся и повторно используется ID логической попытки, если потребуется
   идемпотентность повторов команды, и где проверяется конфликт содержимого.
3. Как фиксируется граница между прежним агрегатом и новыми событиями, чтобы
   одна пара не учитывалась одновременно обоими способами.
4. Как обрабатываются ротация/замена истории, пропавшие исходные события и
   несколько писателей без потери уже записанной памяти.

V1 оставляет эти решения открытыми. Уникальные ID нельзя присваивать старым
событиям на основании текста, времени или позиции в файле и затем объявлять
такое восстановление доказанным происхождением наблюдений.

## Проверка реализации

```powershell
& '.\.venv\Scripts\python.exe' -I -S -B -X utf8 tools/eval_learning_event_identity.py
```

Набор использует только собственные временные файлы и загрузку нужных
стандартнобиблиотечных модулей по точным путям. Он проверяет прежние байты
истории, совместимость payload/API/времени, bridge к writer, отдельные ID для
одинакового текста, работу существующего аудитора с смешанной историей и
копией строки, прежние результаты analyzer и границы остальных журналов.

Существующие `eval_command_learning.py` и `eval_command_processor.py` не входят
в изолированный набор этого пакета: они загружают настройки приложения.
Настоящие команды, ОС-действия, `.env`, модели и обучение не запускаются.
