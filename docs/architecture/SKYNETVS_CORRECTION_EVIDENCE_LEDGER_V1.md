# SKYNETVS_CORRECTION_EVIDENCE_LEDGER_V1

Дата: 2026-10-27. Пакет M154, сообщение №95.
База исходников: `1844fd2109f845dc545880eef770bbbf69817756`.
Блок `learning_event_provenance` открыт; перенос в `main` отложен до завершения блока.

## Назначение и граница текущего изменения

Постоянный журнал связывает идентификатор наблюдения с полным содержимым строки
и сохраняет, какие два события уже использованы как свидетельство исправления.
Он нужен, чтобы повторное чтение, перекрытие снимков или восстановление старой
истории не давало повторного начисления уже принятой пары.

Это самостоятельный компонент. Текущий writer, `FeedbackAnalyzer`,
`CorrectionMemory` и `tools/build_correction_memory.py` не подключены к нему.
Рабочие счётчики, `status`, timestamps, legacy baselines и cumulative checkpoints
не меняются этим пакетом. Реальная история не читается при установке.
Настоящая база журнала не создаётся; все вызовы нового API в проверках направлены
в изолированные временные каталоги с синтетическими данными.

В SQLite сохраняются собственные свидетельства журнала. Это ещё не обновление
`correction_memory.jsonl`, не обучение модели и не автоматическое исправление кода.

## Почему недостаточно запомнить текущие ID

База может впервые увидеть давнее событие: например, после восстановления
фрагмента уже ротированной истории. Отсутствие ID в базе означает лишь, что
журнал его не встречал. Оно не доказывает новизну наблюдения.

Явная инициализация поэтому создаёт новую случайную метку `epoch`. Чтобы будущая
пара могла дать новое свидетельство, обе исходные строки должны содержать
точно эту строку в верхнеуровневом поле `evidence_epoch`. События без метки,
с чужой меткой и все ID исходного baseline сохраняют привязку к содержимому,
но не увеличивают число принятых пар.

При будущем подключении метку должен ставить writer только при создании нового
наблюдения после согласованного отключения старого агрегатного пути. Нельзя
дописывать её старым строкам при загрузке, восстановлении или миграции. Изменение
метки при сохранённом ID меняет полный payload и обнаруживается как конфликт.

Метка периода является локальным соглашением о происхождении, а не паролем,
подписью или доказательством независимых действий пользователя. Код с доступом
к данным может её скопировать; новые вымышленные ID также не становятся
достоверными только от наличия метки.

## Вход и композиция

Публичные функции принимают явный абсолютный корень проекта:

```python
initialize_correction_evidence_ledger(repo)
sync_correction_evidence_ledger(repo)
```

История читается только из `data/learning/command_history.jsonl` через
`read_learning_history_snapshot()` версии №94. Затем используется
`plan_correction_pair_evidence()` версии №93. Никакие параметры caller не могут
подменить результат неполного чтения флагом `snapshot_complete=True`.

Reader сохраняет физические позиции: строго разобранный словарь либо `None`.
Повреждённые строки не удаляются и не создают ложного соседства. Все ограничения
reader и planner действуют дополнительно к лимитам журнала. Полнота bounded
LF-снимка с неизменными наблюдаемыми metadata не означает чистоту истории,
атомарный снимок файловой системы или наличие доверенных событий.

Журнал использует тот же внутренний канонизатор полных строк, что и замороженный
planner. Эта зависимость осознанно фиксируется read pins пакета; изменение
канонизации требует отдельного пересмотра версии и миграции, а не молчаливого
продолжения старой базы.

## Полная привязка идентификаторов

Привязка создаётся для каждого видимого непустого строкового `event_id`
независимо от отбора пригодных пар. Непригодный для обучения словарь с видимым ID тоже важен:
его содержимое не должно впоследствии незаметно измениться под тем же ID.

Ключ ID сохраняет исходное значение. Пробелы не отрезаются при сравнении,
регистр не меняется. Проверка `strip()` используется только для исключения
пустого ID. ASCII JSON-представление ключа позволяет сохранить непрозрачные
Unicode/NUL/surrogate значения без передачи недопустимого UTF-8 в SQLite.

В базе хранится полный канонический payload, а не только хеш или поля готовой
пары. Порядок ключей и JSON-экранирование не создают различий; неизвестные поля,
вложенные значения, метка периода и различия JSON-типов участвуют в сравнении.
Точное правило сериализации наследуется от planner.

Разное содержимое под одним ID в текущем снимке или относительно сохранённой
привязки отклоняет всю новую обработку. Нельзя успеть записать несколько
правильных пар и затем частично отказаться от конфликтующей строки.
Если видимый ID нельзя связать с сравнимым полным payload, обработка также
отклоняется. Из неразобранных строк скрытые ID не восстанавливаются.

Повторённый внутри одного снимка ID помещается в постоянный карантин, даже
если его копии идентичны. Удаление лишней копии из следующего снимка не
восстанавливает пригодность этого ID. Обычное повторное присутствие одной
строки в разных снимках является replay, а не само по себе карантином.

Поздний карантин или конфликт не переписывает исторические принятые пары.
Конфликт даёт отказ транзакции, поэтому отдельная постоянная запись о таком
конфликте в этой же транзакции не создаётся. Это различие с карантином явное.

## Baseline и приём новых пар

Первая инициализация регистрирует все видимые ID текущей истории как baseline
и создаёт ноль принятых пар. Старые агрегаты не пересчитываются и не исправляются
догадкой. Наличие подходящих соседних строк в baseline не даёт начисления.

Поздняя пара проходит правило frozen planner и дополнительные проверки журнала:

1. Оба ID принадлежат текущей метке `evidence_epoch`.
2. Ни один ID не находится в baseline или постоянном карантине.
3. Полные payload совпадают с сохранёнными привязками.
4. Ни один endpoint не использован ранее другой принятой парой.

Оба endpoint, ошибочный и исправленный, используются глобально не более одного
раза. Ограничение не сводится к уникальности кортежа пары: новое соседство не
позволяет повторно использовать уже учтённое исправление с другим контекстом.
Повтор ранее принятой пары не увеличивает счётчик. Количество принятых пар
восстанавливается из постоянной базы после повторного открытия.

Ротация, усечение или более старый полный снимок не очищают привязки, карантин
и использованные endpoints. Невидимый сейчас ID не удаляется из журнала.
Восстановленные старые строки без текущей метки не получают новых начислений.
Если ресурсный предел достигнут, модуль отказывает; автоматической очистки,
сброса baseline или выдачи нового периода не происходит.

## Транзакции и отказ

База находится в `data/learning/correction_evidence.sqlite3`. Инициализация
создаёт этот конечный файл эксклюзивно, без перезаписи существующего файла.
Схема, метка и baseline записываются транзакцией SQLite. Само создание файла
происходит перед этой транзакцией: сбой может оставить пустой или неполный
файл. Он сохраняется для разбора и не заменяется автоматически повторным
вызовом. `sync` отсутствующую базу не создаёт.

Для изменения применяется `BEGIN IMMEDIATE`; база должна использовать
`journal_mode=DELETE`. Задаются `synchronous=FULL` и включённые foreign keys. Повторный writer получает
контролируемый отказ при занятой базе. Привязки, карантин, пары и использованные
endpoints записываются в одной транзакции. Все SQL-значения передаются
параметрами. Соединение закрывается после каждого вызова.

Ошибка до попытки COMMIT вызывает rollback. Если результат COMMIT неизвестен
или rollback сам завершился ошибкой, API не выдаёт свежие подтверждённые
начисления и не обещает отсутствие изменений. Следующая обработка должна
заново открыть базу и свериться с фактически сохранёнными записями.

SQLite поддерживает только одного одновременного writer; `BEGIN IMMEDIATE`
получает write transaction заранее. COMMIT может завершиться ошибкой занятости,
сохранив активную транзакцию. Эти правила описаны в
[SQLite Transaction](https://www.sqlite.org/lang_transaction.html).
При открытии базы SQLite может самостоятельно восстановить hot journal, что
меняет файлы даже до основного решения приложения; журнал нельзя удалять
вручную в качестве «очистки». См.
[File Locking and Concurrency](https://www.sqlite.org/lockingv3.html).

Гарантия SQLite относится к её транзакции при соответствующих свойствах ОС
и файловой системы. Она не делает атомарными отдельно прочитанную JSONL-историю
и отдельно записываемую `correction_memory.jsonl`. См.
[Atomic Commit in SQLite](https://www.sqlite.org/atomiccommit.html).

## Схема постоянного состояния и результата

`STATE_KIND` равен `SKYNETVS_CORRECTION_EVIDENCE_LEDGER_V1`, версия схемы — 1.
Версия правила пары совпадает с `adjacent_unique_observation_v1` frozen planner.
Проверяются application ID, версия и точный набор SQL-объектов схемы.
Несовместимая или неподдерживаемая база не пересоздаётся.

| Таблица | Содержание и связь |
|---|---|
| `meta` | Одна запись: вид состояния, версия, правило пары, метка периода, число физических строк baseline, имя прежнего источника `feedback_analyzer_v2` |
| `events` | ASCII JSON-ключ ID, полный канонический payload BLOB, флаги baseline и карантина |
| `pairs` | ID обоих endpoints и приватное сериализованное свидетельство planner |
| `endpoints` | Уникальный использованный ID, ссылка на пару и роль `failed`/`corrected` |

Каждая принятая пара должна иметь ровно две соответствующие записи endpoints.
Foreign keys и дополнительные проверки связей исключают осиротевшие ссылки
и несогласованные роли. Старое свидетельство может ссылаться на ID, который
позже попал в карантин: это допустимая история, а не повод удалить начисление.

Проверка существующей базы структурная: схема, типы/флаги, объёмы, связи и
согласованность endpoints. Для ID текущего снимка сравниваются точные payload.
Она не является проверкой подлинности всей прежней истории и не доказывает,
что внешняя программа не изменила содержимое базы. Отдельной подписанной
аттестации или полной повторной проверки каждого старого evidence BLOB нет.

Результат публичных функций API имеет вид
`SKYNETVS_CORRECTION_EVIDENCE_LEDGER_RESULT_V1` и следующие поля:

| Поле | Значение |
|---|---|
| `operation` | `INITIALIZE` или `SYNC` |
| `status` | `INITIALIZED`, `APPLIED`, `UNCHANGED` либо `REFUSED` |
| `reason`, `input_reason` | Фиксированный код отказа; причина reader/planner сохраняется отдельно; сырые exception и приватные пути не возвращаются |
| `epoch` | Метка текущего периода при успешном результате; при отказе очищается |
| `transaction_committed` | `True` после успешного COMMIT; `False`, когда новое начисление не зафиксировано этой операцией; `None` при неизвестном исходе транзакции |
| `ledger_file_created` | Создан ли конечный файл текущей попыткой инициализации; не равнозначно успешному созданию схемы |
| `stats` | Счётчики текущей операции и общие числа базы после успешной операции; при отказе `None` |
| `scope`, `limits` | Явные границы поведения и фиксированные ресурсные ограничения |

`UNCHANGED` означает отсутствие новых привязок, карантина и пар. Новая
непригодная для начисления строка всё равно может добавить привязку и дать
`APPLIED` при `new_pairs=0`. Статус нельзя подменять числом новых пар.

В `stats` отдельно отражаются строки и видимые ID, новые привязки/карантин/пары,
replay и причины пропуска пар: baseline, метка периода, карантин, занятые
endpoints. Общие числа относятся к сохранённому журналу, а не к readiness
модели или значениям `seen_count` в correction memory.

## Ресурсные ограничения

| Ресурс | Предел |
|---|---:|
| Постоянные привязки событий | 1 000 000 |
| Сумма канонических payload событий | 256 MiB |
| Принятые пары | 500 000 |
| Сумма сериализованных evidence пар | 128 MiB |
| Основной файл SQLite | 512 MiB |

Лимиты строк/глубины/объёма reader и planner сохраняются. Рост постоянного
состояния проверяется до вставки новых записей; `max_page_count` дополнительно
ограничивает файл базы. Счётчики размеров вычисляются SQL-агрегатами без загрузки
всех прежних payload в Python. Число объектов схемы и строк meta ограничивается
до materialization их результата.

Эти пределы не являются точной границей RAM, суммарного места с journal или
времени работы SQLite. Индексы, страницы, служебный журнал и парсер базы имеют
свои расходы. При отказе нет автоматической ротации или «освобождения места»
удалением старых привязок.

## Приватность и Git

База содержит полные приватные тексты, ID и вложенные данные строк. Она не
является обезличенным публичным отчётом. В `.gitignore` добавлены только точные
пути базы и её SQLite sidecars `-journal`, `-wal`, `-shm`. Остальные правила
и весь прежний текст `.gitignore` сохранены.

Установщик создаёт публичный `M154_CorrectionEvidenceLedger_Result.json`
с версиями, контрольными суммами и обезличенными результатами synthetic suites.
Он не открывает пользовательскую базу, историю, `.env`, модели или обучение.
Названные тесты создают собственные фикстуры; обнаружение и запуск всех тестов
проекта не используется.

## Что требуется до подключения к рабочему обучению

Следующий законченный этап должен определить единый переход от прежнего
агрегатного учёта к событийному: остановить старое начисление для этого источника,
сохранить реальные counts/status/checkpoints как legacy baseline и согласованно
начать маркировать только новые наблюдения. Уже накопленные private данные
проверяются отдельно, когда это потребуется для такого перехода.

Проекция журнала в correction memory должна быть восстанавливаемой: повтор
после сбоя не должен повторно прибавить delta. Передавать event delta в
`sync_cumulative_candidates()` нельзя — этот метод ожидает cumulative totals.
SQLite и JSONL не образуют общую транзакцию; для проекции нужен явный checkpoint
и проверяемый алгоритм повторного применения либо единый авторитетный storage.

До выполнения этого этапа runtime integration и aggregate-to-event cutover
остаются выключенными. Synthetic PASS подтверждает реализованные сценарии,
но не чистоту реальной истории, readiness обучения, переобучение NLU или
независимость накопленных наблюдений.


## Именованные проверки и findings подготовки

Новый `tools/eval_correction_evidence_ledger.py` содержит 44 именованных
синтетических теста. Вместе с семью сохранёнными наборами (180 проверок)
состав source gate — 224 проверки. Evaluator загружает только три standalone
модуля в изолированное synthetic package; app entry points не импортируются.
Проверяются реальные временные SQLite-базы, повторное открытие, занятый writer,
ошибки до и после COMMIT, rollback, конфликт payload, оба endpoints, ротация,
карантин, метка периода и сохранение посторонних фикстур.

До первого запуска исправлены три конкретных недостатка подготовительного
модуля: SQL LIKE с underscore мог неверно исключить чужой schema-object;
чтение schema/meta не было ограничено числом возвращаемых строк; ошибка rollback
в ветке UNCHANGED могла не получить явный неизвестный исход. Используются
точный GLOB-prefix, LIMIT 5/2 и отдельное отслеживание попытки rollback.
Также завершена синтетическая фикстура перестановки ролей endpoints с прежним
числом строк, чтобы проверять сами связи, а не только сумму.

Исходные версии, findings и patches сохранены в handoff. Эти исправления
обнаружены статическим review до первого тестового запуска; они не выдаются
за упавшие пользовательские тесты. Результат Windows-применения этого пакета
проверяется отдельно по его будущему Result в Git.


После первого успешного standalone evaluator (44 проверки) первый общий
source gate обнаружил реальное падение `package_boundaries`: case
`LEARNING PACKAGE DEPENDS ONLY ON CORE AND ITSELF` отклонил относительные
импорты нового модуля. Из 32 cases этого набора провален один; остальные
семь suites тот запуск ещё не выполнял.

Исправление использует канонические абсолютные `modules.learning` импорты.
Evaluator создаёт изолированные namespace-объекты под этими именами и
восстанавливает прежние `sys.modules`, не исполняя реальные package init.
Frozen boundary guard не ослаблен и не изменён. Этот случай показывает,
почему проверка компонента дополняется общей проверкой архитектуры проекта.
Полные логи неудачного gate, исходные версии и исправление сохраняются.
