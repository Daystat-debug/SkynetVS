# SkynetVS Cognitive Core V2

**Статус на 20.11.2026:** архитектурная основа принята владельцем; эта редакция вынесена на согласование. Исходная ревизия: `e67c9ad013f4fa451046b9c461e8f055db8beaaf`. Это спецификация целевого поведения. M289 остаётся отдельным пилотом.

## Первый сценарий и граница процессов

В режиме `explain_code` пользователь задаёт текстовый вопрос по разрешённому репозиторию. Хост выбирает снимок и фрагменты, модель предлагает ответ, хост проверяет основания для публикации. Fast Path сохраняет существующее поведение при отключённом Core. Диктовка, подтверждения и управление Windows остаются в голосовом runtime.

Первый клиент — Developer Tasks UI. Внутри его процесса точка сборки передаёт координатору три операции: получить доказательства, вызвать provider и проверить отмену. Хост также проверяет ссылки по выданным доказательствам. Тест запускает тот же координатор без Tk, Git и весов. Другой клиент может предоставить другой разрешённый источник. Core не импортирует UI, Git reader, Qwen, STT/TTS, Router или Actions.

Git-адаптер повторно использует [существующие чтение снимка и ранжирование](../../modules/developer_task_ui/app/context_search.py). Текст, координаты и blob берутся из одного захвата; публичная квитанция без исходника и отображаемый текст окна для этого непригодны. Алгоритм поиска имеет одного владельца. Общий код Core ведётся в одном каноническом месте; при штатной интеграции проверяемые копии поставляются из одних и тех же байтов. Отдельный сервис, IPC и перенос retrieval до появления второго потребителя не требуются.

Сохраняются проверки [закреплённого манифеста родителем](../../modules/developer_task_ui_launcher.py) и [состава комплекта дочерним процессом](../../modules/developer_task_ui/launch.py). Изменение поставки требует проверки состава, хешей и запуска без импорта исходников из рабочей копии. Флаги Python `-I -S -B` ограничивают окружение импортов и запись bytecode; они не изолируют процесс средствами ОС и не отзывают права пользователя. Входные фрагменты и вывод модели — данные. API сценария не принимает shell-команды, произвольные пути, patch, разрешения на запись или обучение.

## Три контракта

| Данные | Минимальная форма | Владелец и инвариант |
|---|---|---|
| `TaskRequest` | `task_id, kind, question, source_id` | Хост создаёт ID и сопоставляет логический источник с разрешённой областью; интерфейс передаёт вопрос. Первый вид — `explain_code`. Дедлайн и бюджеты задаёт хост. |
| `EvidenceSet` | `task_id, source_id, snapshot_id, coverage, gaps[], items[]`; элемент: `ref_id, text, locator` | Адаптер источника. Для Git снимок — commit, координаты — путь, blob OID и включительные номера строк от 1. ID фрагмента уникален в наборе. `complete/partial` характеризует обследование разрешённой области, а не достаточность ответа. В gaps указываются пропуски и причины. На отправке provider хост отдельно фиксирует, какие фрагменты действительно вместились. |
| `AnswerProposal` | `status, claims[], reason?`; утверждение: `text, anchors[]`, ссылка: `ref_id, lines` | Provider предлагает `answer` с утверждениями и ссылками либо `insufficient` с причиной и пустыми claims. Хост привязывает предложение к активной задаче и допускает ссылки только на фактически переданные строки снимка. Provider не назначает итоговое состояние и не получает полномочий. |

**Подлинная цитата подтверждает содержание конкретных строк. Она не доказывает, что вывод из них верен, что перечислены все требуемые факты или что описанное произошло на работающем ПК.** Статус буквальной проверки, решение о показе и смысловая оценка записываются отдельно.

## Владение состоянием

Координатор держит одну запись задачи в памяти: запрос, снимок, текущий шаг, дедлайн и итог. Переходы: `accepted → running → answered | insufficient | failed | cancelled`; отмена допускается и из `accepted`. Ход работы: retrieval → generation → verification. При пустом пригодном контексте вызов модели пропускается.

- `answered`: хост принял предложение к показу, ссылки прошли проверку. Смысловое качество может ещё ожидать оценки.
- `insufficient`: различать отсутствие совпадений в области, частичный поиск, запрос вне области и необходимость живого наблюдения. Код причины сохраняется.
- `failed`: ошибка чтения, смена обязательного снимка, недоступность provider, дедлайн либо отклонение формата/ссылки. Записать шаг и причину; сырой ответ пользователю не публиковать.
- `cancelled`: пользователь или закрывающийся интерфейс отменяет свой task_id. Проверять отмену между шагами и атомарно перед выдачей итогового результата. Первое терминальное состояние окончательно. По возможности прервать работу; запоздалый ответ не показывать. Повтор — новая задача.

Состояние голосового окна, журнал наблюдений, подтверждённая память и обучающая выборка имеют разных владельцев. Ответ модели автоматически никуда не продвигается. Просьба изменить код требует отдельного запроса Developer Tasks и его действующих проверок. Будущие внешние эффекты используют существующие контракты полномочий и исполнения.

## Правила для разработчиков и агентов

1. Новый интерфейс поставляет запрос, новый источник — доказательства, новая модель — предложение. Проверять подмену каждого компонента без загрузки остальных. Qwen — сменный локальный provider. Собственную модель сравнивать на той же роли и том же закрытом наборе; включение и откат оформлять отдельно.
2. Новые файлы именовать по ответственности. Идентификаторы M289 и подобных опытов оставлять в экспериментальных материалах. Не импортировать tooling и личные каталоги ModelLab из production. Для переноса существующих модулей действуют Inventory V2 и правила Phase 2.
3. Проверять контракт, изолированную поставку и смысловую полезность раздельно. Негативные сценарии: отсутствующий источник, подменённая ссылка, недоступный provider и отмена во время генерации. Сохранять существующие точки входа Fast Path, Developer Tasks и pipeline.
