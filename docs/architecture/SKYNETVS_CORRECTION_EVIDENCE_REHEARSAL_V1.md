# Репетиция обработки фактических событий на отдельной приватной копии

## Задача и граница результата

После подтверждённого включения ACTIVE необходимо проверить совместимость
реальной истории, текущего ledger и старой correction memory. Следующий шаг
выполняет две обработки одного зафиксированного набора данных в отдельной
приватной рабочей копии. Рабочая база проекта не открывается через SQLite;
реальная память не получает начислений от этой операции.

Операция `rehearse_correction_evidence(repo, run_directory)` возвращает
закрытый обезличенный результат. Его публикация допустима только после
`validate_public_result(value)`. Это проверка захваченных реальных данных,
а не обучение модели, автоматическое одобрение кандидатов или перенос в main.

Входной control должен быть ACTIVE. Операция не вызывает активацию, не
создаёт новый период, не исправляет историю и не выбирает legacy builder.
Наличие двух успешных команд не означает наличие пары исправления.

## Приватные каталоги и сохранность

Caller выбирает новый абсолютный локальный `run_directory` с уже существующим
безопасным родителем вне дерева проекта. Нельзя использовать сам проект,
вложенный в него каталог, его предка или существующий каталог попытки.
Проверки путей отвергают symlink/reparse и файлы с несколькими hardlink.
Предыдущие попытки, включая неполные, сохраняются. Автоматического удаления,
сброса, восстановления поверх пользовательского проекта или повторного
использования каталога нет.

Внутри каждой попытки хранятся:

| Относительное имя | Назначение |
| --- | --- |
| `before/data/learning/` | Проверенная исходная копия семи файлов; никогда не передаётся SQLite или builder |
| `backup_ready.json` | Приватные размеры, хеши и metadata исходного захвата |
| `working/data/learning/` | Вторая, отдельно проверенная копия; SQLite и builder работают только здесь |
| `first_build_intent.json`, `second_build_intent.json` | Сохранённое намерение выполнить соответствующий проход только в working |
| `first_build_outcome.json`, `second_build_outcome.json` | Частный результат вызова, если он вернулся |
| `outcome.json` | Закрытый итог, если его удалось записать |

Семь файлов совпадают с набором контролируемой активации: command history,
correction memory, runtime control, SQLite ledger и три его sidecar.
Отсутствие файла сохраняется как отсутствие. Пределы также переиспользуются:
история 32 MiB, память 64 MiB, control 4096 байт, база/journal/WAL по 512 MiB,
SHM 64 MiB, суммарно 768 MiB. Это не копирование всего проекта, окружения
или моделей.

Одна общая learning lock охватывает raw capture и повторную проверку байтов
всех семи живых файлов. После этой проверки lock отпускается. Поле
`source_preserved_at_capture=true` означает подтверждённую сохранность в
этой точке. Оно не обещает, что другой процесс не изменит проект позднее.
Сама операция после отпускания lock использует только зафиксированные копии.

Lock-файл может быть создан и остаётся на месте; его не копируют вторым
дескриптором во время Windows byte-range lock. Старые процессы и внешние
редакторы не обязаны соблюдать lock, поэтому caller использует установленную
проверку процессов. Получение списка процессов — наблюдение в момент времени,
а не общая блокировка всех программ.

Копирование raw SQLite-файлов не объявляется универсальной гарантией горячего
backup. После захвата все SQLite-проверки, включая возможное восстановление
журнала, выполняются только в working. Исходные before-байты сравниваются
ещё раз после успешных двух проходов. Имя `before` само по себе не делает
каталог защищённым от произвольного внешнего редактора; операция лишь
сохраняет его и проверяет неизменность.

## Допустимость снимка и действительное новое наблюдение

История читается полным strict reader и проверяется существующим planner.
Неполное чтение, плохие строки, непереносимые значения и повторяющиеся ID
дают отказ. Legacy-строки без ID сохраняют место и не дополняются задним числом.
Память проверяется строгим reader активации, включая нормализованные ключи,
confidence, старые checkpoints и переносимость JSON.

`current_epoch_rows` считает строки, уже несущие точную текущую epoch.
Сама epoch, event IDs, тексты, slots и private hashes наружу не возвращаются.
Наличие таких строк подтверждает только маркировку захваченных наблюдений.
Оно не доказывает независимость действий пользователя, успешное выполнение
команды, правильность intent или готовность данных для обучения.

Пара допускается прежними правилами: соседняя отклонённая команда и затем
принятая с другим текстом, интервал от 0 до 60 секунд, confidence принятой
не ниже 0.40, без missing slots. Оба endpoint должны иметь уникальные ID,
точную active epoch и не быть baseline, quarantined или уже использованными.
Это эвристика происхождения, а не семантическое доказательство исправления.

Чтобы проверить живую запись, пользователь запускает обновлённое приложение
после активации и выполняет обычные безопасные команды. Если возникает
настоящее непонимание, можно быстро переформулировать ту же задачу. Нельзя
дописывать синтетические пары в настоящую историю или специально создавать
фиктивные ошибки ради положительного счётчика. Если подходящих новых пар
пока нет, это ограниченное покрытие, а не техническая ошибка.

## Первый проход в working

Сначала читаются control и полные сохранённые totals из working ledger.
Проверяется epoch и отсутствие регрессии checkpoints. Перед каждым вызовом
builder control повторно должен быть ACTIVE с той же epoch.

Первый `build_learning_corrections(working)` использует неизменённый runtime:
проверяет ledger, синхронизирует текущую историю и проецирует полные totals.
Результат builder отражает проекцию. `UNCHANGED` не означает, что sync не
добавил bindings или quarantine без новой пары.

Проверка после первого прохода сравнивает накопительные счётчики и
checkpoints с реальными данными памяти. Старые seen_count увеличиваются
только на разность event totals; старые status, created_ts,
cumulative_evidence, неизвестные поля и порядок существующих строк сохраняются.
Для неизменившихся строк сравниваются все JSON-значения. Сравнение использует
переносимый канонический JSON и различает `true`, `1`, `1.0`, `0.0`, `-0.0`;
обычное Python-сравнение для этого недостаточно.

Для изменённой строки проверяются ожидаемые confidence, объединённые slots,
sources и event checkpoint. Last-seen отражает время проекции в working.
Новая строка имеет status `candidate`; автоматического approval нет.
History и control в working должны сохранить исходные байты и metadata.

`new_pairs_first` — изменение числа принятых пар в ledger. Отдельно
`new_evidence_first` — фактическая разность, перенесённая в память. Второе
может быть больше первого: прежний прерванный build мог сохранить пару в
живом ledger, но ещё не проецировать её в память. Копия должна восстановить
такой недостающий результат, не называя его новым приёмом пары.

## Второй проход и проверка повторного начисления

В working не добавляются новые строки. Выполняется ровно второй builder.
Успешная проверка требует:

- mode EVENT, status UNCHANGED, `new_evidence=0`, `written=false`;
- полного совпадения накопительных totals, включая кандидатов;
- совпадения всего JSONL памяти: присутствия/отсутствия, байтов и metadata;
- совпадения SQLite-базы и sidecar по присутствию, байтам и metadata;
- сохранности history и control;
- сохранности исходного before capture.

Проверка всей базы дополнительно охватывает сохранённые bindings,
quarantine и endpoints, а не только количество accepted pairs. Хеши для
сравнения остаются приватными. Проверка не выполняет третий build и не
пытается проверить произвольные будущие изменения данных.

## Закрытый публичный результат

`status` равен `VERIFIED` или `REFUSED`. Coverage независимо описывает,
что действительно удалось проверить:

| Coverage | Значение |
| --- | --- |
| `NEW_PAIRS` | В working приняты новые пары и подтверждён повтор без второго начисления |
| `PENDING_PROJECTION_ONLY` | Новых пар не принято, но в working внесена ранее недостающая проекция, повтор не начисляет её заново |
| `NO_NEW_PAIRS` | Новых пар и недостающей проекции нет; подтверждена стабильная повторная обработка текущего набора |
| `NOT_ASSESSED` | Полная проверка не завершилась |

`NO_NEW_PAIRS` с `current_epoch_rows=0` не проверяет маркировку нового живого
наблюдения. Такой результат нельзя выдавать за положительное начисление.

Поля `first_build_status` и `second_build_status` различают NOT_RUN,
ATTEMPTED, APPLIED, UNCHANGED, REFUSED и UNKNOWN. Если runtime вернул REFUSED,
ledger уже мог принять изменения, а память могла иметь неизвестный исход
записи. Это не означает, что working остался прежним. Если вызов оборвался
исключением, статус UNKNOWN сохраняет эту неопределённость.

Все reason/stage/coverage принадлежат фиксированным спискам; количества
ограничены и отделены от boolean; неподтверждённые измерения равны `null`.
В публичный результат не проходят paths, timestamps, raw exceptions,
содержимое файлов, ID, epoch, ключи кандидатов или хеши приватных данных.
Ошибка записи окончательного outcome не стирает подтверждённые исходы двух
проходов и не превращает выполненный build в NOT_RUN.

## Доставка и проверки

Launcher проверяет исходники и process gate, применяет четыре разрешённых
payload, запускает именованные `package_boundaries` и
`correction_evidence_rehearsal`, затем выполняет отдельный private child.
Тот загружает только восемь явно закреплённых leaf modules без package
initializers, приложения, моделей и пользовательских библиотек.

Рабочие каталоги обслуживания находятся под
`%USERPROFILE%\Downloads\SkynetVS_Runs\M154`. По завершённому результату
обезличенный PASS либо FAIL автоматически коммитится и отправляется в
experiment. Предыдущие 348 synthetic checks неизменённых компонентов
явно переиспользуются с проверкой исходных bytes и evidence; они не
обозначаются как заново выполненные в этом пакете.

Новый evaluator проверяет только границу capture/copy/replay/report на
собственных временных fixtures. Native Windows и реальные пользовательские
данные подтверждаются последующим Result, а не Linux-подготовкой.
Блок `learning_event_provenance` остаётся OPEN до выполнения его критериев;
одна репетиция не доказывает работу live projection и не переносит блок в main.
