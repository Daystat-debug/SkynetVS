# SkynetVS: контролируемое включение журнала исправлений, V1

## Назначение и основание

Пакет №97 переводит существующий проект с прежнего накопительного подсчёта
на уже установленный event runtime. Основание — опубликованный коммит
`47a824867b0c1d6b3297a971d1828c67a718e238`: пакет №96, 316 именованных
синтетических проверок в Windows/Python 3.12.10, 17 payload-файлов и Result.
Фактическая активация в №96 не выполнялась.

Это обслуживание приватного состояния, а не обучение модели. Первое включение
сохраняет существующие `command_history.jsonl` и `correction_memory.jsonl`
побайтно. Старые `seen_count`, статусы, метаданные и cumulative checkpoints
не пересчитываются и не исправляются догадкой. Существующие события образуют
исходную границу с нулём вновь принятых пар. Только последующие наблюдения,
которые writer записывает с активным epoch, могут давать новые event evidence.

## Граница операции

Новый модуль `modules/learning/correction_evidence_activation.py` предоставляет
`activate_correction_evidence_safely(repo, backup_directory)` и валидатор его
закрытого публичного результата. Это явная операция обслуживания. Обычный
запуск приложения сам её не вызывает.

Для непрерывной блокировки прежнее тело активации вынесено в приватный
`correction_evidence_runtime._activate_learning_evidence_locked`. Публичный
`activate_learning_evidence` сохраняет прежнюю сигнатуру, получение блокировки
и обработку отказов. Приватную функцию допустимо вызывать только владельцу
той же `learning_evidence_lock`; новый модуль соблюдает это условие.

В пределах одного захвата блокировки выполняются проверка фиксированных
путей, копирование исходных файлов, проверка копий, запись подтверждённого
manifest резервной копии, активация и проверка сохранности истории/памяти.
Подтверждённый backup предшествует первой попытке изменения runtime state.
Блокировка применяется к участвующим writer/builder/activation; она не
управляет старым процессом, который уже загрузил код без этой блокировки.

## Подготовка пользователя и Windows launcher

Перед запуском следует закрыть SkynetVS и фоновые задачи проекта, включая
старые builders. Launcher не завершает процессы принудительно. Он проверяет
процессы перед изменением source и повторно перед приватной активацией.
Остановка на этой проверке сохраняет рабочее состояние пакета для повторного
запуска после закрытия мешающего процесса. Проверка процессов — наблюдение
в определённый момент, а не запрет запускать другие программы позднее.

Source, тесты и документы проверяются по зафиксированным хешам. Приватная
активация разрешена лишь после успешных именованных синтетических suites;
FAIL исходных тестов приводит к отчёту без активации. Приватный этап запускается
в отдельном изолированном Python child с фиксированным набором импортов.
Неожиданный вывод остаётся в локальном журнале, а публичный JSON принимает
только закрытую схему и разрешённые коды.

Состояния обслуживания, резервные копии, логи и synthetic temp находятся под
`%USERPROFILE%\Downloads\SkynetVS_Runs\M154`. В пользовательском проекте
сохраняются ветка, индекс чужих изменений, stash, `.env`, модели, окружение и
посторонние файлы. Пакет не выполняет reset, clean или повторное клонирование.
Атомарная замена собственного source/control файла использует короткий
временный файл рядом с ним. Весь набор source-файлов не является общей
файловой транзакцией.

## Фиксированный состав приватной резервной копии

Для каждой попытки выделяется новый каталог вне репозитория. Существующий
каталог не очищается и не переиспользуется как пустой. Копируются только:

1. `data/learning/command_history.jsonl`;
2. `data/learning/correction_memory.jsonl`;
3. `data/learning/correction_evidence_runtime.json`;
4. `data/learning/correction_evidence.sqlite3`;
5. `data/learning/correction_evidence.sqlite3-journal`;
6. `data/learning/correction_evidence.sqlite3-wal`;
7. `data/learning/correction_evidence.sqlite3-shm`.

Отсутствие файла отражается в приватном manifest; оно не заменяется пустым
файлом в проекте. Копии и manifest проверяются и синхронизируются на диск до
cutover. Размеры ограничены. Символьные ссылки, reparse points, hard links и
необычные типы файлов отклоняются. Manifest, частичная копия и частичное новое
состояние при сбое сохраняются для разбора; автоматического восстановления
поверх живых данных нет.

Постоянный однобайтный `correction_evidence_runtime.lock` не копируется через
второй дескриптор во время захвата: Windows блокирует эту область. При
отсутствии lock его создание является отдельным объявленным эффектом ещё
до cutover. Закрытие процесса освобождает блокировку средствами ОС; файл
остаётся и не служит признаком включения.

Вызовы SQLite могут выполнить recovery, поэтому исходные DB и sidecars
копируются до первого SQLite-вызова. Это побайтная копия наблюдаемого набора
файлов под блокировкой участвующих процессов. Она не является гарантией
согласованной резервной копии базы, которую одновременно меняет сторонний
процесс, не использующий протокол. Старые процессы требуется закрыть.

## Допустимость данных и первый baseline

Полнота чтения истории сама по себе не доказывает допустимость её строк.
Поэтому дополнительно проверяются JSON, типы и значения полей, переносимость
Unicode, структура событий, идентификаторы и ресурсные ограничения. Старые
строки без event ID допустимы как legacy и не получают ID задним числом.
Некорректные строки и неоднозначные повторные ID не удаляются и не чинятся
автоматически: операция прекращается с фиксированным кодом.

Пустой файл истории допустим и даёт пустой baseline; отсутствие самой истории
вызывает отказ. Пустые физические строки внутри истории тоже отклоняются,
а не отбрасываются при подсчёте позиций. Отсутствие correction memory допустимо:
операция не создаёт её. Для существующих строк памяти ключ должен совпадать
с нормализованными failed text, corrected text и intent, confidence должен
находиться в диапазоне [0, 1]. Неизвестные поля и строковые статусы сохраняются.

Память проверяется строгим reader с дополнительными ограничениями и
проверкой JSON. При первом переходе недопустимы оставшиеся event checkpoints
без управляющего состояния. При повторном вызове для ACTIVE checkpoint
сопоставляется с текущим epoch и полными totals; отсутствие или регресс
сохранённого положительного evidence не трактуется как повод обнулить память.

Перед cutover проверяется, что живые входы соответствуют сохранённым копиям.
После него проверяется сохранность истории и памяти. Чужое параллельное
изменение приводит к отказу/неподтверждённому исходу, а не к автоматическому
откату через запись старой копии поверх текущего файла.

## Повтор после прерывания

LEGACY проходит через PREPARING и создание ledger к ACTIVE. PREPARING с
допустимым нулевым ledger можно продолжить. ACTIVE с согласованной базой
возвращает подтверждённый повтор без нового epoch и без начислений.
Повреждённый control, orphan ledger, несовпавший epoch или неоднозначное
частичное состояние сохраняются и требуют отдельного разбора.

После durable intent исключение или потеря ответа дочернего процесса не
доказывают, что приватных изменений не было. Отчёт должен явно сохранять
неопределённость. Повтор сверяет фактическое состояние; он не удаляет базу,
не меняет историю, не выбирает legacy по умолчанию и не запускает projection.

История/память и SQLite не объединены общей транзакцией. Этот пакет не
выполняет builder, sync новых пар, projection, promotion, model load, training
или полный pipeline. Последующая обычная обработка использует runtime №96.
Её подтверждение на реальных новых событиях остаётся отдельным этапом.

## Публичный отчёт и Git

Публичный `docs/maintenance/M154_CorrectionEvidenceActivation_Result.json`
содержит результаты source suites и отдельный результат реальной активации.
Коды, булевы флаги и агрегированные количества проходят закрытый валидатор.
Тексты команд, slots, event ID, epoch, абсолютные пользовательские пути,
частные хеши и содержимое backup не публикуются.

Перед приватным этапом launcher проверяет, что фиксированные runtime-файлы
не отслеживаются Git и находятся под ignore. Он коммитит только пять
payload-файлов и Result. Завершённый FAIL также коммитится и отправляется
обычным push, как ранее согласовано; частные файлы в commit не включаются.
Ошибка push сохраняет готовый commit и состояние для повторной отправки.
Сбой process preflight до приватной попытки сохраняется как возобновляемая
остановка, а не как завершённый переход.

Текущая рабочая ветка:

Блок `learning_event_provenance` остаётся OPEN; main promotion:

обучена лучше, а локальные ID и epoch не доказывают независимость или
