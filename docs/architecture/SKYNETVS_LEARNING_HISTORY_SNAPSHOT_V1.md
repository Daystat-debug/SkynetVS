# Чтение истории с сохранением физических позиций — V1

Блок сопровождения: `learning_event_provenance`, M154, сообщение №94.
Исходная база: `4f7735e0e50fb8b5d6ce64b992b47dfe3b3a6e1c`.
Статус: отдельный компонент и синтетические проверки; подключение к рабочему
анализатору, накоплению памяти и обучению в этот пакет не входит.

## Назначение

Планировщик `plan_correction_pair_evidence()` рассматривает соседние позиции
переданного списка. Поэтому читатель не должен удалять повреждённую или пустую
строку: после удаления возникает соседство, которого не было в исходном файле.
Прежний `FeedbackAnalyzer._read_jsonl()` пропускает такие строки, а подбор пар
затем сортирует оставшиеся записи. Его поведение в этом пакете сохранено;
новый читатель подготовлен для будущего отдельного пути событийного учёта.

Модуль `modules/learning/learning_history_snapshot.py` читает только
`data/learning/command_history.jsonl` внутри явно заданного локального корня.
Он сохраняет физический порядок и возвращает одну позицию на каждую строку,
завершённую LF. Содержимое возвращаемого снимка приватное: это исходные объекты
с текстами, ID и slots, а не публичный агрегатный отчёт.

## API и результат

```python
read_learning_history_snapshot(repo)
```

`repo` обязателен. Поддерживаются точный встроенный `str` и конкретный `Path`
текущей платформы. Корень должен быть абсолютным; относительные пути, `..`, NUL,
UNC и Windows device namespace не принимаются. Произвольные объекты с
`__fspath__` и подклассы не вызываются ради преобразования аргумента.

В модуле нет CLI, поиска корня по текущему каталогу, чтения настроек или
неявного запуска планировщика. Импорты ограничены стандартной библиотекой.

| Поле | При полном чтении | При отказе |
|---|---|---|
| `kind` | `SKYNETVS_LEARNING_HISTORY_SNAPSHOT_V1` | То же значение |
| `status` | `COMPLETE` | `REFUSED` |
| `reason` | `None` | Один фиксированный код |
| `snapshot_complete` | `True` | `False` |
| `metadata_unchanged` | `True` | `False` |
| `rows` | Список `dict` или `None` в исходном порядке | Пустой список |
| `observations` | Счётчики завершённого чтения | `None` |
| `scope`, `limits` | Отдельные копии фиксированных контрактов | То же |

`COMPLETE` означает: файл прочитан до EOF в установленных пределах, все его
строки завершены LF, число прочитанных байтов совпало с размером открытого
файла, а предусмотренные наблюдения metadata не выявили изменения.
Пустой регулярный файл может вернуть `COMPLETE` с нулём позиций.

Полнота чтения не означает корректность всех JSON, пригодность каждой записи,
доверенность ID, готовность к обучению или атомарный снимок файловой системы.
`metadata_unchanged=False` при отказе означает, что требуемая стабильность не
подтверждена; это не обязательное утверждение о фактически произошедшей записи.

## Строки, барьеры и сохранение видимых ID

Единицей позиции служит физическая строка, разделённая байтом LF. CRLF допустим;
его завершающие байты входят в размер строки. Последний LF не создаёт фиктивную
пустую позицию после EOF. Пустая строка между двумя LF создаёт свою позицию.

| Содержимое завершённой строки | Сохранённая позиция |
|---|---|
| Строго разобранный JSON-объект | Полный `dict`, без фильтрации полей |
| Пустая строка или только JSON whitespace | `None` |
| Неверный UTF-8 или JSON | `None` |
| Повтор одного JSON-поля, включая вложенные объекты и эквивалентные escapes | `None` |
| `NaN`, бесконечность или переполнение JSON float | `None` |
| JSON-массив, число, строка, boolean или `null` вместо объекта | `None` |

Выбор первого или последнего значения повторяющегося поля не выполняется.
Из неразобранного текста не извлекаются приблизительные ID. Такое событие
сохраняет своё место как барьер, но его скрытая идентичность остаётся неизвестной.

Строго разобранный объект сохраняется даже при неправильной схеме, отсутствии
ID или escaped lone surrogate. Это намеренно: существующий планировщик сначала
учитывает видимый точный `event_id`, а затем проверяет пригодность payload.
Если поздний объект с тем же ID непригоден, его ID всё равно должен блокировать
раннюю копию. Замена такого объекта на `None` потеряла бы эту информацию.

Следовательно, `decoded_objects` не является числом пригодных наблюдений,
а `barrier_lines` считает только позиции `None` уровня чтения/разбора.
Планировщик дополнительно исключает legacy, schema-invalid, surrogate, duplicate
и другие непригодные объекты по собственным правилам.

Порядок строк не сортируется. Никакие позиции не удаляются, тексты и ID не
нормализуются. Например, `F, None, A` не превращается в соседнюю пару `F, A`.

## Незавершённый хвост и отказ целиком

Текущий `LearningMemory._append_jsonl()` дописывает JSON и перевод строки.
Поэтому любая непустая последняя часть без LF считается незавершённой записью,
даже если её байты отдельно составляют корректный JSON или только пробелы.

При незавершённом хвосте, лимите ресурсов, ошибке I/O, недопустимом пути или
обнаруженном изменении файла возвращается `REFUSED`, `rows=[]`,
`observations=None`. Ранее прочитанные пригодные объекты наружу не передаются.
Это предотвращает использование частичного списка, в пропущенной части
которого мог находиться повторный ID или другое существенное наблюдение.

Коды отказа фиксированы:

| Код | Значение |
|---|---|
| `INVALID_REPO` | Неподдерживаемый тип или форма корня |
| `MISSING` | Компонент пути или файл отсутствует до успешного открытия |
| `NON_REGULAR` | Недопустимый тип компонента или целевого файла до открытия |
| `SYMLINK_REFUSED` | Найден symlink/reparse point до открытия |
| `RESOURCE_LIMIT` | Превышен предел чтения/разбора или достигнут recursion limit |
| `UNTERMINATED_FINAL_LINE` | Непустая последняя строка не завершена LF |
| `CHANGED_DURING_READ` | Нарушено ожидаемое соответствие файла/descriptor/metadata/размера |
| `UNREADABLE` | Ошибка файлового I/O |
| `INTERNAL_ERROR` | Другая перехваченная ошибка без раскрытия её текста |

Исчезновение между первоначальным осмотром и успешным открытием может дать
`MISSING`; после открытия — `CHANGED_DURING_READ`. Ни один вариант не отдаёт
частичные строки. Пути, содержимое и текст исключений в `reason` не включаются.

## Ограничения ресурсов

| Ограничение | Значение |
|---|---:|
| Байтов на файл | 32 MiB |
| Байтов на физическую строку, включая её завершение | 256 KiB |
| Физических позиций | 100 000 |
| Вложенность JSON-контейнеров | 64 |
| Лексических единиц на строку | 100 000 |
| Лексических единиц за чтение | 2 000 000 |
| Десятичных цифр в integer, без знака | 4 096 |

Перед `json.loads()` выполняется ограниченный лексический проход. Единицей
считаются открывающий контейнер, начало quoted string, включая ключи, либо начало
непрерывного примитивного токена вне строк. Скобки внутри строк и escaped quotes
не увеличивают глубину контейнеров. Этот проход ограничивает и неудачные попытки
разбора JSON; ошибки синтаксиса отдельно проверяет стандартный parser.

Строки с неверным UTF-8 и пустые строки не передаются JSON parser, но всегда
учитываются в пределах сырых байтов и физических позиций. Ограничение lexical
units не выдаётся за точное число decoded nodes или точную границу памяти Python.

Integer преобразуется небольшими десятичными блоками после проверки длины.
Это не меняет глобальные `sys`-настройки и не зависит от установленного в процессе
лимита преобразования длинной строки в integer. Планировщик сохраняет собственные
отдельные ограничения и может отказать при дальнейшей обработке снимка.

Ресурсные исключения обрабатываются раньше общих ошибок JSON/`ValueError`.
Они не превращаются в обычный барьер строки. При точном достижении byte/line
limit проверяется EOF: скрытый следующий байт или строка не отбрасывается молча.

## Файловые проверки и пределы гарантий

До открытия проверяется цепочка компонентов пути через `lstat`: symlink и
Windows reparse points отвергаются, каталоги и конечный регулярный файл
проверяются по типу. Открывается только фиксированный файл и только для чтения;
`O_BINARY`, `O_NOFOLLOW`, `O_NONBLOCK` добавляются там, где доступны.

Перед чтением сопоставляются первоначальная версия пути, открытый descriptor
и повторный осмотр цепочки. После EOF проверяются descriptor и путь ещё раз.
Счётчик прочитанных байтов должен совпадать с размером открытого файла.

Между `lstat` и `fstat` сравниваются совместимые поля:
`dev, ino, S_IFMT(mode), size, mtime_ns`. Полные `mode` и `ctime_ns` сравниваются
только между наблюдениями одного API. Это сохраняет уже установленный контракт
Windows CPython 3.12, где path stat и descriptor stat могут различаться по
семантике ctime и permission bits.

Эти проверки обнаруживают обычные изменения, но не блокируют writer, не дают
атомарного snapshot и не обнаруживают все гонки или намеренное восстановление
metadata. Изменения после возврата также возможны. Чтение может обновить atime.
Локальная форма пути не доказывает, что файловая система физически не размещена
на сетевом диске; функция не создаёт сетевых соединений сама.

## Сочетание с планировщиком и следующий этап

Синтетические тесты явно передают результат reader существующему planner:

```python
snapshot = read_learning_history_snapshot(repo)
plan = plan_correction_pair_evidence(
    snapshot["rows"], snapshot_complete=snapshot["snapshot_complete"]
)
```

Вызывающая сторона должна сохранить исходную причину отказа reader. У planner
неполный вход имеет собственный код `INCOMPLETE_SNAPSHOT`; он не заменяет
подробность причины первого этапа. Даже `COMPLETE` reader может быть отвергнут
planner по его собственным пределам или смешанным режимам времени.

Модуль не меняет существующие writer, analyzer, auditor, correction memory,
builder и правила накопления counts. Он не включает постоянный учёт уже
принятых событий, связь ID с payload между снимками, работу с ротацией,
несколько writers, обучение модели или переход со старого агрегата.

Следующий отдельный этап — контракт постоянного учёта событий и явной границы
между прежними накопленными counts и новыми observations. До этого нельзя
запустить два способа накопления для одних событий параллельно.

## Проверка и доставка

`tools/eval_learning_history_snapshot.py` использует собственные синтетические
файлы и изолированную загрузку модулей. Проверяются physical positions, строгий
JSON, поздние непригодные объекты с повторным ID, EOF/хвост/лимиты, обычные
изменения файла, Windows stat semantics, закрытие descriptors и отсутствие
записи либо раскрытия исходных данных при отказе.

Подготовка и пользовательский пакет запускают семь явно перечисленных suites:
шесть прежних наборов со 150 случаями и новый evaluator. Discovery, корневой
`test.py`, приложение, настоящая история, модели и обучение не запускаются.

Публичный Result содержит только фиксированные scope fields, разрешённые имена
тестов, их результаты и хеши приватных логов. Реальные `rows`, тексты, ID,
пути и traceback в него не входят. `actual_history_snapshot=NOT_RUN` и
`actual_pair_planning=NOT_RUN` относятся к реальным пользовательским данным;
синтетические вызовы reader и planner в тестах действительно выполняются.

Пакет сохраняет согласованный порядок: четыре payload-файла и новый Result,
автоматические commit/push результатов PASS или FAIL в experiment. Рабочие
данные нового запуска находятся под `Downloads\SkynetVS_Runs\M154`; прежние
каталоги сохраняются. Временный файл атомарной замены создаётся рядом с её
целью. Перенос блока в `main` отложен до его завершения.
