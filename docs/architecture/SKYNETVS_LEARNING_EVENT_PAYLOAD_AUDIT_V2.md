# Согласованность содержимого записей с event_id: аудит V2

Статус: второй пакет открытого блока `learning_event_provenance`.
База experiment: `2b9e99e546720744dad5dd7ef8101d175bb62a8a`.
Подтверждённый main: `61c372223b0abaea97fe973de50d02f51efa2520`.
Перенос блока в main отложен до его завершения.

## Назначение

`LearningMemory.log_command()` уже добавляет идентификатор к новым записям
истории. Контракт writer описан в
[`SKYNETVS_LEARNING_EVENT_IDENTITY_V1.md`](SKYNETVS_LEARNING_EVENT_IDENTITY_V1.md).
Новый этап расширяет самостоятельный `tools/audit_learning_data.py`:
он различает повтор одинаковой записи и использование одного ID для разного
содержимого. Он читает существующие два фиксированных файла и выдаёт только
обезличенные счётчики. Изменять данные или формировать correction pairs он
не начинает.

Проверяется согласованность нескольких сохранённых представлений одного ID
в пределах прочитанной истории. Отсутствие конфликтов не подтверждает автора
события, истинность распознавания, успех действия, независимость наблюдений
или правильность исторических счётчиков. Одиночное редактирование строки,
когда прежнего содержимого в файле уже нет, сравнить не с чем. Постоянного
реестра ранее прочитанных ID этот инструмент не ведёт.

## Сравнение ID и содержимого

Сохраняется прежнее правило допустимого ID: непустая после `strip()` строка.
Сам ключ сравнивается **точно**, без `strip()`, приведения регистра или
преобразования в UUID. Поэтому `id`, ` id ` и `ID` — разные значения. Writer
создаёт UUID4 в `.hex`, но исторический необязательный ID аудитор не ограничивает
только этим форматом. Отсутствие ID у старой строки остаётся информацией;
присутствующее некорректное значение остаётся finding.

Для каждого допустимого ID сравнивается **весь разобранный JSON-объект строки**:
`ts`, `accepted`, тексты, метаданные, вложенные слоты, массивы и любые неизвестные
поля. Нельзя незаметно исключить поле и тем самым разрешить его изменение под
сохранённым ID. Сам ID также входит в сравниваемое представление.

Внутреннее представление получается стандартным JSON-сериализатором:

```python
json.dumps(row, sort_keys=True, ensure_ascii=True,
           allow_nan=False, separators=(",", ":")).encode("ascii")
```

Сравниваются полученные байты. Это локальный контракт сравнения разобранных
JSON-значений, а не стандарт внешней канонизации, подпись или сравнение исходных
байтов файла. Хеш вместо содержимого для решения о равенстве не используется.

| Изменение представления | Результат сравнения |
|---|---|
| Порядок полей объекта, включая вложенный объект | Равенство |
| Отступы JSON, LF/CRLF, эквивалентные JSON escape-последовательности | Равенство |
| Порядок элементов массива | Различие |
| Пробелы внутри строки, регистр, Unicode-нормализация строки | Различие |
| Добавление, удаление или изменение любого поля, в том числе неизвестного | Различие |
| Значения `true`, `1`, `1.0` | Три разных представления |
| `1e0` и `1.0`, разобранные в одно значение float | Равенство |

Десятичная запись float проходит обычное преобразование JSON-парсером в float.
Различные исходные числовые литералы могут округлиться в одно значение. V2 не
обещает обнаружить различие исходных литералов после такого преобразования.
`-0.0` и `0.0` сохраняют разные сериализованные представления; целочисленное
`-0` после разбора становится `0`. Временные строки не нормализуются в моменты
времени для сравнения payload: изменение текста `ts` под тем же ID — различие.

Прежний строгий разбор JSON сохраняется: повторные имена полей, недопустимые
числа, невалидный UTF-8 и другие ошибки учитываются отдельно. Сравнение строки
с некорректными полями не делает её корректным обучающим примером. Разобранная
строка с одиночным суррогатом по-прежнему получает `invalid_unicode_lines`;
ASCII-экранирование позволяет обработать её диагностически без утечки или
необработанной ошибки кодирования.

## Счётчики всей группы

Группа состоит из всех прочитанных объектов с одним точным допустимым ID.
Если в ней есть хотя бы два разных представления payload, конфликтной считается
**вся группа**. Первое встретившееся содержимое не объявляется правильным.

| Поле | Смысл |
|---|---|
| `findings.duplicate_event_id_rows` | Прежний счётчик: для каждой группы из N строк прибавляется N−1 |
| `observations.replayed_event_id_rows` | N−1 только для групп с одним представлением содержимого |
| `findings.conflicting_event_id_groups` | Количество групп с разным содержимым |
| `findings.conflicting_event_id_rows` | Все строки этих конфликтных групп, включая первые и одинаковые копии |

Например, четыре записи одного ID с содержимым A, A, B, A дают три повтора ID,
одну конфликтную группу, четыре конфликтные строки и ноль replay-строк.
Перестановка этих четырёх записей не меняет данные счётчики. Отдельная прежняя
диагностика порядка временных отметок при перестановке, конечно, может измениться.

Если обнаружен конфликт после нескольких одинаковых копий, прежние replay-строки
этой группы переклассифицируются в конфликтные. Это классификация результата
аудита в памяти процесса; исходные записи при этом не редактируются.

Валидатор публичного результата проверяет, кроме типов и ограничений:

```text
duplicate = replayed + conflicting_rows - conflicting_groups
2 * conflicting_groups <= conflicting_rows <= rows_with_event_id
conflicting_groups <= rows_with_event_id - duplicate
0 <= replayed <= duplicate
```

Любой повтор ID, включая точную копию, остаётся finding. При полном чтении
такие данные дают `FINDINGS_IN_CHECKED_STRUCTURE` и код 1. Это не ошибка запуска
самого аудитора и не отрицательный результат синтетического теста, который
намеренно проверяет обнаружение повтора.

## Схема V2, границы и частичное чтение

Публичный результат имеет `kind=SKYNETVS_LEARNING_DATA_AUDIT_V2` и
`schema_version=2`. Схема закрытая: только разрешённые поля, статические коды
и ограниченные целые счётчики. В неё не входят ID, команды, локальные пути,
канонические payload, их хеши или тексты исключений.

Старые опубликованные отчёты V1 сохраняются без изменений. Текущий валидатор
V2 явно отвергает V1; он не выдаёт старый отчёт за результат новой проверки.
Существующие места использования внутри проекта — standalone CLI и именованные
синтетические evaluator-наборы. Старые выданные пакеты закреплены на своих
версиях и хешах; их не следует использовать как обновляющий запуск для V2.

Прежние ограничения чтения сохраняются: 32 MiB на файл, 256 KiB на строку,
100 000 строк и глубина JSON 64. V2 добавляет лимит
`event_payload_bytes=67108864`: не более 64 MiB канонических байтов первых
представлений всех обнаруженных ID. ASCII-экранирование может увеличивать
размер относительно исходного UTF-8, поэтому этот предел задан отдельно.
Для каждого ID сохраняются только первое представление, число появлений и
признак конфликта. Все варианты содержимого не накапливаются.

Этот лимит ограничивает удерживаемые канонические байты, а не весь расход RAM
интерпретатора: структуры Python, ключи ID, разбираемая строка и временное
представление имеют дополнительный расход. Проверяемый размер очередной строки
по-прежнему ограничен до разбора. При исчерпании предела результат становится
неполным, а не сообщает о согласованности всего файла.

Строка, на которой превышен предел, уже учтена как прочитанные байты/строка,
но не должна попасть в половину объектных или ID-счётчиков. Счётчики объектов
и групп описывают только обработанный префикс. Лимит, замена, дописывание или
другая обнаруженная смена файла сохраняют `NOT_FULLY_CHECKED` и код 2, даже
если в обработанном префиксе уже есть findings.

Сохраняются прежние запреты symlink/reparse-путей и проверка метаданных до,
во время и после чтения, включая исправленное сопоставление stat/fstat Windows.
Это обнаружение обычных изменений, а не файловая блокировка, защита от
враждебного процесса или атомарный снимок двух файлов. Чтение может обновлять
время последнего доступа файловой системы.

## Совместимость с обучением

`FeedbackAnalyzer`, builder, correction memory и promotion этим пакетом
не меняются. В частности, новая диагностика пока не исключает повторные
строки из счётчиков и не останавливает автоматически настоящий builder.
`stable_event_identity_verified=false`, исторические числа не проверены,
готовность к обучению остаётся `NOT_ASSESSED`.

Причина отдельного этапа существенна: текущий analyzer выбирает соседние
rejected → accepted записи. Простое удаление строк может создать новую пару
из прежних несоседних наблюдений. Накопительная отметка памяти также не умеет
вычитать уже учтённое. Поэтому перед интеграцией нужны правила пары, барьеров
для повреждённых участков и перехода от прежнего агрегата к событиям.

Следующая работа должна определить идентичность обоих концов correction pair,
версию правила подбора и запрет повторного использования принятого наблюдения
как нового подтверждения. Требуется отдельная граница перехода, чтобы одна пара
не поступала одновременно через прежний агрегат и новый реестр. Хранение ID
при ротации, сбои, согласованность записи и несколько писателей остаются
открытыми задачами. V2 — диагностическая основа этих решений.

## Проверки и доставка

Новый `tools/eval_learning_event_payload_audit.py` проверяет сравнение и
классификацию на собственных временных данных. Существующие 43 проверки
аудитора, 10 writer, 23 памяти и 32 границ пакетов сохраняются в фиксированном
наборе. Корневой `test.py`, discovery, настоящая история, приложение, обучение
и полный pipeline не запускаются.

Установщик `SkynetVS_M154_AuditLearningEventPayloads.ps1` применяет четыре
закреплённых файла к точной базе experiment и запускает только эти синтетические
наборы. Он не выполняет аудит настоящих history/correction-memory файлов.
Фактический Windows-результат создаётся в
`docs/maintenance/M154_LearningEventPayloadAudit_Result.json`.

Изменения и обезличенный результат автоматически коммитятся и отправляются
в текущую экспериментальную ветку, включая FAIL. Произвольные соседние изменения
не добавляются в commit; отдельное изменение целевого файла вызывает остановку
до его перезаписи. Обычные Git hooks сохраняются. Возобновление доставки
использует сохранённый результат без второго тестирования или второго commit.
Это не перенос блока в main и не миграция пользовательских данных.
