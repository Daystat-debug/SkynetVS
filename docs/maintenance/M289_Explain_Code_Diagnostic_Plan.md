Снимок исходников: `e67c9ad013f4fa451046b9c461e8f055db8beaaf`. Архитектура и значение статусов определены в [спецификации](../architecture/SKYNETVS_COGNITIVE_CORE_V2.md).

## Материал и воспроизводимость

- Диагностический набор D — сохранённый запуск ModelLab `m289_preview_ba27865bbfcd41479fb4246bbfe10174`: `PUBLIC_RECEIPT` (цитата при неполном ответе), `MIX_REMAINDER` (отказ при найденном кандидате), `INCOMPLETE_SEARCH` (промах поиска), `UNKNOWN_NAME` (отрицательный контроль), `LIVE_GIT_LOCATION` (хост удержал ответ без живого наблюдения). Для каждого сверить Run, индивидуальную квитанцию, текст, строки и human_rubric. Диагноз уточняется по данным. Эти пять случаев можно использовать для настройки; их результаты учитываются отдельно от H.
- H — открытый диагностический набор: все 12 вопросов и ключ опубликованы до разработки. Зафиксировать SHA-256 утверждённого протокола, commit исходников и список ID. При прогоне поиск и модель получают только дословный вопрос и входы штатного сценария; ключ, эталонные пути и рубрика исключаются из корпуса, промптов и памяти. После разработки провести отдельную независимую оценку на новых, ранее не использованных вопросах: до запуска зафиксировать набор, ключ и версию решения, скрыть ключ от системы и не подбирать по результатам настройки. Результаты D и H в эту оценку не включать.
- До запуска записать хеши пакета пилота, модели GGUF и inference-бинарника, версии/бэкенд, параметры декодирования и seed (либо отметку «не поддерживается»), шаблон промпта, лимиты поиска/контекста/ответа/времени, область чтения и версию проверяющего. Сохранить исходные настройки M289 для базовой линии. Если артефакт или снимок не совпал, записать BLOCKED; подмену версии не считать повтором. Веса, произвольные пользовательские журналы и сырые локальные пути не публиковать.

Категории: однофайловые — H1, H2, H4; многофайловые — H3, H7, H8; недостаток сведений в разрешённых исходниках — H9, H10; живое состояние ПК — H5, H6; неоднозначность — H11, H12. H1–H6 сохраняют исходные формулировки. Пути в ключе относительно `modules/developer_task_ui/app/`. Каждый проверяемый факт оценивается отдельно. Допускается эквивалентная формулировка с опорой на Git blob. До первого прогона оценщик извлекает указанные строки из закреплённого commit и фиксирует OID и хеш текста.

## Порядок измерений

1. **Базовая линия и поиск (A).** После разбора D зафиксировать диагностическую версию и пройти H1–H12 по порядку с чистым состоянием задачи. Сохранить вопрос, статус/пропуски сканирования и кандидатов до отбора окон. Для шести отвечаемых случаев (H1–H4, H7, H8) считать долю требуемых исходных участков в первых 1 и 4 кандидатах по фактическому списку: кандидат должен покрывать нужный символ в нужном blob. Для каждого из H3, H7, H8 отдельно отметить, найдены ли оба файла и попали ли обе стороны связи в контекст. Верно угаданная связь без второй опоры не даёт полного балла.
2. **Полнота контекста (A).** Зафиксировать ID и диапазоны найденных, выбранных, обрезанных и действительно переданных provider фрагментов. Прямо перед вызовом проверить, для скольких обязательных фактов в отправленных строках есть основание. Считать отдельно потери поиска и последующего ограничения бюджета. Если генерация пропущена, контекст для модели пуст, причины явно отмечаются. Получить ответ, сохранить его до решения хоста и итог после проверки.
3. **Модель на правильном контексте (B).** Дать тому же provider те же вопросы с целыми эталонными строками в формате EvidenceSet; сохранить лимиты и промпт A. Рубрику не передавать. Для H5 дать лишь статическое описание, для H6 — пустой набор с пропуском генерации. Для H9–H10 дать строки о реально доступных данных без недостающих измерений; для H11–H12 — основания для обеих трактовок без выбора за пользователя. Если эталон не вмещается, отметить BLOCKED_BUDGET. Оценщик проверяет сырой ответ до просмотра решения хоста: факты, неподтверждённые добавления, уместность отказа или уточнения. Пропуск генерации оценивается как решение хоста; качество модели в таком случае — N/A.
4. **Публикация (C).** Без вызова модели передать валидатору фиксированные предложения на том же EvidenceSet: (1) полный ответ H1 с точной опорой; (2) ответ H1 с чужим ref_id; (3) с искажённой цитатой; (4) H4 только о пропуске файла, с подлинной строкой; (5) конкретный код возврата для H5 со ссылкой на статический исходник. Ожидания по буквальной проверке: 1 и 4 проходят, 2 и 3 отклоняются. Решение о показе полноценного ответа по человеческой рубрике: только 1; для 5 требуется удержание из-за отсутствия наблюдения. Для 4 отдельно отметить возможное расхождение валидатора и оценщика. Зафиксировать полные байты фикстур и ожидаемые метки до первого вызова валидатора.

Никаких подсказок по эталонному файлу в A. В B подмена касается только входа retrieval → модель в диагностическом драйвере; неподлинные ссылки не регистрируются как реальные. Сохранённый пакет M289 и его проверки закреплённого снимка остаются эталоном. Если штатный мост допускает только top-1, этот предел отражается в A, а B маркируется как контрфактический тест provider на эталоне. Новые источники не открываются.

## Отчёт и критерий завершения диагностики

Одна строка на case/вариант: версия, снимок, basis (static/live), статус и длительность поиска, позиции нужных кандидатов, ref_id/диапазоны до и после бюджета, число необходимых/переданных фактов, вызов модели, статус и время provider, буквальная валидность, предложенные/подтверждённые факты, решение хоста, оценка публикации и первая стадия потери. Техническая ошибка остаётся в таблице; пропуск генерации не превращается в успешный ответ модели.

Отдельно для D и H вывести числители и знаменатели. Для шести отвечаемых вопросов H — покрытие поиска@1/@4, полноту переданного контекста и ответа B; для трёх многофайловых дополнительно — покрытие обеих сторон связи. Для H9–H10 считать верное указание недостающих сведений, для H5–H6 — отсутствие выдуманного live-факта и корректное удержание, для H11–H12 — адресное уточнение либо условный ответ с различением трактовок. Общий отказ без объяснения неоднозначности не засчитывать. Для всех категорий показать неподкреплённые утверждения и ошибки публикации; для C — ожидаемое и фактическое решение по каждой фикстуре. Привести A и B рядом, неприменимое обозначать N/A. Итоги H характеризуют эти 12 открытых случаев.

Диагностика завершена, когда все строки учтены, ошибки и пропуски объяснены либо обозначены как не локализованные, а результаты можно связать с закреплёнными входами. Отрицательный результат допустим. Для последующего принятия первого сценария нужны отдельные испытания совместимости и отмены, подтверждённый многофайловый ответ и отсутствие публикаций с поддельными ссылками или выдуманным live-фактом. Этот документ не запускает эксперимент.
