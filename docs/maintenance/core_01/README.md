# Skynet Core 0.1. Исследование пути вызовов

Команда устанавливает один статически подтверждённый путь от указанной функции к другой в пяти файлах Git HEAD на начало задачи. Она также принимает прежние вопросы о прямых вызовах и полях отчёта. Для многошагового вопроса пользователь задаёт только начало и конец. Промежуточные имена хост извлекает из наблюдений инструмента.

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/skynet_investigate.py "Как от search_repository вызовы доходят до extract_symbols?"
.\.venv\Scripts\python.exe -I -S -B tools/skynet_investigate.py --json "Может ли search_repository через другие функции вызвать modules_from_source?"
.\.venv\Scripts\python.exe -I -S -B tools/eval_investigation.py verify
```

Для запуска нужен тот же Windows-стенд с ранее проверенным комплектом M289. Проверка сверяет результаты, в том числе сохранённый неуспех T4. В штатной команде и этой проверке расход генераций равен нулю.

## Пример полного цикла

1. В задаче A хост распознаёт начало `search_repository`, конец `extract_symbols` и строит план обратного поиска. Проверяет, что оба имени однозначно обозначают определения в снимке.
2. `calls(extract_symbols)` находит обращение из `rank_symbols`. Это ещё не начало пути. Хост проверяет ссылки и ставит в очередь найденное определение. [Место вызова](https://github.com/Daystat-debug/SkynetVS/blob/d222aa04cd5647269fbf5b8f2e749717d97eb8e6/modules/developer_task_ui/app/retrieval/m127_symbol.py#L72-L77)
3. `calls(rank_symbols)` даёт `rank`. Импорт и место вызова относятся к тому же определению M127, с которого продолжился поиск. [Импорт](https://github.com/Daystat-debug/SkynetVS/blob/d222aa04cd5647269fbf5b8f2e749717d97eb8e6/modules/developer_task_ui/app/retrieval/m130_rank.py#L18) · [Вызов](https://github.com/Daystat-debug/SkynetVS/blob/d222aa04cd5647269fbf5b8f2e749717d97eb8e6/modules/developer_task_ui/app/retrieval/m130_rank.py#L125)
4. `calls(rank)` находит искомое начало. Хост прекращает поиск, связывает три звена по снимку, пути и строке определения, передаёт только основания выбранной цепочки и проверяет предложение перед публикацией. Пользователь видит путь в прямом порядке. В этом примере выдано три утверждения и 11 ссылок с учётом повторов. [Импорт](https://github.com/Daystat-debug/SkynetVS/blob/d222aa04cd5647269fbf5b8f2e749717d97eb8e6/modules/developer_task_ui/app/context_search.py#L14) · [Вызов](https://github.com/Daystat-debug/SkynetVS/blob/d222aa04cd5647269fbf5b8f2e749717d97eb8e6/modules/developer_task_ui/app/context_search.py#L153)

## Что измерено

На снимке `d222aa0` выполнены 11 предварительных случаев и четыре задачи, зафиксированные после реализации. Для проверки ложной инструкции использована отдельная временная копия этого коммита с одним безвредным комментарием. Критерий для пути требует точного порядка всех звеньев, буквальных ссылок на оба определения, выражение вызова и межфайловый импорт. Оценщик отдельно сверяет координаты с ручной разметкой и байты с Git. Для отрицательного случая проверяются причина и пустой набор опубликованных утверждений. [Исходные задачи](controls.json) · [Новые вопросы](transfer.json) · [Поштучный журнал](results.json)

| Задачи | Итог |
|---|---|
| До реализации | 11/11 по рубрике, включая инструментальную ошибку, подменённую ссылку, предел шагов, неоднозначное имя и выход за область |
| T1 и T2 | Обе новые цепочки восстановлены полностью. Через `module_rank` обнаружены три звена, от функции `main` к `rank_title_only` — два |
| T3 | В обратном направлении путь установить не удалось. Выдана причина, утверждений о невозможности вызова во всём проекте нет |
| T4 | Формулировка «Дотягивается ли … через промежуточные функции до …?» привела к лишнему уточнению. В проверенных исходниках есть два нужных звена. Эталон не выполнен |

Сравнение на **пяти различных положительных задачах о путях** (A, B, T1, T2, T4), без повторного учёта копии с комментарием:

| Способ | Полные пути | Нужные звенья |
|---|---:|---:|
| Один вызов прежнего `compose` с исходным русским вопросом | 0/5 | 0/11 |
| Один вызов `calls` с заранее данным точным именем конечной функции | 1/5 | 5/11 |

На трёх положительных задачах переноса цикл дал 2/3 полных ответов и 5/7 нужных звеньев, однократный `calls` — 0/3 и 3/7. По всем 15 случаям проверено 61 появление ссылки, включая унаследованный ответ `flow`. На задачах о путях дополнительных необоснованных звеньев в опубликованных ответах не обнаружено. Разметка и проверка выполнены в рамках одного проекта. Эти числа не оценивают произвольные вопросы по Python.

## Выбор компонентов и пределы

Хост использует прежние `TaskRequest`, `EvidenceSet`, `AnswerProposal` и `Task.run`. `lab.Objects` закрепляет Git HEAD и разрешённые blob. `calls.lookup` разрешает прямые вызовы и импорты. Для обычных вопросов прежний `compose` делегирует `auto`, `calls` и `flow`. Выделенная из `collect` функция `pack_result` упаковывает каждый результат тем же способом. Перед выдачей `verify_snapshot` сверяет привязку утверждений к фактически переданным основаниям. Новая часть — интерпретация запроса о пути, очередь обратного поиска и решение о продолжении. [Координатор](../../../tools/skynet_core_task.py) · [Адаптер доказательств](../../../tools/skynet_core_explain.py) · [Цикл](../../../tools/skynet_investigate.py)

В `modules/core` размещены, в частности, конфигурация и телеметрия. `runtime/mode_manager.py` ведёт состояние голосового окна, `command_runtime.py` обслуживает команды, а право на действие выдаёт `ActionAuthority`. Для статического исследования такое право не требуется. Планировщик Developer Tasks `make_behavior_plan` принимает проверенный результат сравнения и формирует обязанности по тестированию. Его входной контракт отличается от запроса о пути. Прежний `--changes` нужен для сопоставления двух снимков. Новый режим работает с одним Git-снимком, Working Tree не читает. [Планирование Developer Tasks](../../../modules/developer_task_ui/app/symbol_behavior_plan.py) · [Полномочия](../../../modules/action_authority.py) · [Обзор изменений](../../../tools/skynet_change_review.py)

Для поиска пути допускаются не более шести обращений к `calls`, до 96 накопленных уникальных ссылок, пять файлов размером до 256 КиБ каждый и вопрос до 600 символов. Очередь пропускает повторно встреченное имя. При исчерпании шагов результат удерживается. В прежнем режиме составного вопроса действует его собственный предел в восемь частей. Внешний процесс прекращает исследование по истечении 25 секунд, включая запуск работника. Отдельно проверено удержание по короткому внешнему тайм-ауту. Используется прежний Windows Job с завершением дочерних процессов. Реальный файловый symlink сохраняет статус **UNVERIFIED**.

В записанном прогоне медиана обработки задачи с захватом снимка составила 322 мс, диапазон 259–403 мс, без независимой проверки оценщиком. Пять отдельных запусков полной CLI для A с разбором JSON в PowerShell дали 662, 648, 612, 632 и 622 мс, медиана 632 мс. Максимум наблюдавшихся обращений к `calls` на задачу — четыре.

## Модели и проверка границ

Четыре раза локальная Qwen3-8B предлагала маршрут только по публичной формулировке вопроса, без исходников и полномочий. Рубрика проверяла и вид операции, и упорядоченные аргументы. Детерминированный выбор дал 4/4, Qwen — 3/4. В случае K предложение для вопроса о поле не совпало с контрактом. Журнал хранит результат сравнения, точное несовпавшее поле не сохранено. Запуск модели занял 15,746 с, четыре генерации — по 196–290 мс после запуска. Здесь проверялась интерпретация задачи, генерация итоговых объяснений не измерялась. На свободной формулировке T4 Qwen не проверяли. [Параметры и оценки](planner.json) · [Воспроизводимый тест планов](../../../tools/eval_investigation_planner.py)

Проверены назначение M-серий в архитектурном брифе и состав локальных артефактов, в частности M163 shortlist, M226 live diagnostics и M268 OwnM150 AnswerSFT с пометкой NOT_DEPLOYED. Подтверждённого преимущества этих компонентов в выборе следующего статического шага нет. В этом эксперименте их качество не измерялось. В CLI работает детерминированный контроллер. Способность самостоятельно изобретать планы для новых классов задач не установлена.

Проверены `eval_core_adapter.py verify` (шесть вопросов и десять контролей публикации, доступа и отмены), `test_core_task.py`, `eval_expanded_reader.py regression` (38/38), `eval_change_review.py verify` (11/11) и `eval_package_boundaries.py` (32/32). Детерминированная проверка не вызывает модель. Для отдельного повтора именно сравнения планов нужен новый выходной файл и ещё четыре генерации:

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/eval_investigation_planner.py "$env:TEMP\skynet-core01-plans-repeat.json"
```
