# Объяснения с проверяемыми исходниками

Практический результат — команда `--calls` для чтения прямых вызовов именованной функции. В двух новых содержательных вопросах она правильно указала вызывающие функции, привязку фактических аргументов к параметрам и назначение результата. На одном из этих вопросов старый CLI пропустил второе место вызова. Свободное объяснение произвольного кода остаётся ненадёжным: при новой выдаче обычного текста на K1–K3 и L1 получилось **0/4** полных ответов.

## Как пользоваться

Из корня экспериментальной ветки на машине с установленным и проверяемым комплектом M289:

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/skynet_explain.py --calls "Кто вызывает rank, какие аргументы передаёт и куда записывает результат?"
.\.venv\Scripts\python.exe -I -S -B tools/skynet_explain.py --prose "Как в отчёте поиска показывают оценку ключевого файла?"
```

В `--calls` укажите имя одной функции верхнего уровня. CLI объясняет прямой вызов внутри функции верхнего уровня в пределах трёх разрешённых файлов. Он связывает имя с определением в том же модуле или явным импортом и сопоставляет аргументы с видимой сигнатурой Python. Он пропускает затенённые имена, вложенные области, методы, динамическую диспетчеризацию и вызовы через переменные. Значения аргументов описаны выражениями из исходника. Код проекта не исполняется. Отсутствие найденного вызова не устанавливает, что функция не используется в приложении.

`--prose` принимает обычный вопрос. Qwen выбирает разделы по индексу из имён и лексики текущего кода. Вторым вызовом она получает оригинальные строки выбранных разделов и пишет обычный текст. По каждому прочитанному диапазону программа сверяет commit, blob, SHA-256 исходника и байты диапазона. Ссылки показывают контекст всего объяснения. CLI помечает смысл и полноту как требующие проверки; в этом режиме нет ни модельного рецензента, ни ограничения «три ссылки на утверждение». Вызов без флагов сохраняет прежний режим.

## Что показали измерения

Все измерения выполнены по Git-снимку `1d5a306`. Оценены тексты из консоли и исходники по ранее зафиксированным фактам. Сценарий прямых вызовов проверялся на отдельном наборе после фиксации первой серии. Эти две выборки оценивают разные способности. | Случай | Полнота выданного ответа | Смысл и опора в исходниках |
|---|---|---|
| O1, oracle | 3/3 факта по существу | Верно различены `binary` и `not_utf8`, обе ветви обходят запись в `sources`. Пометка «Частично» излишняя. Один диапазон подтверждает всё объяснение. |
| O2, oracle | Частичный | Модель назвала создание читателя и `shutil.which`, упустила `is_file` и возврат абсолютного пути. Слова о «стандартных каталогах» не следуют из Unix-ветви. Все нужные строки были показаны. |
| K1, CLI | Верно описана регистрация ошибки, пропущен `join(timeout=3)` | Путает ожидание процесса (15 с) с ожиданием каждого потока (3 с). Обе операции были в ссылке B88–108. |

В прочитанных блоках нет B106–108 с возвратом stdout. Baseline, наоборот, назвал stdout, но взял предел в 6 цифр из другой операции, а ссылка не показывала сам возврат. |
| K3, CLI | Указан источник счётчика, пропущено публичное поле | Ответ дошёл до `rank_symbols` и `function_candidates_total`, но выдал промежуточное имя за поле поиска. Упоминание словаря `out`, якобы возвращаемого из `rank`, ошибочно. Навигатор выбрал только файл ранжирования, поэтому вызывающий код с `candidate_functions` отсутствовал. |
| K4, CLI | Обоснованный отказ | Для числа ошибок при последнем обходе нужен журнал. Прежний CLI тоже удержал ответ, но предложил уточнить операцию вместо запроса журнала. |
| L1, CLI | Сообщение о пустом контексте приведено точно; формат списка описан частично | Показано форматирование `.3f`, но не указаны нумерация с единицы и путь в каждой строке. Все эти данные были в показанном фрагменте. |
| L2, CLI | Обоснованный отказ | `main.py` вне области, 0 вызовов модели. |

В исходных O1/O2 наложились несколько причин. Схема отбросила вывод O1 с семью адресами; в следующем варианте экранированный NUL стал непечатным символом после разбора JSON. На O2 буквальные ссылки проходили даже при ошибке направления условия. Затем Qwen-рецензент сначала одобрил неполный ответ, а при другой компоновке признал все утверждения подтверждёнными и одновременно потребовал отсутствующий в рубрике тип. Новая выдача устранила эти причины структурного отказа; K1 и L1 показывают остаточные ошибки чтения достаточного кода, K2 и K3 — потери при выборе реализации и её вызывающего кода. ## Проверка и бюджет

Два подхода и **16/16 генераций** одной установленной Qwen3-8B-Q4_K_M. На oracle с обычным текстом ушло 2, на базовые K — 4, на новый режим K/L — 9, на старый CLI для S1 — 1. Статический режим не запускал модель. После инициализации чтения Git время ответа S1/S2 составило 0,099/0,104 с. Для базового S1 с холодной моделью — 7,028 с. Для `--prose` K1 занял 8,45 с с запуском модели, тёплые K2/K3 — 1,55/2,35 с. Каждый замер однократный.

Шесть трасс проверены отдельно от модели: **54/54** выведенных в этих прогонах Git-ссылки прошли техническую сверку, включая повторы. Для `--prose` проверено также присутствие исходных строк каждого диапазона в фактически переданном запросе. Прошли целевые тесты CLI, 15 прежних проверок grounding и 32/32 проверок архитектурных границ.

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/test_skynet_explain.py
.\.venv\Scripts\python.exe -B -m tools.eval_package_boundaries
$logs = (Get-ChildItem docs/maintenance/evidence_reader/*.jsonl).FullName
.\.venv\Scripts\python.exe -I -S -B tools/eval_evidence_reader.py check @logs
```

Для повторения отдельного измерения драйвер принимает группу, режим и **новый** путь JSONL. Измеренные пары: `oracle prose`, `cli baseline`, `cli prose`, `call_oracle static`, `calls static`, `calls baseline`. Драйвер открывает временную копию закреплённого commit. Проверки CLI используют обычные разбор аргументов, обработку вопроса и вывод, при этом сохраняют открытый проверенный снимок и провайдер между вопросами одного прогона. Отдельно проверен запуск `--calls` из командной строки на HEAD экспериментальной ветки.

Для общего сценария следующий технический шаг — связывать вопрос с конкретной операцией и прослеживать её получателя, возвращаемое значение и его использование до формирования текста. Для K1 это даёт различие между ожиданием процесса и потока, для K3 — переход от поля ранжирования к публичному полю поиска. Измерения не устанавливают необходимость более крупной модели.
