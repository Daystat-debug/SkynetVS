# Cognitive Core читает сохранённый рабочий код

В одном и том же месте вызова `rank_symbols` читатель нашёл `limit=100` в Git HEAD и `limit=37` после сохранения правки в отдельной лабораторной копии. В обоих случаях `rank` присваивает результат переменной `sym`, а поле `function_candidates_total` восходит к `len(rows)`. Величина лимита выдачи и происхождение счётчика различены в ответе. [Формулировки и изменение до реализации](questions.json) · [Утверждения, фрагменты, координаты и хеши](results.json)

## Запуск в Windows

Из корня SkynetVS, с проектным Python и установленным проверяемым комплектом M289:

```powershell
$q = "Кто передаёт параметры в rank_symbols и как формируется function_candidates_total?"
.\.venv\Scripts\python.exe -I -S -B tools/skynet_core_explain.py --working-tree "$q"
.\.venv\Scripts\python.exe -I -S -B tools/skynet_core_explain.py --git-head "$q"
.\.venv\Scripts\python.exe -I -S -B tools/skynet_core_explain.py "$q"
.\.venv\Scripts\python.exe -I -S -B tools/eval_working_tree.py verify
```

Первый вызов делает свежий снимок сохранённых файлов. Второй разрешает HEAD один раз на задачу и далее читает объекты по SHA. Третий сохраняет исходный Git Snapshot `ee908b0`. Можно добавить `--json` для просмотра `TaskRequest`, `EvidenceSet`, `AnswerProposal` и решения хоста. Ссылки HEAD адресуют коммит; доступность этого коммита на GitHub зависит от его публикации.

## Какие байты подтверждают ответ

Хост привязывает источник `skynetvs.retrieval.working-tree` к каталогу установленного проекта и пяти путям из `lab.SCOPE`: `context_search.py`, `git_source.py` и трём модулям ранжирования M126, M127 и M130. Параметров CLI для произвольного каталога, пути или маски нет. Каждый запрос получает собственный снимок. Источник передаёт исходный текст прежним AST-инструментам через общий интерфейс. В изменениях анализаторов затронута выдача идентификаторов и ссылок. Выбор инструментов и разрешение связей выполняет существующий код. [Источник](../../../tools/skynet_working_tree.py) · [Хост](../../../tools/skynet_core_explain.py)

1. Перед чтением источник последовательно открывает компоненты пути от диска, проверяет атрибуты и конечный путь каждого дескриптора. Все каталоги и пять файлов остаются открытыми во время захвата. Reparse points, дополнительные жёсткие ссылки и файлы крупнее 256 КиБ отклоняются. Для текста проверяется кодировка Python, поддерживается UTF-8 с BOM и без него.
2. Снимок содержит точные байты. Его идентификатор строится из упорядоченного списка путей и SHA-256 файлов. В хеш входят исходные переводы строк. Локатор содержит идентификатор снимка, относительный путь, включительные номера строк от 1, SHA-256 файла и фрагмента. `file:`-ссылка указывает на действительный путь с диапазоном и снимком во фрагменте URI. После следующего сохранения по тому же пути может открыться новая версия. Проверенный текст прежнего фрагмента остаётся в выданном `EvidenceSet`.
3. На время AST-анализа файловые дескрипторы освобождаются. Перед публикацией хост повторно открывает **весь** разрешённый набор, проверяет объект файла, размер, время записи и точное равенство байтов. Дескрипторы с разрешённым совместным чтением удерживаются до терминального решения задачи. Конфликт с открытым писателем, смена файла или содержимого удерживают публикацию. После ответа дальнейшие сохранения относятся к следующей задаче. Это снимок на момент проверки. [Режимы совместного доступа Windows](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)

## Измерения и ограничения

| Заранее зафиксированный вопрос | Git HEAD | Working Tree лабораторной копии |
|---|---|---|
| W1. Вызов и происхождение счётчика | Лимит 100, длина `rows` | Лимит 37, длина `rows`. В каждом ответе 9 фрагментов и один подтверждённый статический переход |
| W2. Происхождение `no_model_training` | Литерал `True` | Тот же литерал, локальная ссылка |
| W3. Поиск вызовов в `outside.py` | `out_of_scope` | `out_of_scope`, доказательств не выдано |

Парное измерение использует временный Git-клон с реальным HEAD `fb45423`. Только диагностический инструмент материализует в нём разрешённые файлы и меняет один аргумент. Наличие незакоммиченной правки проверяется Git. Из временного клона сохранены переносимые координаты и фрагменты. Реальный каталог проекта проверен отдельно при HEAD `3c8453d`: три процесса с JSON и три с текстовым выводом подтвердили одни и те же утверждения и соответствующие источнику ссылки. [Вывод на реальном проекте](checkout.json)

Из 14 проверок хранения и публикации 13 выполнены, одна пропущена:

- Изменение с прежними размером и временем, замена на другой файл с теми же байтами и изменение файла вне процитированных фрагментов дали `working_changed`. Ответ и доказательства из устаревшего захвата удержаны.
- Уже открытый писатель дал `working_busy`. Попытки открыть файл для записи во время чтения, повторной сверки и после проверки ссылок до терминального решения получили отказ Windows. После закрытия дескрипторов следующая задача увидела новую правку `37 → 38`.
- Отклонены выход за профиль, жёсткая ссылка, реальный junction в пути, поддельный GitHub URL и ссылка из прежнего снимка на побайтово совпадающую строку. Отдельная инъекция атрибута reparse для файлового дескриптора проверила отказ. Создать настоящий файловый symlink под данной учётной записью Windows не позволила (`WinError 1314`). Этот результат не включён в число пройденных проверок.

Сохранены прежние проверки Core, 38/38 архивных решений, 14/14 пар предыдущего сравнения и 32/32 архитектурных проверки. Работа ограничена фиксированным локальным диском Windows, пятью сохранёнными файлами и синтаксическим подмножеством статических анализаторов. Несохранённый буфер редактора в снимок не попадает.
