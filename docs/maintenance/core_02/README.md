# Skynet Core 0.2. Кто вызывает производителя поля

Вопрос задаётся существующей команде из корня SkynetVS на Windows. Для запуска нужен прежний локальный комплект M289. Оба запуска ниже обходятся без генерации модели.

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/skynet_investigate.py "Кто вызывает функцию, которая формирует function_candidates_total?"
.\.venv\Scripts\python.exe -I -S -B tools/eval_producer_investigation.py verify
```

## Пример решения

1. Хост закрепляет Git HEAD и распознаёт вопрос о вызывающих участках. Пользователь указал только ключ результата. План предполагает получить определение производителя и искать вызовы только после его проверки.
2. Первый шаг — `flow(function_candidates_total)`. Хост берёт из существующего индекса `flow.Slice.producers` узел функции, узел ключа и выражение значения. В контрольном снимке этой паре соответствуют определение `rank` и строка, формирующая поле. Хост проверяет однозначность имени и координаты обеих ссылок. Глубокое происхождение значения для этого вопроса не требуется. [Определение](https://github.com/Daystat-debug/SkynetVS/blob/1de73ad46041fac1a9a9a2b00e9e14dbf3564567/modules/developer_task_ui/app/retrieval/m130_rank.py#L110) · [Поле](https://github.com/Daystat-debug/SkynetVS/blob/1de73ad46041fac1a9a9a2b00e9e14dbf3564567/modules/developer_task_ui/app/retrieval/m130_rank.py#L135)
3. Из первого наблюдения получается аргумент второго шага — `calls(rank)`. Для каждого места хост сверяет commit, путь и строку определения с первым шагом, проверяет ссылки на определение, вызывающий участок и выражение вызова. В примере найдены `search_repository` и функция `main` из M130. Это два прямых обращения в обследованных файлах. [Импорт](https://github.com/Daystat-debug/SkynetVS/blob/1de73ad46041fac1a9a9a2b00e9e14dbf3564567/modules/developer_task_ui/app/context_search.py#L14) · [Вызов в search_repository](https://github.com/Daystat-debug/SkynetVS/blob/1de73ad46041fac1a9a9a2b00e9e14dbf3564567/modules/developer_task_ui/app/context_search.py#L153) · [Вызов в main](https://github.com/Daystat-debug/SkynetVS/blob/1de73ad46041fac1a9a9a2b00e9e14dbf3564567/modules/developer_task_ui/app/retrieval/m130_rank.py#L151)
4. Перед публикацией хост ещё раз сверяет HEAD и проверяет через `Task.run` все выданные утверждения и их основания. В результате три утверждения и девять появлений Git-ссылок. JSON доступен с `--json`: цель находится в исходном вопросе, тип плана — в `plan`, последовательность инструментов, аргументы и наблюдённые статусы — в `steps`, принятые утверждения — в `claims`, причина удержания — в `reason`.

Распознавание направления использует роль каждого идентификатора, предлоги и глагол достижимости. Так Core понимает и «Можно ли из main добраться до modules_from_source?», и прежний T4. Для вопросов о производителе проверяются роли вызывающего и вызываемого. Доказательства и решение о публикации по-прежнему проходят через существующие контракты. ### Сравнение одинаковых задач

Для сопоставления выделены все 13 вопросов о поле без инъекции инструментальной ошибки, включая разновидности формулировок и контролируемые Git-изменения. Фиксированному сценарию заранее известен вид задачи. Имя поля он извлекает из того же вопроса, имя функции получает из `flow`. Он отдельно запускает исходный `Slice.answer` и `calls.lookup` и использует общий механизм проверки предложения. Обоим двухшаговым вариантам доступны один снимок, два инструментальных шага, 25 с и 96 уникальных выдаваемых ссылок. Однократный `compose` получает исходный вопрос. Для отрицательного случая рубрика требует правильную конкретную причину и пустой ответ.

| Вариант | Полные ответы на 10 положительных | Причины на 3 отрицательных | Медиана после захвата снимка |
|---|---:|---:|---:|
| Однократный compose | 0/10 | 0/3 | 47,0 мс |
| Фиксированный flow → calls | 10/10 | 3/3 | 96,9 мс |
| Core 0.2, включая выбор плана | 9/10 | 3/3 | 97,4 мс |

`compose` удержал ответы во всех 13 случаях с общим запросом уточнения. Разница в один положительный ответ между двумя другими вариантами обусловлена T5: «Чей результат содержит title_token_count и кто пользуется этой функцией?». Core остановился до вызова инструментов. При известной операции фиксированный сценарий выдал подтверждённый ответ. На этих задачах преимущество ядра над фиксированной последовательностью по качеству не показано. Практический результат — одна команда различает несколько видов задач, а второй инструмент получает аргумент из проверенного наблюдения. Пять запусков полной CLI на основном примере с проверкой JSON заняли 682, 647, 663, 658 и 633 мс, медиана 658 мс. Время включает запуск Python и работника, чтение Git и выдачу ответа. Это замеры одного стенда.

### Сохранённые ошибки и границы

В первой версии `ba1c4de` вопрос об исходящих вызовах производителя ошибочно получил три утверждения о входящих вызовах. Строки были подлинными, направление ответа расходилось с вопросом. Во второй итерации разграничены грамматические роли; исходящие вызовы производителя получают явное ограничение. Запись ошибки и нераспознанная формулировка T5 сохранены. [Первый прогон](iteration1.json) · [Случай инверсии](direction.json)

Статический охват ограничен пятью файлами и поддерживаемыми возвратами словарей и прямыми вызовами. При нескольких производителях одинакового поля, неизвестном ключе или отсутствии доказанного вызывающего участка публикация удерживается. Смена HEAD проверяется перед зависимым шагом и при решении о выдаче. Исторический `eval_investigation.py verify` сравнивает с прежним отрицательным результатом T4 и поэтому сообщает о расхождении. Новая проверка повторяет все 15 задач: результаты 14 совпали с архивом, для T4 проверены оба вновь найденных звена. Исходный журнал Core 0.1 сохранён.

Регрессии статического чтения — 38/38, обзора изменений — 11/11, границ пакетов — 32/32, проверки адаптера включают шесть вопросов и десять контролей публикации, доступа и отмены. Полномочия, голосовой runtime и Developer Tasks UI сохранили прежние границы. Настоящий файловый symlink остаётся **UNVERIFIED**. Выполнены две инженерные итерации и ноль генераций локальной модели. Способность к самостоятельному интеллектуальному планированию здесь не измерялась.
