# Качество объяснений на достаточном контексте

Две итерации дали **0 из 2** полных выданных ответов каждая. В исходном CLI результат тоже **0 из 2**. Во второй итерации появился содержательный межфайловой черновик, который проверяющий компонент удержал. Отдельный контрольный набор K1–K4 остался неиспользованным. Поиск не изменялся.

## Сравнение

Все три прогона читали одни и те же Git-блобы из `ff52dff`. Вопросы, необходимые факты, диапазоны oracle и порог перехода к CLI зафиксированы в коммите `7da41f7`. Оценка ниже выполнена вручную по этим фактам и исходникам. Для каждого вопроса в JSONL сохранены точный ввод каждого вызова, исходный вывод, решение программы, время и идентичность модели. Во всех восьми вызовах Qwen3-8B-Q4_K_M завершила генерацию с причиной `stop`. Максимум фактически использованных выходных токенов — 247 при лимите 448. [Контроль и критерии](control.json)

| Вариант | O1, обработка двух видов файлов | O2, поиск Git на Unix и передача пути | Полных выдано | Генераций |
|---|---|---|---:|---:|
| Исходный | Удержан, 15,67 с | Опубликован неполный с ошибкой, 1,40 с | 0/2 | 2 |
| Итерация 1, короткие блоки и повторная оценка | Удержан, 15,64 с | Опубликован неполный, 2,09 с | 0/2 | 3 |
| Итерация 2, более длинные блоки и оценка пропусков | Удержан, 13,61 с | Удержан, 2,35 с | 0/2 | 3 |

O1 был первым вызовом новой сессии. Время запуска провайдера составило соответственно 14,44, 13,39 и 13,14 с. Для O2 модель уже была загружена. По одному замеру на ячейку.

**Исходный CLI.** В O1 модель различила две причины пропуска, но поместила семь ссылок в одно утверждение при разрешённых трёх. Текст также не назвал оба счётчика. В O2 утверждение об отсутствии читателя сослалось на создание списка путей вместо ветви в вызывающем файле. Объяснение перепутало условие использования переданного аргумента и пропустило возврат абсолютного пути. Проверка буквальных строк прошла. Аналогичный разрыв уже виден в V1 предыдущего checkpoint: ссылка на вызов `cat-file` не доказывала членство команды в списке разрешённых. [Прогон baseline](oracle_baseline.jsonl) · [Предыдущий разбор](../code_reader/README.md)

**Итерация 1.** Qwen выбирала короткие смежные блоки. CLI сверял их строки с Git, после чего отдельный вызов той же модели оценивал полноту и подтверждение утверждений по выбранным блокам. В O1 JSON содержал escape нулевого символа в тексте. После декодирования такой текст не прошёл проверку печатных символов. В O2 модель назвала обёртку поиска и конструктор, но пропустила `shutil.which`, проверку файла и преобразование пути. Рецензент видел только процитированные блоки и выставил всем трём выводам `true`, полноте также `true`. [Первый эксперимент](oracle_blocks.jsonl)

**Итерация 2.** Для чтения ветвей в исходной последовательности смежные строки группировались до 12 строк с границами на объявлениях функций и классов. Генератору предложено раскрывать вызовы до конкретных операций. Рецензент получал все процитированные блоки и остальные показанные фрагменты в пределах бюджета, с отдельным полем для пропуска. В O1 Qwen вернула одновременно `claims` и `missing` с единственной фразой про нулевой байт. В O2 она описала поиск через `shutil.which`, возврат абсолютного пути и его передачу в конструктор. Проверка обычного файла выражена лишь словами «если он найден». Рецензент поставил три положительных оценки и `complete: true`, одновременно назвав пропуском отсутствие типа `Path`. Этот тип не входил в зафиксированные требования. По правилу обработки противоречий публикация была удержана. [Второй эксперимент](oracle_final.jsonl) · [Проверка и возврат пути в Git](https://github.com/Daystat-debug/SkynetVS/blob/ff52dff713e772b9f8b03b0ca9e8a9a021ad998e/modules/developer_task_ui/app/git_source.py#L32-L39) · [Вызов в поиске](https://github.com/Daystat-debug/SkynetVS/blob/ff52dff713e772b9f8b03b0ca9e8a9a021ad998e/modules/developer_task_ui/app/context_search.py#L147-L150)

Оба oracle-вопроса имели достаточный контекст. Доля удержаний на них составила 1/2, 1/2 и 2/2. Ни в одной версии межфайловой ответ не прошёл заранее заданный критерий. Независимая точность CLI, корректность отказов на K и прирост качества поиска в этом эксперименте не измерялись. Два вопроса выявляют конкретные ошибки генерации и рецензирования, но не устанавливают предел возможностей Qwen3-8B.

## Запуск и воспроизведение

Из корня проекта в прежнем локальном окружении с проверяемым комплектом M289:

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/skynet_explain.py
.\.venv\Scripts\python.exe -I -S -B tools/skynet_explain.py --review
```

По умолчанию доступен принятый однопроходный CLI с явной пометкой об уровне проверки. Опция `--review` включает последнюю экспериментальную версию, до двух генераций на вопрос. Оба режима принимают также один вопрос аргументом. В экспериментальном режиме Git-ссылки ведут на диапазоны, показанные модели. Успешная повторная оценка остаётся мнением той же модели.

Проверки без генерации:

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/test_skynet_explain.py
.\.venv\Scripts\python.exe -B -m tools.eval_package_boundaries
$logs = (Get-ChildItem docs/maintenance/explanation_quality/oracle_*.jsonl).FullName
.\.venv\Scripts\python.exe -I -S -B tools/eval_explanation_quality.py verify @logs
```

Прошли целевые проверки, в том числе отклонение неизвестного блока, неподкреплённого вывода, пропуска и противоречивого вердикта, 15 штатных проверок цитат, 32 архитектурные проверки и сверка трёх трасс. Отдельный запуск CLI с `--review` на вопросе вне области дал отказ до вызова модели.

Для нового измерения oracle используется `tools/eval_explanation_quality.py oracle baseline <новый.jsonl>` либо `oracle reviewed <новый.jsonl>` с теми же флагами Python. Первый вариант эксперимента воспроизводится на `7f52868`, второй — на коммите этого отчёта. Драйвер создаёт временную копию зафиксированного репозитория, проверяет происхождение Git-ссылок и отказывается перезаписывать существующий журнал. Повтор потребует новых генераций.

Если выделять следующий бюджет, первым сравнением стоит проверить другой доступный локальный генератор на точно таком же достаточном контексте и с новой ручной оценкой конечных ответов. Это позволит отделить ошибки конкретной модели от ошибок схемы подтверждения перед дальнейшей работой над поиском.
