# Core 0.3. Как аргумент доходит до другой функции

Из корня проекта на Windows с установленным комплектом M289:

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/skynet_investigate.py "Какое выражение из search_repository доходит до rank_title_only.title?"
.\.venv\Scripts\python.exe -I -S -B tools/eval_argument_flow.py verify
.\.venv\Scripts\python.exe -I -S -B tools/eval_investigation.py verify
```

В первом примере аргументом служит выражение `effective` внутри `search_repository`. Оно передаётся в `rank.title`; затем `rank` передаёт своё `title` в `rank_title_only.title`. В JSON доступны поисковые шаги, полный SHA снимка и канонические ссылки каждого утверждения. [Первый вызов](https://github.com/Daystat-debug/SkynetVS/blob/1836acd4cf0f12900c007904e21b4a6ff0b6b5d3/modules/developer_task_ui/app/context_search.py#L153) · [Второй вызов](https://github.com/Daystat-debug/SkynetVS/blob/1836acd4cf0f12900c007904e21b4a6ff0b6b5d3/modules/developer_task_ui/app/retrieval/m130_rank.py#L116)

## Что определяет следующий шаг

Цель поиска — один подтверждённый пример передачи из выражения в заданной функции. Задача разбивается на подцели вида «какое место передаёт этот формальный параметр в данное определение?». Для каждого шага `calls.lookup` разрешает вызов, хост проверяет его точные координаты в AST, определение, ссылки и межфайловый импорт. Сигнатура связывает позиционный или именованный аргумент с формальным параметром. Если промежуточный вызов передаёт простое локальное имя, `flow.assigned` может подтвердить присваивание из другого имени. Каждое такое присваивание получает собственную ссылку.

Если выражение принадлежит указанной исходной функции, найдено свидетельство. Если промежуточное имя ведёт к параметру вызывающей функции, в очередь добавляется новая пара «функция, параметр». Вычисление нового выражения, переприсваивание или пропущенный аргумент останавливают эту ветвь. Остальные допустимые ветви остаются в очереди. Подтверждённые места вызовов переиспользуются в пределах одной задачи. Так на отрицательном P3 вызов `modules_from_source(path,src)` найден, однако локальная переменная цикла `path` не подтверждает передачу параметра из `rank`. Ответ удержан. [Место использования](https://github.com/Daystat-debug/SkynetVS/blob/1836acd4cf0f12900c007904e21b4a6ff0b6b5d3/modules/developer_task_ui/app/retrieval/m130_rank.py#L67-L69) · [Реализация](../../../tools/skynet_argument_flow.py)

Планировщик детерминированный. Он выбирает и пересматривает подцели передачи аргумента по наблюдениям. Интерпретация русского вопроса остаётся ограниченной. Для нового маршрута нужны имя исходной функции и назначение в форме `функция.параметр`. Результат описывает синтаксическую передачу при достижении указанных мест. Выполнимость всей цепочки на определённом входе, неизменность содержимого переданного объекта и фактическое значение на ПК отдельно не проверяются.

## Качество на новых задачах

Протокол зафиксирован в `e126554`, реализация — в `072ce0f`. Реальные вопросы, эталоны и первый случайный seed закреплены в `0d1b175` после реализации и до прогона. После первого измерения добавлена отдельная серия, где несколько ветвей проходят локальную проверку. Её условия и второй seed зафиксированы в `2cb561a` перед запуском; код Core остался тем же. Это проверка переноса внутри одного проекта, без внешнего независимого оценщика. [Протокол](protocol.md) · [Первый набор](transfer.json) · [Дополнительный набор](branching.json)

У простых альтернатив есть преимущество на этапе понимания языка: оценщик передаёт им правильно разобранную цель. Доступ к исходникам, установление связывания аргументов, проверка ссылок и лимит в шесть обращений к поиску вызовов одинаковы. На P9 («Чем main снабжает параметр rank_title_only.title?») CLI запросил лишнее уточнение. На неизменённом коде превосходство над альтернативами не показано. Из 26 положительных задач Core 0.3 решил 25, из шести отрицательных удержал все шесть по требуемой причине. Из 32 решений Core 0.2 балл получил только запрос уточнения при неизвестной функции.

При разветвлении перебор исчерпал шесть поисков в G09, G11 и G12. Во второй серии ранняя проверка с выбором только одной ветви упустила B01, B05, B07 и B08. В B08 Core 0.3 потребовалось пять поисков, включая проверку альтернатив. Серии специально испытывают разные причины потерь; распределение таких графов в повседневных проектах не измерялось. ## Ресурсы и регрессии

В совместном прогоне медиана на уже открытом снимке составила 129 мс для Core 0.3, 134 мс для перебора с кешем и 125 мс для выбора одной ветви. За 32 задачи этим вариантам потребовалось соответственно 59, 88 и 55 поисков вызовов. Время включает проверку и принятие ответа, исключая внешнюю сверку оценщиком. Пять отдельных запусков полной CLI для первого примера заняли 714, 700, 684, 681 и 761 мс, медиана 700 мс. Локальных генераций — 0. Сохранились пять разрешённых файлов, внешний дедлайн 25 с, привязка к Git HEAD и лимит в 96 уникальных ссылок для данного поиска.

Дополнительно проверены удержания при бюджете в один шаг, запросе вне области, вопросе о живом запуске, подмене другим действительным определением, изменённой ссылке, смене HEAD и ошибке инструмента. Реальный файловый symlink по-прежнему **UNVERIFIED**.

Команда `eval_investigation.py verify` снова проходит: берёт архив из принятого Git-коммита 0.1, сравнивает 14 неизменившихся результатов и отдельно проверяет исправленный T4 по исходной рубрике с проверенными звеньями. Исходные результаты сохранены. Проверка 0.2 использует ту же функцию сравнения. Результаты 0.2 воспроизведены, включая её прежний неуспех T5 (26/27). Проверки статического чтения — 38/38, обзора изменений — 11/11, границ пакетов — 32/32.
