# M289. Конечное качество ответов Cognitive Core V2

**Полного ответа на новом наборе не дал ни один вариант.** В лучшем по частичному покрытию варианте C пользователь получил два из двенадцати необходимых фактов. Оба относятся к одной функции в одном вопросе. Результат не обосновывает внедрение в продукт.

Начальное чистое дерево — `79f4855be3254700227cc2cc4406e4f6693a6667`. [Восемь вопросов, ключ, правила остановки и оценки](control.json) закреплены в `3bad899e5ddbce09f0e473039e1d62206fc809b3` до реализации. Исходники читаются из отдельного Git-снимка `e67c9ad013f4fa451046b9c461e8f055db8beaaf`. В наборе пять отвечаемых вопросов (три многофайловых) и три контроля. Только вопрос и тип static/live подаются в контур. Эталоны и номера опорных строк доступны оценщику.

## Сравнение

O — исходный M289. A — последний принятый эксперимент с русским поиском и многофрагментной сборкой. В B сначала локальная Qwen видит вопрос и сгенерированный по трём разрешённым файлам каталог имён функций. Она может вернуть до трёх частей с ID функции и лексическими подсказками или пустой план. Хост проверяет ID, ищет совпадающие строки внутри выбранного определения, выполняет штатную инспекцию и сборку, затем вызывает обычный M289 для ответа. В C те же план и сериализованный пользовательский запрос. Во втором подходе модель оформляет выводы с явными адресами строк; хост берёт буквальную цитату из указанной моделью строки и использует прежний валидатор. Такую цитату точно извлекает хост. Семантическую связь между ней и выводом отдельно проверял оценщик. [Код обоих подходов](../../../tools/m289_quality_route.py)

| Показатель | O | A | B | C |
|---|---:|---:|---:|---:|
| Полные ответы с подтверждёнными фактами | 0/5 | 0/5 | 0/5 | 0/5 |
| Полные многофайловые ответы | 0/3 | 0/3 | 0/3 | 0/3 |

| Удержания на контролях / адресные объяснения или уточнения | 3/3 · 0/3 | 3/3 · 0/3 | 3/3 · 0/3 | 3/3 · 0/3 |
| Медиана от вопроса до решения, включая отказы, с | 2,795 | 2,826 | 3,115 | 2,885 |
| Генерации ответа | 0 | 5 | 2 | 2 |

Семь общих вызовов планировщика учтены один раз в бюджете и полностью включены в задержку каждого из B и C. Всего 16 вызовов. Две проверенные гипотезы, два экспериментальных подхода, дополнительных итераций — ноль. Настройки всех генераций — та же Qwen3-8B-Q4_K_M, llama.cpp b11960 Vulkan, 37/37 слоёв на GPU, контекст 4096, seed 289, температура 0, максимум 448 токенов, отключён кэш промпта. Хеши пакета и установленной модели проверялись локально. Разовый захват снимка и построение каталога заняли 14,11 с, проверка и старт отдельных сессий — 6,39–16,39 с. Они исключены из медиан. Для T5, единственного вопроса с публикацией, C занял 6,08 с. Каждый вариант измерен один раз на вопрос. Порядок вариантов фиксирован, вывод о преимуществе по скорости по этим временам ненадёжен.

## Где произошли потери

- В O семь верхних кандидатов оказались вне разрешённой области, один запрос не дал совпадения. В A по всем пяти отвечаемым вопросам контекст дошёл до Qwen, и во всех пяти случаях модель вернула insufficient.
- На T1–T4 планировщик каждый раз указал ID 1 и 2, соответствующие `context_search._sha` и `expand_query`. Часть терминов местами содержала имена других функций. При повторном вычислении по тем же blob хотя бы одна часть каждого такого плана не имела даже лексического совпадения в выбранной функции. Сборка вернула пустые доказательства. Корректность формата плана и существование ID не обеспечили релевантности.
- На T5 в обоих вариантах переданы `context_search.py:47–54` и `m130_rank.py:22–23`. Второй диапазон относится к `candidate_id`. Для ответа нужна проверка в `rank` на строках 114–115. B сообщил предел в 1200 символов до расширения. C добавил правильный предел в 2500 байт UTF-8. Оба сослались на подлинную проверку расширенного текста в `context_search.py:52`; это не доказывает повторную проверку во втором файле. За требуемый третий факт балл не начислялся. Фраза C о 4096 байтах верна для стадии расширения, но не отвечает на вопрос о ранжировщике.
- На T6 предложена функция хеширования, хотя для ответа нужна статистика по пользователям за месяц. Генератор удержал ответ. На T7 маршрут остановился без живого наблюдения. На T8 отсутствовал объект, о котором задан вопрос. Планировщик всё же вернул ID, затем сборщик не нашёл опорной строки. Ни в одном из трёх случаев отображённое сообщение не объяснило пользователю, какие сведения следует предоставить.

Оценка выполнена одним рецензентом. Для разметки показывались опубликованный текст, ссылки, строки и цитаты под идентификаторами без названий вариантов. Одинаковые результаты дедуплицированы. Ход выполнения эксперимента был известен рецензенту; независимой слепой оценки не было. Отказ до генерации и отсутствие содержания не дают балла за отвечаемый вопрос. На контролях безопасное удержание и полезное объяснение подсчитаны отдельно. Утверждение о правильной стадии, подтверждённое строкой другой стадии, не засчитывается как доказанный требуемый факт. ## Воспроизведение

[Журнал](run.jsonl) хранит резервирование каждого вызова, сырой вывод Qwen, параметры и квитанции сессий, планы, пользовательский результат, канонические Git-ссылки и задержки. Для каждой переданной ссылки проверены commit, OID, SHA-256 файла и байты диапазона из Git. Пользовательский JSON реконструирован и сверен по SHA-256. Для B/C совпали хеши пользовательского ввода на всех восьми вопросах, включая отсутствие вызова. Число резервирований, завершений и запросов сервера совпало. Лимиты выдержаны, все сессии завершены. Пройдены 15 штатных проверок grounding, целевые проверки неизвестного ID и ссылки на чужую строку, архитектурные границы 32/32.

Подсчёт результатов из готового журнала не вызывает модель:

```powershell
.\.venv\Scripts\python.exe -B tools/review_m289_answer_quality.py docs/maintenance/m289_answer_quality --scores
```

Для отдельного будущего повтора на исходном Windows-стенде с локальными закреплёнными артефактами используется новое имя файла. Эта команда расходует генерации:

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/eval_m289_answer_quality.py new-run.jsonl
```

**Решение на checkpoint.** По основному критерию победителя нет. C даёт небольшой прирост частичной полноты, недостаточный для дальнейшей настройки на этом наборе. Следующая предложенная проверка — на отдельном наборе поручить модели выбирать из короткого списка проверенных фрагментов с видимым кодом и местом вызова между файлами. Измерять следует правильный выбор обеих опор до расходования генераций на формулирование ответа.
