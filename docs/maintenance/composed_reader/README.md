# Составные вопросы по исходному коду

Запустите диалог из корня экспериментальной ветки в установленном окружении SkynetVS:

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/skynet_explain.py --compose
```

Можно сразу передать вопрос:

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/skynet_explain.py --compose "Кто вызывает rank, куда записывает результат и как число функций-кандидатов попадает в итоговый отчёт?"
```

**Ответ по существу.** В `search_repository` результат `rank(effective, sources)` сохраняется в `base`. Поле `base['function_candidates_total']` становится `candidate_functions` в отчёте. Внутри `rank` значение взято из `sym['symbol_candidates']`, где `sym` получен от `rank_symbols`. Реализация поставщика за пределами трёх разрешённых файлов. Есть второй вызов `rank` из `main`, где результат сохраняется в `out`; для этого вызова связь с полем отчёта не установлена. `format_context` читает поле под подписью «функций», если ему передан этот отчёт. Фактическая передача экземпляра здесь не видна. [Вызов и построение отчёта](https://github.com/Daystat-debug/SkynetVS/blob/152412b/modules/developer_task_ui/app/context_search.py#L153-L167) · [Источник значения](https://github.com/Daystat-debug/SkynetVS/blob/152412b/modules/developer_task_ui/app/retrieval/m130_rank.py#L125-L135) · [Второй вызов](https://github.com/Daystat-debug/SkynetVS/blob/152412b/modules/developer_task_ui/app/retrieval/m130_rank.py#L144-L152) · [Чтение поля](https://github.com/Daystat-debug/SkynetVS/blob/152412b/modules/developer_task_ui/app/context_search.py#L211)

## Как устанавливается связь

Отдельный флаг сохраняет согласованное поведение одиночного `--auto`, включая прежние уточнения. В `--compose` сначала разрешаются все запрошенные цели. Вопрос о переменной, куда присвоен результат, уже входит в разбор прямого вызова. Для вопроса о происхождении поля запускается трассировка от поля к источнику. В диалоге ответ на уточнение одной цели сохраняет остальные части вопроса.

Поиск вызовов и трассировка независимо фиксируют commit, путь, строки и столбцы выражения вызова, а также путь и позицию разрешённого определения. Связь прикрепляется только к тому месту вызова, которое встретилось на обратном пути от выбранного поля. В журнале сохранены координаты совпадения, фактическая последовательность инструментов, вывод CLI и сверяемые диапазоны Git. Если цели разрешены, но доказанного перехода нет, CLI сообщает доступные факты по обеим частям и границу доказательства. [Реализация](../../../tools/skynet_compose.py)

## Проверка конечных ответов

Пример D оценивался отдельно от десяти новых вопросов C1–C10. Рубрика зафиксирована в `0b55f75`, исходники — `152412b`, измеряемый код — `e8a73a3`. Каждый вопрос предъявлен и прежнему `--auto`, и новому режиму на одинаковых Git-блобах. Проверка включала ручную сверку утверждений с рубрикой и кодом. | C8–C10 | До запуска инструментов получены отказ по внешнему файлу, запрос данных реального запуска и уточнение для неподдерживаемой оптимизации. |

На новых двухинструментных вопросах **C1–C5 прежний режим решил обе части в 0/5 случаев, новый выполнил обе части в 5/5**. По глубине результата: одна полная статическая цепочка (C1), две цепочки до установленной границы (C2, C4), два разбора с обоснованным отсутствием связи (C3, C5). Подтверждены **3/3 ожидаемые связи**, ложных связей в этих пяти ответах при ручной сверке — **0**. В C6–C10 и в дополнительном диалоговом ходе действия совпали с рубрикой. Считать все эти случаи полными трассировками было бы неправильно.

На D и C1–C10 сверены **67/67** показанных ссылок (28 различных диапазонов); в диалоге — ещё **18/18**. Проверены commit, blob, байты диапазона, SHA-256 файла и фрагмента, URL в выводе и существование указанных узлов AST в сохранённом снимке. Время нового режима на C1–C5 после открытия снимка — 0,246–0,301 с на вопрос. По одному замеру с инструментацией. Две итерации, **0/12 генераций**, провайдер не запускался.

## Ошибки и границы

Первая реализация `c0d5550` ошиблась на записи `data = get(9); data['score'] = 555`: прежний анализ присваиваний смотрел только на номера строк и связывал позднее чтение поля с результатом вызова. Во второй итерации проверка учитывает позицию операции внутри строки. Отдельный контрпример с двумя вызовами одной функции на одной строке подтверждает, что связь получает только нужный вызов. [Журнал ошибки](development.txt) · [Воспроизводимые проверки](../../../tools/test_composed_reader.py)

Сценарий ограничен возможностями двух статических читателей: прямые разрешимые вызовы функций верхнего уровня, поддерживаемые поля и пути возврата в трёх файлах. Перефразировки, вложенные условия и неоднозначные местоимения могут потребовать уточнения. Разбор ограничен восемью короткими частями. Набор проверяет статические пути на одном снимке и не измеряет поведение программы в конкретном запуске.

Помимо контролируемых и архитектурных тестов проверено совпадение прежних структурированных ответов со ссылками: 4/4 для `--calls`, 8/8 для `--flow`, 15/15 и 12/12 на двух сериях `--auto`, плюс оба прежних диалога.
