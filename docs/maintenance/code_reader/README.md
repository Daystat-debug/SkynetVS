# Локальные вопросы по коду SkynetVS

Экспериментальный CLI читает три разрешённых файла из Git HEAD и даёт локальной Qwen пронумерованные фрагменты. Для каждого опубликованного вывода он печатает ссылки на строки конкретного коммита. На свежих проверках он нашёл нужные строки в обоих случаях, но не дал ни одного полностью правильного и подтверждённого ответа. Результат стоит использовать как средство навигации с ручной проверкой объяснения.

## Запуск на подготовленном Windows-стенде

Из корня проекта:

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/skynet_explain.py
```

Введите вопрос по-русски. Для выхода введите `/exit`. Можно задать один вопрос сразу:

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/skynet_explain.py "Что происходит с процессом, когда вывод превышает ограничение?"
```

При запуске CLI показывает текущий commit и область чтения: `app/context_search.py`, `app/git_source.py` и `app/retrieval/m130_rank.py` внутри Developer Tasks UI. Учитываются только зафиксированные в Git версии. Ссылки указывают на GitHub; если commit пока только локальный, строки можно проверить командой `git show <SHA>:<путь>`. При смене HEAD требуется перезапуск. На обычный вопрос приходится до одной генерации; установленный провайдер допускает 16 за сессию.

Нужны имеющиеся Python проекта, исходный launcher и установленный пакет пилота M289, проверяемый комплект Developer Tasks UI и локальная Qwen3-8B-Q4_K_M с верифицируемым llama.cpp b11960 Vulkan на поддержанном стенде. Программа не устанавливает эти зависимости. CLI выбран, чтобы дать обычную точку входа без изменения комплекта UI и голосового runtime. Изолированные флаги Python не являются песочницей ОС.

## Как формируется ответ

[Поиск](../../../tools/skynet_source_windows.py) сопоставляет слова, части идентификаторов, числа и префиксы русских слов со строками трёх Git-источников. Редкие совпадения весят больше. Найденные места дополняются окрестностями вызовов и определений в других файлах, когда имя цели единственно среди разрешённых функций. Такая связь по имени — кандидат для анализа, а не доказательство динамической диспетчеризации. Вопрос и фактический код передаются модели за один вызов с пределом 9600 байт на вход. Это замена прежнего пути с несколькими обращениями, а не увеличение полномочий.

[CLI](../../../tools/skynet_explain.py) не исполняет анализируемый код. Для каждой ссылки он проверяет допустимый путь, commit, тип и OID Git blob, SHA-256 файла и цитируемой строки, принадлежность строки предъявленному контексту и состояние HEAD перед выдачей. Окончательный текст проходит штатную проверку M289. Подлинная строка может не доказывать утверждение. Проверены отказ при запросе к main.py и остановка при подмене OID или смене HEAD.

## Что измерено

Базовая линия — предыдущий вариант C (commit `cab517f`). Для сравнения использован один закреплённый снимок `e67c9ad`. Драйвер сверил все три blob с текущей веткой; обычный CLI читает HEAD рабочего проекта. Все генерации выполнены локально с прежними параметрами. Успех требует не только ссылок, но и правильного текста по всем пунктам рубрики.

1. Первый CLI просил указать номера строк каждого файла и затем сформировать ответ. На отдельном вопросе о таймауте он удержал ответ (4 генерации). Дополнительный замер одного файла (1 генерация) вернул строки 94, 97, 100–103; строки с остановкой процесса и повторным ожиданием не были непосредственно выбраны.
2. Версия `c69989b` извлекала буквальные цитаты и частичные объяснения отдельно по каждому файлу. На заранее закреплённых [U1–U4](holdout.json) она и базовая линия удержали все четыре ответа: полных 0/3, многофайловых 0/2, отрицательный случай удержан 1/1. Пояснение к U4 осталось общим. В U3 модель нашла нужный вызов, но добавила неподходящие счётчики из другого файла. В U4 один промежуточный вывод приписал main.py историческую частоту пропусков; пользователю он не был опубликован. [Сырые данные версии с цитатами](cli.jsonl) · [Базовая линия](baseline.jsonl)
3. Финальная версия `5a9e719` использует детерминированный поиск и один ответ Qwen без промежуточных пересказов. U1 и U3 использованы для регрессии. Ещё до этой правки закреплены два [новых вопроса V](final_holdout.json). После предъявления V алгоритм не менялся. По журналу входных строк все эталонные опоры U1, U3, V1 и V2 дошли до модели. [Ответы, выбранные строки и время](final.jsonl)

| Случай финального CLI | Фактический результат |
|---|---|
| U1, два файла, регрессия | Ответ удержан. Нужны были A:75,78–80 и B:65. Они присутствовали, но модель также сослалась на отсутствующие A:55 и A:56. |
| U3, один файл, регрессия | Опубликован ответ «каждые 40 файлов» с текущим и общим счётчиками. Ссылка на строку 134 подтверждает счётчики. Опущено условие наличия обработчика уведомлений, не процитирована строка 133 с проверкой кратности. |
| V1, два файла, свежий | Модель указала аргумент blob и дала ссылки на чтение и запрос размера. Она ошибочно объяснила разрешение команды этим аргументом. Приведённая строка 141 в git_source.py — ещё один вызов. Проверку списка разрешённых команд на строке 60 модель получила, но не использовала. |
| V2, один файл, свежий | Строки 79–80 верно подкрепляют запись ошибки и остановку процесса. Модель сообщила о прекращении чтения, но не объяснила прямо, что очередной блок не добавляется. Ещё одно утверждение о регистрации ошибки сослалось на строки 103–104, которые сами этого не доказывают. |

Итого на V опубликовано 2/2, полностью и с достаточными ссылками отвечено **0/2**, многофайловых **0/1**. На общем регрессионном поднаборе U1/U3 финальный CLI опубликовал 1/2, базовая линия — 0/2; полных ответов 0/2 у обоих. Базовая линия на V не запускалась. Финальный CLI на историческом отрицательном U4 не измерялся. Время финального варианта: U1 — 8,68 с, включая запуск модели 6,55 с; U3 — 2,20 с, V1 — 0,98 с, V2 — 1,73 с. Каждое время измерено один раз.

**Бюджет исчерпан:** 4 + 1 на разработку, 16 на U для второй версии, 5 для baseline, 4 для финального сравнения = **30 генераций**, три итерации. Гипотеза о том, что одна лишь доставка правильных строк даст полноценный ответ, на V не подтвердилась. Ближайший предмет отдельной проверки — умеет ли модель отличать место вызова от места принятия решения и привязывать каждую часть объяснения к доказывающей её строке.

## Проверка

Без обращения к модели:

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/test_skynet_explain.py
.\.venv\Scripts\python.exe -B -m tools.eval_package_boundaries
```

Целевые проверки покрывают выбор строк, ложный адрес, подмену blob, смену HEAD, предел входа и межфайловую связь на контролируемом примере. Прошли все 15 штатных проверок grounding и 32/32 проверок архитектурных границ. Отдельно проверен диалоговый запуск из рабочей ветки с отказом по внешнему пути без вызова модели.

Для будущего повторения сравнений [драйвер](../../../tools/eval_skynet_explain.py) принимает `baseline`, `cli` (версия с цитатами) или `final` и новое имя файла JSONL. Такой повтор тратит генерации.
