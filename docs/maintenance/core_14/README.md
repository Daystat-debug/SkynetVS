# Cognitive Core 0.14. Привязка смысла запроса к доказательству

На 21 новой задаче Core 0.14 дал столько же полных ответов, сколько 0.13-offline, — пять. Ошибочных объявлений полноты стало меньше, но выросло число полных отказов. В контрольных парах с одним и тем же объектом обе версии прошли 2 из 8. Оснований заменить 0.13-offline новым вариантом нет.

## Что связывает ядро

Хост сохраняет исходный текст каждой части и его смещения. Разрешение объекта по-прежнему выдаёт Git-снимок, путь и AST-диапазон выражения, а при отсылке также идентификатор предшествующего упоминания. В 0.14 к той же части присоединяется `relation`. Поле `kind` задаёт непосредственно запрошенный вид ответа. Указатель `inherited_from` хранит, откуда взят общий предикат у сочинённого цитированного объекта. Эти две ссылки независимы. Например, второй объект может унаследовать просьбу назвать условие первого, сохранив своё собственное выражение, условие и строки кода.

Для классификации используется остаток формулировки после удаления цитаты и совпадающих с меткой объекта слов. Модель выбирает вид сведений либо указывает пробел. Порог и отрыв первого варианта калибруются на исторических данных. Один сохранённый источник по-прежнему может обслуживать несколько требований. Хост достраивает зависимости сбора. Для вопроса об аргументах это место выражения, вызывающая функция и привязка параметра к выражению вызова. Только последнее утверждение попадает в `direct`, остальные индексы — в `support`. На этапе публикации проверяются объект, требуемая цепочка типов, квитанции и проекция утверждений. Проверка подмены возвращает `claim_binding`, даже если злоумышленник поменял местами два индекса подлинных утверждений.

Повторное вычисление проекции проверяет внутреннюю согласованность. Если интерпретатор изначально спутал запрос аргумента с запросом вызывающей функции, хост может подтвердить правильный статический факт о вызове и ошибочно объявить задачу решённой. Это наблюдается в контрольном R3. Семантическую ошибку выявляет внешняя рубрика. ## Результаты

Объект оценивается по пути, функции и строке выбранного выражения. Тип оценивается отдельно по точному набору необходимых статических типов с зависимостями. «Совместно» требует обеих оценок на одной просьбе. «Факт» требует предъявленной строки и правильного содержимого конкретного условия, вызова или передачи значения. Ссылки проверяются до свёртки в журнал. Полный ответ требует всех запрошенных фактов и корректного статуса. В полезном частичном ответе должны присутствовать все доступные факты и явно отмечаться недоступные части. Строгая оценка дополнительно требует правильного объяснения пробела. Для зачёта контраста обе задачи должны получить полный ответ с точным типом для каждого объекта. Один ответ может входить в две пересекающиеся пары.

## Где представление помогло и где потеряло смысл

- **K6.** На вопрос после двух сообщений о керне и ампуле 0.14 привязал «второй» к ампуле и предъявил именно `faded ← False` в вызове из `inspect_vial`. У 0.13-offline было ложное объявление полноты. В K4/K5 обе версии успешно меняют доказательства для обоих объектов при замене запроса вызывающей функции запросом условия.
- **R3 и исторический E4.** Вместо аргумента 0.14 выбирает вызывающую функцию. Ссылка верна, значение отсутствует. В историческом R2 новый вариант восстановил просьбу о вызывающем участке первой диагностики. В историческом E5 оставил пробел, но не распознал причину — требование внешнего адреса. Эти три случая участвовали в исторической калибровочной серии. [Отдельный диагностический повтор](history_results.json)
- **K1–K3, K9.** Обе версии теряют предмет вопроса при описании просушки керна без точной цитаты. Переход к другой модели типов не устраняет неоднозначный поиск объекта. В K7 сохранён корректный частичный ответ с указанием неоднозначности местоимения. В K8 новая версия сохранила неизвестное требование, но уступила прежней в точности причины.
- **Вторая серия.** В V1 версия 0.13-offline доставляет прямой вызов, а 0.14 удерживает ответ из-за низкой уверенности в смысле. В V2 тот же механизм удержания предотвращает ошибочную публикацию. В V3 ядро нашло оба объекта, но связало общий запрос вызывающей функции только со вторым. Общий предикат после группы объектов и отдельное предложение, вводящее тему, выходят за возможности переноса предиката с предыдущей части. В V4 не распознан запрос значений в точке вызова. На обеих новых сериях пороги после измерения сохранялись неизменными.

Архитектурно стоит сохранить различие между запрошенным и вспомогательным свидетельством. Для самостоятельного понимания задачи остаётся открытым построение отношения над всей группой упоминаний, включая расположенный после неё предикат и альтернативные трактовки вида ответа. На этих данных выбор наиболее похожей размеченной части недостаточен для такой операции. Переход на 0.14 по умолчанию не обоснован.
