# M289: разрешённая область до ранжирования

Проверяется одно изменение для экспериментального текстового explain_code. Верхний кандидат по всему репозиторию может быть недоступен пилоту даже тогда, когда в списке ниже есть подходящая разрешённая функция. В экспериментальном варианте прежний поиск получает пересечение уже проверенного снимка с теми же тремя путями M289 **до** выбора файлов и подсчёта BM25. Пустое пересечение возвращает пустой список. Запрос, словарь подсказок, порядок по баллам, положительный порог, размер выдачи, выбор одного верхнего представления, обрезка и проверка ссылок остаются штатными. [Адаптер](../../../tools/m289_scoped_retrieval.py) не использует ключи H/N и не читает новые файлы. Доступный снимок, получение commit/blob и остальные проверки остаются в исходном провайдере. Вариант подключён к реально исполняемому исследовательскому контуру; установленный комплект, голос и production не изменялись.

## Где исчезают десять вопросов

[Расширение русского запроса](../../../modules/developer_task_ui/app/context_search.py#L27) добавляет английские слова только по фиксированным подстрокам. Затем [токенизатор файлового поиска](../../../modules/developer_task_ui/app/retrieval/m126_rank.py#L20) извлекает ASCII-слова, дробит идентификаторы и отбрасывает числа, короткие части и stop-слова. Файловый балл >0 открывает второй шаг: [M130](../../../modules/developer_task_ui/app/retrieval/m130_rank.py#L110) выбирает до 10 файлов и ранжирует символы. В закреплённом пакете M289 `m254_runner.py:130–143` проверяет файловый сигнал и оставляет первые восемь функций с положительным баллом. `m254_core.py:271` инспектирует только первую. `retrieval284.py:133–147` требует совпадения выбранной функции с top-1 и отказывает, если её путь вне SCOPE.

| Случаи исходного H | Что именно произошло в базовой линии |
|---|---|
| H1 (1201 символ), H8 (список кандидатов), H9 (6 000 000), H11 (лимит), H12 (хеш) | Ни одна поисковая подсказка не добавила полезного токена. Кириллица и числа не стали токенами; во всех пяти случаях их список пуст, ни один файл не имеет положительного балла. Это NO_MATCH на файловой проверке, ещё до отбора положительных функций. |
| H3, H4, H10 | Вопросы о разных вещах превратились в одинаковые `file, document`. У всех один top-1: `developer_task_execution_boundary_composition_payload.py::_file_version@1023`. Файл вне области. |
| H6 | Остался `windows`; выиграл `developer_task_execution_backend_lifecycle_windows.py::build_windows_sandbox_environment@449`. Файл вне области; к тому же статический исходник не доказывает состояние микрофона. |
| H7 | Остался `head`. В порядке выдачи: `_require_current_head`, `GitHeadCatalog.verify_head`, `_render_current_head_labels`, `scan_head`. Верхняя функция находится в `developer_task_execution_environment_inventory.py`. Проверка SCOPE вернула OUT_OF_SCOPE без попытки взять третью или четвёртую. `scan_head` на четвёртом месте покрывает только одну сторону вопроса; `GitSourceReader._sha` в этой четвёрке отсутствует. |

## Протокол

Корпус: отдельный clone на `e67c9ad013f4fa451046b9c461e8f055db8beaaf`. [Базовые результаты](../m289_diagnostic/A.json) читаются из `d32683c`; для всех H повторное базовое измерение обязано точно воспроизвести прежние статус retrieval, список селекторов и хеш переданного промпта (включая отсутствие вызова). [Драйвер](../../../tools/eval_m289_scoped_retrieval.py) проверяет оригинальные байты пилота, синтетические положительный/отрицательный поиск, пустую область, отказ инспекции вне области и сохранность входного снимка.

[Новый набор N](holdout.json) закреплён в Git **до реализации и первого предъявления**: `72c214290cbcc9f87e526bf3ee433277b304d9bf`, blob `a5ffbe10b77bfedaca28fc8a3352ef35e3ab6d03`. Шесть отвечаемых вопросов (три однофайловых, три многофайловых), два контроля; встречаются как вопросы с именем из кода, так и без него. Он независим от подбора этого изменения, открыт и мал. Для обоих плеч ранжировщику подавался только дословный вопрос. Эталонные селекторы и номера строк использованы только оценщиком. Проверенный снимок прогрет один раз, сессии вопросов свежие, три парных повтора на вопрос с чередованием порядка. Время — от входа в штатный `answer` до отказа либо передачи сериализованного промпта на границе provider, без inference, расчёта метрик, загрузки весов и первичного чтения снимка. На границе выполнение останавливает измерительный зонд: гипотетически переданные строки измерены, ответ модели не генерировался.

Повтор: из корня проекта, Windows и исходный локальный пакет M289 — `.\.venv\Scripts\python.exe -I -S -B tools\eval_m289_scoped_retrieval.py <новый-файл.json>`. [Парные измерения](measurements.json) содержат токены, сигнал до ранжирования функций, исходные списки, позиции эталонов, привязанные к blob диапазоны, строки на входе provider и времена каждого прохода.

## Результаты

В таблице слева — исходный поиск, справа — поиск по разрешённым кандидатам. Для покрытия единица подсчёта — требуемая функция конкретного вопроса. Для контекста факт засчитан только при наличии **всех** его опорных строк в сериализованном запросе. Статусы и время включают контрольные вопросы.

| Показатель | H, регрессия (12) | N, новые вопросы (8) |
|---|---:|---:|
| Требуемые функции в top-1 | 0/10 → 0/10 | 0/9 → 2/9 |
| Требуемые функции в top-4 | 1/10 → 4/10 | 0/9 → 3/9 |
| NO_MATCH | 5/12 → 5/12 | 5/8 → 5/8 |
| OUT_OF_SCOPE | 5/12 → 0/12 | 2/8 → 0/8 |
| READY на этапе retrieval | 2/12 → 7/12 | 1/8 → 3/8 |
| Факты с полной опорой в контексте | 0/19 → 0/19 | 0/11 → 2/11 |
| Отвечаемые вопросы со всеми фактами в контексте | 0/6 → 0/6 | 0/6 → 1/6 |
| Многофайловые вопросы со всеми нужными функциями в top-4 | 0/3 → 0/3 | 0/3 → 1/3 |
| Многофайловые вопросы со всеми нужными файлами на входе модели | 0/3 → 0/3 | 0/3 → 0/3 |
| Задержка до отказа или входа в provider, мс | 2241,9 → 1807,5 | 611,3 → 182,4 |

Время — медиана по вопросам от медиан трёх проходов. Это измерение одного запуска на прогретом снимке; группы H и N выполнялись последовательно. Сравнивать следует два варианта внутри группы. Сверка с Git восстановила содержимое каждого переданного диапазона и SHA-256 сериализованных запросов. Все кандидаты экспериментального варианта принадлежат разрешённым путям.

**Что изменилось у конкретных вопросов.** У H3 в top-4 появились две из трёх нужных функций, у H4 — одна из одной. Обоим на вход всё равно передан фрагмент `receipt_without_source`. У H7 `scan_head` поднялась с четвёртого места на второе, но на первом осталась нерелевантная разрешённая `_render_current_head_labels`; ни один из четырёх фактов не дошёл. У H6 после снятия отказа на вход поступил фрагмент `module_rank`, который не содержит сведений о текущем состоянии микрофона. Поэтому рост READY на H сопровождается и передачей нерелевантного контекста.

На N2 релевантная `git_environment` поднялась с пятого места на первое, и её строки полностью покрыли вопрос. На многофайловом N4 обе функции попали в top-4 (`GitSourceReader._run` на первом, `scan_head` на третьем). На вход попал только первый фрагмент, покрыв один из двух фактов. На N6 обе функции остались ниже top-4. N1, N3, N5 и оба контроля N7, N8 сохранили NO_MATCH.

**Вывод.** Учёт разрешённой области до ранжирования устранил семь отказов по пути и улучшил покрытие кандидатов на обоих наборах. Прирост фактически доставленного контекста сосредоточен в двух новых вопросах. На регрессионном H прирост полноты контекста нулевой. Полный многофайловый контекст не доставлен ни разу. Результаты относятся к retrieval и подготовке контекста на закреплённом снимке. Качество генерации и решения о публикации в этом эксперименте не измерялись.
