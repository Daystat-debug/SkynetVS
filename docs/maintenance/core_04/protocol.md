# Core 0.4. Поиск от наблюдаемого результата

Исходный Core и снимок реального проекта — `dc7000c`. Практическая задача — объяснить диагностику по тексту сообщения или коду ошибки. Вопрос может содержать предполагаемую входную функцию. Имя функции, которая выдаёт диагностику, пользователю знать необязательно. Для составного вопроса нужен один доказанный статический путь от входа до места с нужным сообщением и локальное условие возникновения при достижении этого места. Фактическое выполнение, достижимость на конкретном входе и распространение исключения до пользователя находятся за границей утверждения.

До измерений фиксируем реализацию. Затем отдельным коммитом фиксируем новые русские вопросы к реальным пяти файлам, координаты и смысл ожидаемых утверждений. После этого открываем ответы инструментов. Дополнительно используем одноразовые Git-снимки с неизвестными до фиксации алгоритма именами, расположением нескольких источников одной диагностики и связями. Источник seed — первые восемь hex-цифр коммита реализации. Истинные связи задаёт генератор исходного текста. Повторную настройку по этим наборам не проводим.

Сравнения на одном снимке и вопросе:

- Принятый Core 0.3 с его обычным русским интерфейсом.
- Поиск литерала с тем же AST-извлечением места и условий. Для вопроса с указанным входом проверяет саму функцию и непосредственных вызывающих.
- Последовательная проверка возможных мест по одному с обходом в ширину и общим кешем проверенных вызовов. Имеет тот же разбор русского и тот же набор допустимых ссылок.
- Совместный поиск от возможных мест с пересмотром фронта на основании наблюдений. Расписание по глубине. При найденном свидетельстве возвращает один пример.

Общий предел новых режимов — одно обследование AST и до пяти запросов вызовов, до 96 уникальных доказательств и 25 с на вопрос. Измеряем полностью правильные конечные ответы, причины удержания, неподтверждённые и лишние утверждения, число шагов и время после открытия снимка. Отдельно замеряем обычную CLI. Для положительного ответа проверяем правильное место, сообщение, ветвь и полярность, все звенья в порядке от входа, определения, координаты вызовов и межфайловые импорты. Ссылки независимо сверяем по Git. Для отрицательного требуются пустые утверждения и причина из рубрики. Сохраняем ответы всех вариантов, включая ошибки. Сильная простая альтернатива может оказаться столь же хорошей или лучше.

Сохраняются исторические verify Core 0.1–0.3, пять разрешённых путей, проверка HEAD, защита публикации и отсутствие исполнения исследуемого Python. Для отдельных тестов используем временный Git-клон. Работы по NLU, HWA и M04 в эксперимент не входят.
