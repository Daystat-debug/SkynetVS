# Cognitive Core 0.13. Привязка требований к объектам программы

## Изменение в исследователе

В историческом A1 Core 0.12 распознал просьбы о двух вызывающих участках. В лексическом плане индекс цели обновлялся только при встрече цитаты. У обеих частей остались `target=0` и индексы утверждений `[0,1,2,3,4]`. Единственный поиск места идентифицировал насос. Проверка подлинности ссылок и типов фактов прошла также для просьбы о манометре. [Исторический результат](../core_12/results.json)

В экспериментальной версии 0.13 исходная часть вопроса хранит смещения в тексте, требуемые типы фактов и отдельную привязку `binding`. В ней указаны выражение, способ сопоставления, ссылка на предыдущее упоминание при наличии и причина пробела. Идентичность выражения задают Git commit, путь, функция и полный AST-диапазон выражения с байтовыми смещениями столбцов UTF-8. Две строки в одной функции и два выражения на одной строке могут быть разными целями. Хост объединяет сбор доказательств по идентичности выражения и возвращает каждой части только соответствующие типы утверждений. Данные существуют в рамках одного read-only запроса.

- Для каждой части хост сначала ищет самостоятельное соответствие по цитате или существующему поиску по описаниям кода. Для возврата к предыдущему объекту хост ведёт порядок упоминаний; простой указатель с единственным предшествующим объектом и порядковая ссылка разрешаются отдельно. Неопознанное прямое упоминание сохраняет своё место в порядке. Явная отсутствующая цитата оставляет пробел. Это ограниченный механизм отсылок в одном русском вопросе.
- При слабом лексическом соответствии Qwen может предложить идентификатор из ограниченного каталога разрешённых выражений. Меню чередует кандидатов для разных частей и ограничено 8000 байтами. Хост принимает только действительный номер из выданного меню. При отсутствии уникального общего термина в самой метке смысловое соответствие остаётся предварительным, и хост удерживает полный статус. Даже уникальный общий термин даёт лишь эвристическое подтверждение намерения пользователя.
- Другой вызов Qwen определяет виды требований по прежнему формату 0.10. Предложенный интерпретатором индекс цели не управляет сбором. Хост повторно вычисляет связи из исходного вопроса, своего каталога и принятых номинаций, проверяет владельца, выражение, строки, привязку к пути и типизированные доказательства. Подмена двух настоящих квитанций для разных выражений в одной функции блокируется тестом. Эта проверка обеспечивает согласованность с выбранным объектом; смысл ошибки первоначального выбора она восстановить не может. ## Протокол

Алгоритм закреплён в `ac4784d` до составления нового набора `59847e4`. Набор содержит 24 авторские задачи, из них 6 на реальных исходниках, 18 на трёх новых синтетических программах. Синтетические байты добавляются в Git-объекты только в изолированном временном клоне. Есть перестановки целей, два выражения в одной функции, два независимых предмета без цитат, разные требования к одному предмету, терминологические пересказы, неоднозначности и отсутствующие сведения. Для каждой просьбы заранее указаны текстовый ориентир, ожидаемая цель и тип доказательства. [Задачи, эталоны, источники и oracle](transfer.json)

1. **Известные требования.** Оценщик подставляет только типы требований для фактических сегментов вопроса. Для неизвестной цели, о которой спрашивают «кто вызывает», подаётся тип `caller`. В resolver не передаются метки объектов, номера предшественников, координаты или фрагменты источников из рубрики. Проверяются заново построенные привязки **и доставка** факта с правильной целью через настоящий хост. Смысловые номинации воспроизводятся из записей тех же вопросов по хешам запросов без новых генераций. Время этого прохода включает воспроизведение, поэтому напрямую сравниваются живые задержки полного пути.
2. **Полное исследование.** Сравниваются версии 0.10–0.12, поиск отдельно для каждой части, поиск с возвратом к последнему упоминанию, граф без Qwen и полный граф. Две простые стратегии используют тот же интерпретатор типов, ограниченный каталог и проверку реальных квитанций. Базовая стратегия oracle `parts_once` знает требуемые типы и использует последний явно цитированный ориентир. Модель и лимиты хоста общие. Задержка измерена на открытом снимке и загруженном provider; порядок запуска чередуется.
3. **Оценка.** Каждая требуемая статическая связь получает один из исходов: правильная доказанная цель, чужая цель или отсутствие привязанного свидетельства. Привязку проверяют по предъявленному `site`, функции, пути, тексту и покрытию эталонной строки. Отдельно проверяется запрошенное утверждение об условии, вызывающем коде или аргументах. Строгая полнота типов требует совпадения набора требуемых видов по частям с учётом их необходимых зависимостей. Частичный ответ полезен, если предъявлены все доступные факты и обозначены все недоступные просьбы. Строгий частичный требует также правильной причины каждого пробела. Ошибка привязки учитывается и при технически подлинной Git-ссылке. Архивные вопросы из 0.12 служат только для регрессии.

## Измерения и выбор вариантов

В первой серии было 46 проверяемых статических требований. При заданных типах привязка к последней цитате дала **30 правильных / 6 чужих / 10 пропущенных**. Поиск отдельно для каждой части дал 33/1/12, возврат к последнему объекту — 38/4/4, граф с явными отсылками — **40/1/5**. У графа было 13 полных ответов из 16 разрешимых и 5 полезных частичных из 6 смешанных. После включения самостоятельного определения типов эти числа упали до 8 и 3, появилась одна ложная полнота. Например, в R1 и R2 правильно выбрана первая из двух диагностик даже при перестановке, но интерпретатор дополнительно потребовал внешние сведения. В B2 модель предложила посторонний объект для продолжения о параметре; статус сопоставления остался предварительным. На A5 ни один из двух терминологических пересказов не привёл к подтверждённому ответу. [Все конечные и oracle-ответы первой серии](results.json)

На этих же 24 задачах граф без модели дал 11 полных и 5 полезных частичных, без ложной полноты. Core 0.12 дал 6 и 1 при семи ложных объявлениях. Архивный A1 воспроизвёл прежнюю ошибку. Обе формулировки A1/A2 в выпускаемом варианте правильно получили `supply_water → measure_tank` и `read_panel → read_gauge` без генерации. На всей регрессионной серии из 20 задач первоначальный вариант графа с модельным определением требований дал 4 полных и 6 полезных частичных против 2 и 5 у Core 0.12 по новой рубрике; чужих доказанных целей стало 0 вместо 2. При известных требованиях во второй серии вариант 0.13 правильно привязал и доказал 24 из 29 фактов, дал 8 полных и 3 полезных частичных без ложной полноты. Правило последней цитаты дало 21 правильную привязку, 3 чужих и 5 пропусков. В полном пути точный набор требований распознан в 11/16 задач у 0.13 и 0.13-offline, в 8/16 у Core 0.12 и у 0.13-model. Оба полезных частичных ответа 0.13 содержали правильные объяснения всех пробелов. На семи вопросах без цитат 0.13 дал 2 полезных ответа против 0 у Core 0.12. [Ответы, факты, оценки по каждой просьбе, шаги и время](confirmation_results.json)

**Что всё ещё приводит к ошибке.** Ноль чужих целей в таблице относится к требованиям, для которых в рубрике есть статический объект. В E5 система сочла адрес почтового отделения доказанным по строке о почтовом сборе: пересечение по одному слову в описании подтвердило не тот смысл просьбы. Вариант без модели оставил пробел. В R2 объект отсылки «первую» верен, но вместо вызывающей функции приведено условие. В E4 запрошены значения аргументов, а предъявлен вызов. Эти три ответа вошли в число ложно полных. В E3 семантический поиск нашёл место перегруза посылки по описанию бандероли, но соответствие осталось предварительным, а сообщение о неоплаченной пересылке потеряно. Безмодельный вариант дал на второй серии больше полезных конечных решений. Преимущество назначения Qwen в поиске для конечного качества не подтверждено.

Текущая единица представления — одно выражение на сегмент. Ошибка деления, неоднозначность местоимения и два требования к разным предметам внутри неразделённого текста остаются ограничениями. Git-ссылки построчные, а различение позиций внутри одной строки опирается на AST. Хост не заявляет, что выражение исполнялось. В сравнениях выполнено 130 живых генераций на первой серии, 33 на архивной и 53 на заключительной; oracle использует повтор ответов на идентичные запросы. Ещё одна генерация была сделана в предварительном запуске CLI. Итого **217**. Заключительный вариант 0.13 отдельно затратил 8945 входных и 92 выходных токена и выполнил 56 действий хоста на 16 задачах.

## Воспроизведение из корня SkynetVS

```powershell
$py = '.\.venv\Scripts\python.exe'
& $py -I -S -B tools/test_object_binding.py
& $py -I -S -B tools/eval_object_binding.py verify
& $py -I -S -B tools/eval_object_binding.py summary
& $py -I -S -B tools/eval_object_binding.py verify --history
& $py -I -S -B tools/eval_object_binding.py verify --final
& $py -I -S -B tools/eval_object_binding.py summary --final
& $py -I -S -B tools/skynet_investigate.py --requirements --requirements-version 0.13 'Укажи место «M134_GOAL_EMPTY_OR_TOO_LONG» и место «M134_EXPANDED_QUERY_TOO_LONG». Какое условие у первого?'
```

`verify` заново строит снимки, разрешает упоминания, собирает доказательства и сверяет ответы, оценки и модельные записи. Для живого повтора с локальным комплектом M289 используется `record --file НОВЫЙ_ПУТЬ.json`. Старый вызов без номера версии запускает 0.10. Runtime и полномочия на пять файлов прежние.
