# Navigation Integration & Architecture Migration 0.1

В `a21f9be` добавлены входы для разработчика из [README](../../../README.md) и [AGENTS.md](../../../AGENTS.md). Они ведут к десяти уже существующим карточкам исходников, границ и проверок. Описание задачи вводится по-русски. Навигатор сверяет адреса выбранной карточки с указанным Git-снимком. Текущее расписание работ находится в [реестре M01–M07](migrations.md).

### Поиск по описанию задачи

```powershell
.\.venv\Scripts\python.exe -I -S -B tools/navigation_lab/nav.py task "Где хранится состояние напоминаний?"
.\.venv\Scripts\python.exe -I -S -B tools/navigation_lab/nav.py topic
```

Первая команда выдаёт `modules/reminder_service.py`, `modules/reminder_repository.py` и `tools/eval_reminder_service.py`. Режим сопоставляет слова вопроса с ключом и описанием каждой карточки; не требует знания имени на диске. Совпадение только по общим словам вроде «проверить» отбрасывается. Если несколько карточек подтверждены разными предметными словами, пользователь видит выбор. При отсутствии совпадений остаётся меню. Такой поиск не определяет причину сбоя и не видит незакоммиченный код.

**Что измерено.** Первые семь вопросов зафиксированы в `1312202`. Первый вариант получил 4/7: например, отнёс вопрос о забытой просьбе к Cognitive Core по общему слову «проверить». Пять дополнительных вопросов зафиксированы в `d8f77c5` до изменения правила выбора. Итог — 5/7 на первой серии, 5/5 на дополнительной. Первым ответом получены нужная пара путей в 6/8 однозначных задач, правильный выбор областей в 2/2 составных и корректный отказ в 2/2 неподдержанных. Ошибочных одиночных маршрутов в этих 12 случаях не было. [Первый прогон](integration_initial.json) · [Первая серия](integration_cases.json) · [Дополнительная серия](integration_transfer.json) · [Ответы CLI и измерения](integration_results.json)

Оба варианта работали по одному SHA `ce6500f` и одинаковым карточкам. Для baseline использован код из принятого коммита. Там, где нужен оператор, проверяющий скрипт выбирает правильный ключ по рубрике. Время включает запуск Python и Git, представляет медиану суммарного времени команд по четырём повторам; время выбора человеком и фактические токены Astra/Codex недоступны.

Два ограничения проявились на практике. Для D3 («полномочия исполнителя») появился лишний вариант Developer Tasks из-за слова «разрешает»; выбор `topic actions` дал оба требуемых пути. Для D7 («помощник забыл просьбу позвонить завтра») система не распознала напоминание. В этом случае `task`, меню и выбор области стоили **трёх вызовов вместо двух**. Результаты показывают пользу как входа в известные подсистемы; переносить их на произвольное понимание задач нельзя.

Генератор `project_inventory.py` по умолчанию создаёт уникальный локальный файл в системном temp, явный `--out` работает как прежде. В чистой одноразовой копии проверены старый default, новый default и явный путь: содержимое совпадает побайтно. Новый default сохраняет чистое рабочее дерево. Содержание сгенерированных отчётов в Git не входит. [Проверка интеграции](../../../tools/navigation_lab/check_integration.py)

### Решение о физическом переносе

**M04 удержан.** Исходное дерево `ce6500f` сравнили с его одноразовой копией. В копии реализацию `modules/reminder_datetime_parser.py` с тем же blob `98238b4324f4328f8fe40b7c3463c7310ffe130e` поместили в `modules/reminders/datetime_parser.py`, перевели прямого production-потребителя и сохранили старый путь через фасад. В ветке по-прежнему лежит исходная реализация.

* У парсера только зависимости стандартной библиотеки. Он определяет две публичные функции (нормализация и разбор), два лимита и dataclass результата. Поиск импортов и имён по всему зафиксированному дереву обнаружил `modules/reminder_command_parser.py:9` и `tools/eval_reminder_datetime.py:11`. В коде NLU есть три вызова командного парсера: `modules/nlu.py:528`, `:695` и `:802`. Разбор запроса на создание напоминания вызывает парсер даты в `modules/reminder_command_parser.py:147`. Имя самого парсера в проверенных манифестах не найдено. [Парсер](../../../modules/reminder_datetime_parser.py) · [Прямой потребитель](../../../modules/reminder_command_parser.py) · [Проверка дат](../../../tools/eval_reminder_datetime.py)
* Обнаружена косвенная привязка: guest profile фиксирует blob `5d1cc573458e4687d355279e1dd94125057a1f31` для проверки дат и `18d76d83aebe098329edf1197233c3e07187e067` для проверки команд. Текстовый поиск только по имени production-файла пропускает эту зависимость. Обе проверки выполнялись без изменений. [Профиль](../../../modules/developer/developer_task_guest_profile_document.py)
* В исходном и пробном дереве 76/76 проверок напоминаний и 32/32 проверок границ. Все поля результатов разбора для 18 примеров дали один и тот же SHA-256. Импорт через старый путь в пробной копии даёт тот же объект класса, что и импорт через новый. Но `__module__` класса изменился. Результат старой версии читается пробной; после обратного переключения Python не может прочитать созданный новой версией `pickle` (`ModuleNotFoundError: modules.reminders`). Это воспроизведённая несовместимость формата Python. Использование такого формата в реальном хранилище напоминаний этим тестом не установлено.
* Независимый блокер — `tools/pipeline.py check`. На исходном дереве он остановился на седьмом шаге `Evaluate NLU`: 6 PASS, 1 FAIL, 96 NOT_RUN из 103. Все 124 поведенческих случая NLU прошли, но `data/intents.json` содержит четыре интента без ожидаемого примера в eval: `EXIT_SKYNETVS`, `OPEN_DEVELOPER_TASK`, `RESTART_SKYNETVS`, `START_LEARNING`. Пробный перенос и поставленный M01 воспроизвели ту же последовательность статусов и тот же список недостающих интентов. Поэтому целиком подтвердить штатный pipeline для M04 невозможно на этой базе. Поток с именем `full` выполняет операции с данными обучения и не заменяет `check`. [Проверка покрытия NLU](../../../tools/eval_nlu.py) · [Pipeline](../../../tools/pipeline.py) · [Протокол репетиции](reminder_move_results.json)

**Сколько Inventory нужно.** Для оценки этого листового переноса достаточно локальной карты напоминаний вместе с поиском потребителей, имён, blob и профилей **по всему Git-снимку**, адресными тестами и двусторонней проверкой старого API. Инвентаризация владельцев несвязанных пакетов не исправит ни NLU, ни имя сериализованного типа. Действующий раздел 2.1 roadmap требует полного Inventory V2 до физического переноса. Основание для узкого исключения можно оформить только для этого листа после исправления обоих блокеров, сохранения старого публичного пути, проверки внешних потребителей и успешного `pipeline check`. M03 остаётся открытым для доменной миграции. Перенос другого production-файла в обход общего отказа pipeline так же оставил бы 96 шагов непроверенными. [Roadmap, разделы 2.1–2.3](../../architecture/SKYNETVS_ARCHITECTURE_ROADMAP_V1.md)

### Проверка и откат

```powershell
$py = './.venv/Scripts/python.exe'
& $py -I -S -B tools/navigation_lab/check.py
& $py -I -S -B tools/navigation_lab/check_integration.py
& $py -I -S -B tools/navigation_lab/probe_reminder_move.py --pipeline
```

Для последней команды нужны проектное Python-окружение и существующая локальная NLU-модель `models/nlu_intent.joblib`. Она выполняет проверки в одноразовых checkout и печатает обезличенный JSON. Без `--pipeline` воспроизводятся доменные проверки, сравнение всех полей, сериализация и откат. В поставленной M01 также воспроизведены 10/10 проверок Navigation 0.1 и 32/32 проверок границ. Исторические `verify` Core 0.1–0.3 завершились успешно: прежние 15/15, 26/27 с известным пропуском T5, а у Core 0.3 — 8/9 на проекте, 14/14 на сгенерированных задачах и 9/9 на альтернативных ветвях. [Команды Core 0.3](../core_03/README.md)

Для отката функциональности M01 в экспериментальной ветке — `git revert a21f9be`. В одноразовой копии обратный diff проверяется сравнением Git tree с родителем этого коммита. Файлы исходных серий и диагностический отчёт можно оставить как историю. Для M04 откатывать production-файлы не требуется.
