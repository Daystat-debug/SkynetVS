### Машиночитаемый итог выполнения

Второй пакет добавляет типизированный `FlowResult`, функцию
`run_flow_result()` и необязательный параметр командной строки
`--summary-json NEW_FILE.json`. Целочисленные `run_flow()` и `run_step()`
сохраняют совместимое поведение. Без нового параметра JSON-файл не создаётся.

Консольная сводка и JSON формируются из одних результатов шагов. Формат JSON:
`kind=SKYNETVS_PIPELINE_RESULT_V1`, `schema_version=1`. Он содержит уникальный
`run_id`, имя потока `flow`, итог `status`, признак `all_steps_passed`,
совместимый `returncode`, счётчики `counts` и упорядоченный список `steps`.
Для каждого шага сохраняются его номер `index` (начиная с 1), имя, статус,
код завершения и короткий `reason_code`. Такой же код причины есть на уровне
потока; неизвестный или пустой поток получает `unknown_flow`, `FAIL` и код 2.
Полные команды, вывод дочерних процессов, окружение и пути журналов
в этот файл не копируются.

| Итог потока | Условие |
|---|---|
| `PASS` | Все шаги непустого известного потока получили `PASS` |
| `FAIL` | Есть ошибка шага либо запрошен неизвестный поток |
| `INCOMPLETE` | Ошибок нет, но есть пропущенные шаги |

`all_steps_passed` равен `true` только для `PASS`. Счётчики `PASS`, `FAIL`,
`SKIP`, `NOT_RUN` и `TOTAL` относятся к шагам, а не к отдельным тестовым
случаям внутри дочерних команд. После ошибки в сводке остаются и последующие
шаги со статусом `NOT_RUN`.

Например, следующий **фрагмент** результата означает неполное выполнение,
несмотря на нулевой код процесса:

```json
{
  "status": "INCOMPLETE",
  "all_steps_passed": false,
  "returncode": 0,
  "counts": {"PASS": 1, "FAIL": 0, "SKIP": 1, "NOT_RUN": 0, "TOTAL": 2}
}
```

При использовании JSON потребитель должен читать результат текущего запуска и
проверять поддерживаемую версию формата. Для принятия успешного запуска нужны вместе:
фактический код завершения CLI, равный 0, валидный JSON с `status=PASS` и
`all_steps_passed=true`. Поле `returncode` внутри JSON описывает результат
самого потока: после его завершения ещё возможна ошибка сохранения или закрытия
выходного файла, при которой CLI вернёт ненулевой код. Один лишь код процесса
0 не подтверждает полный успех, как и один лишь статус из файла. Отсутствующий,
пустой или некорректный JSON тоже не подтверждает успех.

Для каждого запуска нужен **новый путь** отчёта в существующем каталоге.
Относительный путь считается от корня проекта, как и путь текстового журнала.
Файл создаётся эксклюзивно до запуска шагов; существующий файл не
перезаписывается. Если создать файл нельзя или он совпадает с файлом журнала,
конвейер останавливается с ошибкой до запуска дочерних команд. Окончательный
JSON записывается после выполнения потока; при аварийном завершении файл
может остаться пустым или неполным. Ошибка записи отчёта даёт ненулевой код
завершения. Справка не создаёт отчёт и не запускает шаги.

`--no-log` отключает только текстовый журнал runner. Если одновременно задан
`--summary-json`, JSON всё равно записывается. Действия выбранного потока с
моделями, данными и другими файлами определяются его дочерними командами.
Создание JSON не делает такой поток проверкой без изменений.

### Просмотр действий до запуска потока

Третий пакет добавляет `--describe`. Этот режим показывает состав выбранного
потока, известные действия его команд, пути результатов по умолчанию и число
пока неразобранных шагов. Он не запускает дочерние команды, не импортирует
прикладные модули, не читает содержимое `.env`, моделей и пользовательских
журналов и не создаёт текстовый журнал или JSON-итог выполнения.

Например, из корня проекта можно посмотреть действия `full` или `train`:

```powershell
& '.\.venv\Scripts\python.exe' -I -S -B -X utf8 tools/pipeline.py full --describe
& '.\.venv\Scripts\python.exe' -I -S -B -X utf8 tools/pipeline.py train --describe
```

Это именно просмотр описания. Для программного использования доступна
`describe_flow()` со схемой `SKYNETVS_PIPELINE_DESCRIPTION_V1`, версией 1 и
`execution=NOT_RUN`. Она отличается от схемы результата выполнения:
успешный просмотр не означает, что проверки прошли или модель обучилась.

`--describe` нельзя совмещать с `--summary-json` или `--log-file`: такое
сочетание отклоняется до создания файлов. `--no-log` допустим, но для просмотра
не требуется. Неизвестный поток даёт ненулевой код без запуска команд.

Реестр описаний охватывает **14 точных команд по умолчанию**, разобранных по
исходникам и вызываемым функциям. В нём отмечены известные чтения исходников,
данных и конфигурации, вывод отчётов, изменение данных, загрузка, обучение и
запись модели, а также интерактивный ввод. `REVIEWED` означает наличие такого
описания для точной команды. Дополнительные аргументы, другой интерпретатор
или неизвестный скрипт дают `UNREVIEWED`.

Отсутствие тега записи не доказывает отсутствие всех побочных действий.
Описания относятся к известным действиям текущих команд по умолчанию;
они не заменяют разбор изменённого кода, не ограничивают выполнение и не
выдают разрешений. При обычном запуске отдельно учитываются журнал runner,
заказанный JSON и возможные служебные файлы Python, например `__pycache__`.
Режим просмотра не читает конфигурацию, чтобы вычислять фактические пути.

#### Фактические действия основных режимов

| Режим | Действия текущих команд по умолчанию |
|---|---|
| `audit` | Читает intents, шаблоны ответов и текст `modules/actions.py`, печатает результаты сопоставления. |
| `check` | Содержит 103 шага. В этом реестре разобраны 4, остальные 99 явно отмечаются `UNREVIEWED`; среди известных действий есть загрузка NLU-модели. |
| `analyze` | Пять шагов: отчёт истории, обновление correction memory, ещё два отчёта и проверка reply builder. Может изменять `data/learning/correction_memory.jsonl`. |
| `full` | Пять шагов: отчёт истории, обновление correction memory, два отчёта и экспорт кандидатов. Название не означает запуск всех проверок или обучение. |
| `promote` | Экспортирует кандидатов в `data/inbox_unlabeled.jsonl`, `data/learning/alias_suggestions.jsonl` и `data/learning/phrase_correction_suggestions.jsonl`. |
| `raw_inbox` | Экспортирует трудные случаи и кандидатов разрешения команд в `data/inbox_unlabeled.jsonl`. |
| `label` | Запрашивает разметку у пользователя, сохраняет `data/intents.json` и `data/inbox_labeled.jsonl`. Неразмеченный inbox используется как вход. |
| `train` | Читает intents и обязательный `data/nlu_training_recipe.json`, обучает классификатор и записывает активный `models/nlu_intent.joblib`. |
| `eval`, `nlu_diag`, `nlu_risk`, `nlu_risk_guard` | Читают данные и конфигурацию, могут загружать NLU-модель, выполняют предсказания и выводят результаты. Распознанные команды Actions не исполняются. |

`full` и `analyze` различаются последним шагом: у `full` это экспорт, у
`analyze` — проверка reply builder. Поэтому прежнее короткое описание
`full = analyze + promote` было неточным. Состав потоков в этом пакете сохранён.

У существующей реализации есть особенности, которые теперь отражены в
описаниях:

- До блока `learning_data_quality` повторное построение correction memory
  на той же истории снова увеличивало `seen_count` и обновляло время.
  Первый пакет нового блока ниже устраняет повторное прибавление агрегата;
  он не восстанавливает достоверность прежних накопленных значений.
- Оба экспортёра перезаписывают свои выходные файлы даже при нуле добавлений.
- `label` при пустом inbox или отсутствии новых элементов выходит раньше
  сохранения. Если сессия разметки уже началась, итоговое сохранение выполняется
  и после пропусков или команды выхода.
- `train` сохраняет активный joblib **до** последующего `quick_test`.
  Раздельного кандидата модели и допуска к замене здесь пока нет.
- Отчётные команды могут выводить фрагменты пользовательской истории.
  При обычном запуске runner сохраняет этот вывод в локальном текстовом журнале.

### Воспроизведённая ошибка

`FeedbackAnalyzer` возвращает количество найденных пар во всей прочитанной
истории, а прежний builder каждый раз передавал это количество в операцию
прибавления. Одна и та же пара после трёх запусков давала `seen_count=3`.
При добавлении второй настоящей пары следующий запуск давал уже 5.
Пороги отбора используют этот счётчик, поэтому повторный технический запуск
мог превратить один случай в якобы несколько подтверждений.

Вторая причина неточности — разные правила группировки: analyzer разделяет
текст по регистру и пробелам, а память нормализует его. Также обычный отчёт
показывает только десять наиболее частых пар, что не является полным снимком
данных для обновления памяти.

### Изменение первого пакета

Builder запрашивает все найденные correction pairs, объединяет их по тому же
нормализованному ключу, который использует память, и синхронизирует накопленные
количества для именованного источника. Обычный отчёт analyzer сохраняет
прежнее ограничение в десять пар.

Для нового кандидата сохраняется текущее количество. Для уже отслеживаемого
кандидата прибавляется только положительная разница относительно наибольшего
ранее обработанного количества этого источника. Повтор неизменного снимка
сохраняет счётчик, время и байты файла; отсутствующие пары не удаляются.
Прямой `upsert_candidate()` сохраняет прежний смысл прибавления отдельного
наблюдения и не используется builder для повторного импорта полного снимка.

Первое подключение нового механизма к старой записи сохраняет её накопленный
счётчик и время, а текущее количество запоминает как исходную отметку. Такой
переход не прибавляет всю историю второй раз. Прежние завышенные значения
не уменьшаются автоматически: их происхождение нельзя достоверно восстановить
из одного счётчика. Состояние кандидата и дополнительные поля сохраняются.

Пакет использует консервативную отметку наибольшего количества, а не уникальные
идентификаторы событий. Если историю сократить или заменить, меньшее количество
не сбрасывает отметку. Новые случаи после такой замены могут оставаться
неучтёнными, пока количество не превысит прежнее. Для полноценного учёта
редактирования и ротации истории нужен отдельный контракт происхождения событий;
этот пакет его не объявляет реализованным.

Новый путь синхронизации проверяет память перед изменением и сохраняет её
одной атомарной заменой подготовленного файла. Повреждённая запись памяти
не должна исчезать из-за молчаливого пропуска при чтении. Ошибка подготовки
или замены не должна обнулять исходный файл. Это не вводит транзакций между
параллельными процессами. Полная проверка качества исходной истории и правил
выделения correction pairs остаётся отдельной задачей.

### Проверка и применение

Регрессионный набор:

```powershell
& '.\.venv\Scripts\python.exe' -I -S -B -X utf8 tools/eval_correction_memory_idempotence.py
```

Он использует только собственные временные JSONL и синтетические события.
Проверки builder вызывают его на этих данных. Установка пакета запускает
регрессии и сохраняет отчёт, но не читает и не пересчитывает настоящие
`data/learning/command_history.jsonl` и `data/learning/correction_memory.jsonl`.
Обновление настоящей памяти произойдёт при отдельном обычном запуске builder
или потока, который его вызывает, уже с новой логикой.

Пакет включает обычные проверки границ пакетов и регрессии опубликованного
блока pipeline. Фактический Windows-результат будет записан в
`M154_CorrectionMemoryReplay_Result.json` и автоматически отправлен в
экспериментальную ветку вместе с кодом; `FAIL` также сохраняется в истории.
`maintenance_block=learning_data_quality`,
`main_promotion=DEFERRED_UNTIL_BLOCK_COMPLETE`.

Этот этап исправляет накопление сигналов. Он не обучает NLU, не меняет
активный `nlu_intent.joblib`, пороги promotion или классификатора и не
подменяет независимую оценку качества модели успешным запуском этих тестов.
