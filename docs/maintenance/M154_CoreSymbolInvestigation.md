# Исследование функции на одном Git HEAD

Первый ограниченный шаг Core из согласованного плана №113. Он добавляет
проверяемые сведения о связях в Python-коде к существующему окну
«AI-разработка». Новая модель не требуется.

## Использование

1. Ввести цель в поле анализа и нажать «Исследовать функцию…».
2. Указать имя функции либо точный селектор, например
   `modules/text_normalizer.py::normalize_command_text`.
3. При нескольких совпадениях выбрать полный селектор из отчёта и повторить
   исследование. Суффикс `@номер_строки` различает повторные определения.
   Текущий профиль селектора поддерживает имена и пути из ASCII-символов.
4. Изучить определение, исходящие и входящие статические ссылки и unknowns.
   Результат можно скопировать. Он не содержит автоматически созданного diff.
5. Если цель явно просит изменение, существующая кнопка запроса Developer Task
   может подготовить карточку для выбранного файла после повторного захвата
   исходника и проверки привязки.

## Что означает результат

Исследуются функции, async-функции и определения методов. Для каждого
поддержанного прямого вызова указаны caller, callee и место вызова, commit,
Git blob и SHA256 исходника. Чтение выполняется существующим `scan_head` и
`GitSourceReader` только из зафиксированных Git-объектов. Исследуемые модули
не импортируются и не исполняются.

Разрешение имён намеренно ограничено устойчивыми привязками по исходнику.
Параметры, локальное затенение, переприсваивание, динамические атрибуты,
декораторы и неподдержанные контексты не превращаются в уверенные связи.
Методы можно выбрать и изучить, но это не означает доказанного типа `self`
или полной поддержки динамического dispatch.

Ссылка говорит о синтаксической связи в данном исходнике. Она не доказывает,
что вызов выполнится или что имя не будет изменено во время исполнения.
Пустой список входящих связей означает только отсутствие разрешённых ссылок
в охваченном наборе. Он не доказывает, что функция нигде не используется.

Отчёт показывает область чтения, пропущенные/неразобранные файлы, лимиты и
число неразрешённых вызовов. Применяются существующие ограничения чтения
`main.py` и Python-файлов `modules/`, а также отдельные ограничения AST и
размера результата. `vendor`, tests и прочие исключённые области не становятся
покрытыми только потому, что поиск выполнен успешно.

## Карточка Developer Task

Сохраняются исходный mode gate, политика одного разрешённого DTR-A target и
повторный `GitSourceReader.capture`. Изменение цели, HEAD или содержимого
выбранного файла требует нового исследования. Карточка связывает запрос с
выбранным символом, конкретным commit, подтверждёнными ссылками и unknowns.

Исследование не читает рабочий исходник. На отдельном шаге создания DTR-A
штатный capture сверяет рабочий файл с Git, как и прежде. Запрос и его один
полный исходник остаются в существующем локальном хранилище Developer Task.
Нет отправки модели, загрузки весов, обучения или расширения разрешений.

## Проверка и текущий статус

Целевые evaluators:

- `tools/eval_core_symbol_investigation.py` — выбор, разрешение имён,
  неоднозначность, неполнота, привязка и отказ при смене HEAD;
- `tools/eval_core_symbol_task_bridge.py` — DTR-контракт и сохранение привязки,
  запреты при устаревших/повреждённых данных и защищённых путях;
- `tools/eval_core_symbol_ui.py` — headless-проверка состояния окна,
  асинхронного результата и существующих ограничений;
- существующий `tools/eval_package_boundaries.py` — границы пакетов.

Подготовка и синтетические тесты отделены от фактического запуска интерфейса
пользователем. Новый блок `core_symbol_investigation` не считается закрытым
одной установкой или отсутствием исключений в тестах. Предыдущий блок
`learning_event_provenance` уже опубликован в main-коммите
`5ace7d645fc85ec9626ce7befb59ce68b90de505` и закрыт в своём инженерном объёме.
